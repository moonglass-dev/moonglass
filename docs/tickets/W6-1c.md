# Agent: service settings and volumes

The agent applies a `Deploy`'s service settings: the command, labels, restart policy and healthcheck go into the checked spec; each named volume is the managed volume `mg.<project>.<environment>.<name>`, created or reused; every app container gets the alias `<service>.<environment>.internal` and the search domain `<environment>.internal`; a healthcheck gives the Docker health mode of the switch; an app with a volume never runs two releases at once and is never rolled back; and `REMOVE_APP` removes the volumes no other app uses (`docs/specs/release.md`, "Service settings, volumes and names" and "Health"; `docs/specs/delete.md`, "Named volumes"). Owner decision of 2026-11-19.

## Scope

- `internal/deploy`, Deploy:
  - "The container": `Cmd` from `command`, `Labels` from `labels`, `RestartPolicy` from `restart` (empty is `unless-stopped`), `Healthcheck` from `healthcheck`, one `volume` mount per `VolumeMount`, and `NetworkAliases` and `DNSSearch` from the binding. The Engine request carries them from `Checked` only (healthcheck, mounts, endpoint aliases on `mg-<project>`, DNS search).
  - Step 2: the volume rule, `REJECTED` with the exact detail of `docs/specs/release.md`.
  - Step 6: create or check each volume, with the labels and the unmanaged-volume failure of "Volumes".
  - Step 9: the settings recorded on the release row.
- `internal/deploy`, switch and rollback: the Docker health mode of "Health"; `Rollback` refused for a volume app before anything is touched.
- `internal/deploy`, pre-deploy: the step's spec has no aliases and no search domain; it keeps the candidate's command override replaced by `args` as today, and its mounts.
- `internal/deploy`, `REMOVE_APP`: the volumes of "Named volumes", read from agent state before the rows are deleted.
- `internal/agent/state`: a migration adding `command`, `volumes`, `labels`, `restart` and `healthcheck` to `releases` with the defaults of `docs/specs/storage.md` ("Service settings on releases"), and the reads that return them.
- `internal/rollback`: auto-rollback skips an app whose current or previous release mounts a volume, as it skips a stopped app.
- The three specs: already say this; change them only if the built behaviour needs a wording fix.

## Acceptance criteria

- `TestDeployAppliesServiceSettings`: a `Deploy` with a command, two labels, `restart` `on-failure`, a `CMD` healthcheck and one volume creates a container whose inspect shows exactly those (the command, the user labels beside the agent labels, the restart policy, the healthcheck with its timings, the volume mount at its target), plus the alias `<service>.<environment>.internal` on `mg-<project>` and the search domain `<environment>.internal`. A `Deploy` with none of them gives the container of "The container" with no mounts, aliases and search domain set as above.
- `TestDeployCreatesAndReusesManagedVolume`: the first deploy creates `mg.<project>.<environment>.<name>` with the `local` driver, no options and the four labels; after `STOP_APP`, a second deploy of the app mounts the same volume, and a file written by the first container is read by the second.
- `TestDeployRefusesUnmanagedVolume`: a volume of that name without the labels, and one with the labels and a driver option, each fail the step with the exact detail, create no container and write a `failed` row.
- `TestVolumeAppNeverRunsTwoReleases`: a `Deploy` to a running app whose current release mounts a volume, and a `Deploy` that adds a volume to a running app, are `REJECTED` with the exact detail, with state unchanged; the same `Deploy` after `STOP_APP` succeeds.
- `TestRollbackRefusedForVolumeApp`: `Rollback` of an app whose current or previous release mounts a volume is `REJECTED` with the exact detail and no container is started or stopped.
- `TestDockerHealthGate`: with a `CMD` healthcheck that succeeds, the switch passes once the Engine reports `healthy`; with one that fails, the gate fails when the Engine reports `unhealthy`, the candidate is removed and the old release keeps serving; with `NONE`, the gate uses the mode the port gives.
- `TestPreDeployStepGetsNoServiceName`: the pre-deploy container has neither the alias nor the search domain.
- `TestRemoveAppRemovesUnsharedVolumes`: `REMOVE_APP` of a stopped app removes its own volume and keeps one that another app's kept release also mounts; a volume already gone is not an error; a volume used by an unmanaged container fails the command with the exact detail and keeps the app's state rows.
- `TestReleaseSettingsStored`: a release row written with every setting reads back equal, and one written without them reads back the defaults.
- `TestAutoRollbackSkipsVolumeApp`: a crash trigger on a volume app sends no `Rollback`.
- The Docker tests import their images (`docs/specs/deploy-suite.md`), label everything per run and remove it afterwards, including volumes; they skip without an Engine except under `CI`.
- Every existing test passes unchanged.
- `make ci` is green and `scripts/verify check W6-1c` passes.

## Security notes

- `docs/threat-model.md` §6 and §9.2: the Engine request is built from `Checked` only; the volume mount is a `volume` mount of a volume the agent created with no driver options, so no host path is reachable through it. An existing volume with options is refused, never reused.
- Volume names come from the agent's binding, so a `Deploy` reaches only its own environment's volumes (§4: a control-plane takeover still reaches the volumes of the environments it can deploy to, `docs/threat-model.md` §5 limit 1).
- §8: the healthcheck runs inside the container through the Engine; the agent never execs into a container.
- Two releases never write one volume, and nothing but `REMOVE_APP` deletes a volume (`docs/specs/delete.md`).

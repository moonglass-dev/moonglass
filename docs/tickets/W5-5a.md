# Protocol: stop and remove an app

The control plane gains two typed commands for soft delete and purge: `StopApp` under the new type `STOP_APP` = 15 and `RemoveApp` under `REMOVE_APP` = 16, each carrying only `app_id`. `internal/protocol` validates `app_id` with the identifier rule when either payload is opened, rejects unknown fields, and has protocol-abuse tests and a fuzz target for both parsers. This implements "Stop and remove an app (W5-5a)" in `docs/specs/protocol.md` and "Protocol (W5-5a)" in `docs/specs/delete.md` (owner decision D62, field numbers approved with `docs/specs/delete.md` on 2026-11-18).

## Scope

- `proto/moonglass/agent/v1/agent.proto`:
  - `MessageType` gains `STOP_APP = 15` and `REMOVE_APP = 16`. 12 to 14 stay unassigned in this ticket (W4-4 takes them); nothing else is renumbered.
  - New `StopApp { string app_id = 1; }` and `RemoveApp { string app_id = 1; }`, each with a comment that it is a `delete`-class command answered with one `CommandResult`, and that `app_id` is an identifier, never a host path or shell string.
- `internal/protocol/agentv1/agent.pb.go`: regenerated with `make proto`, never edited by hand.
- `internal/protocol`:
  - `validateType` lists `STOP_APP` and `REMOVE_APP`; `typeOf` maps `*agentv1.StopApp` and `*agentv1.RemoveApp`; `validatePayload` calls `validateStopApp` and `validateRemoveApp`.
  - `validateStopApp` and `validateRemoveApp` sit next to `validateRollback` in `deploy.go` and each return `validateID("app_id", …)`. No new rule: the existing identifier rule (1 to 64 bytes of `[A-Za-z0-9._-]`) applies.
  - `Open` already rejects unknown fields through `rejectUnknown`; that covers both new messages.
  - `TestDeployMessagesRejectUnknownType` in `deploy_test.go` uses `15` as an unknown type, which becomes `STOP_APP`. Its list `{UNSPECIFIED, 15, 99}` changes `15` to `2147483647` (the largest enum number, which no ticket assigns), keeping every assertion. This edits an existing test line and needs an owner allowance like the one recorded for W3-7; no other existing test line changes.
- `docs/specs/protocol.md`: the `CommandResult` paragraph's list of commands the agent answers gains `STOP_APP` and `REMOVE_APP` (from W5-5b), and the W5-5a section records that `image_id` and `repo_digest` are empty in their results. The section's numbers and fields are unchanged.

## Acceptance criteria

- `TestStopAndRemoveAppRoundTrip`: a `StopApp` and a `RemoveApp` each round-trip through `Wrap`, `Marshal`, `Unmarshal` and `Open` under `STOP_APP` and `REMOVE_APP` and are `proto.Equal` to the input, for `app_id` of 1 byte, 64 bytes, and one using every allowed punctuation (`a.b_c-D9`). The decoded envelope's `type` is 15 and 16 respectively.
- `TestStopAndRemoveAppRejectMalformed`: for both messages, `Open` rejects with `ErrMalformed`, and the error names `app_id`: empty (the zero message), 65 bytes, containing `/`, a space, a NUL, `:`, a non-ASCII byte, and `../x`.
- `TestStopAndRemoveAppProtocolAbuse`: for both messages, an unknown field appended to a valid payload is rejected with `ErrMalformed`; a `STOP_APP` envelope opened as `RemoveApp` or `Rollback`, and a `REMOVE_APP` envelope opened as `StopApp`, fail with `ErrTypeMismatch`; `Wrap(STOP_APP, …, &RemoveApp{})`, `Wrap(REMOVE_APP, …, &StopApp{})` and `Wrap(STOP_APP, …, &Rollback{})` fail with `ErrTypeMismatch`; a `STOP_APP` or `REMOVE_APP` envelope carrying `error` is rejected by `Marshal` and `Unmarshal`; each message has exactly one field, `app_id`, and no string field whose name looks like a host command (`assertNoShellStringFields`).
- `FuzzOpenStopAndRemoveApp`: arbitrary payload bytes opened under both `STOP_APP` (as `StopApp`) and `REMOVE_APP` (as `RemoveApp`), seeded with a valid payload, a 64-byte `app_id`, empty input, an unknown field and an `app_id` with `/`; `Open` never panics and returns nil or `ErrMalformed`; any accepted payload passes `validateID`, re-wraps, opens again and is `proto.Equal` to the first result.
- Every existing test in `internal/protocol` still passes with its assertions intact; `TestEnvelopeRoundTripEveryType` covers both new types through the descriptor. The only edited existing line is the unknown-type list in `TestDeployMessagesRejectUnknownType`, as above.
- `make proto-check` is clean: `agent.pb.go` matches `make proto` output.
- No new dependency; `go.mod` and `go.sum` are unchanged. No code outside `internal/protocol` changes.

## Out of scope

- What the agent does with either command, the `stopped_at` column, the `delete` command class entry and the per-side send/accept rules and timeouts: W5-5b (with W5-3 for the class table).
- Sending `STOP_APP` from `services.delete`: W5-5d. Sending `REMOVE_APP` from `services.purge` and the retention purge: W5-5e.
- `LOG_REQUEST`, `LOG_CHUNK`, `USAGE` (12 to 14): W4-4.
- Named volumes in `REMOVE_APP`: W6-1.

## Security notes

- `docs/threat-model.md` §3 (the agent treats the control plane as hostile): each payload carries only `app_id`, restricted to `[A-Za-z0-9._-]`, 1 to 64 bytes, checked when the payload is opened before later code acts. No field is a host path, shell string, container name or image reference, so a hostile control plane can name only an app the agent already knows.
- §8 (local policy beats remote command) and `docs/specs/local-policy.md`: both are `delete`-class, so `forbid = ["delete"]` refuses them; this ticket only defines the types, and nothing in a message can change the class (W5-5b, W5-3).
- §9 reviewer checklist: the `.proto` contract changes (`STOP_APP = 15`, `StopApp.app_id = 1`, `REMOVE_APP = 16`, `RemoveApp.app_id = 1`), as approved by the owner with `docs/specs/delete.md` (D62). The plan step must also obtain the owner's allowance for the one edit to an existing test line in `internal/protocol/deploy_test.go` (`15` → `2147483647` in `TestDeployMessagesRejectUnknownType`), recorded in the pipeline prompts as for W3-7. There is a protocol-abuse test and a fuzz target for each new parser.

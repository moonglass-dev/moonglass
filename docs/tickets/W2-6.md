# Pre-deploy steps

After this ticket the agent's executor runs `RunPreDeploy`: a sanitized one-off container from the candidate's image runs the step's argv before the candidate starts. Exit code 0 makes the candidate `ready` and starts it; anything else aborts the deploy and leaves the old release serving. `reversible` is stored for auto-rollback and changes nothing here; steps count as irreversible by default. This implements `docs/specs/release.md`, "Executor: pre-deploy steps (W2-6)".

## Scope

- `internal/deploy`:
  - `func (x *Executor) RunPreDeploy(ctx context.Context, r *agentv1.RunPreDeploy) *agentv1.CommandResult`, in its own file.
  - Order: read the app (`db.App`). An unknown app is `REJECTED`. Apply `State.PreDeployDone(release_id, true)` in memory; an illegal transition is `REJECTED` and nothing is touched. Read the candidate's stored record (image ID, container ID) from `internal/agent/state`. Build the step's `policy.Spec` and call `policy.Check`; a `Rejection` is `REJECTED` with the rendered rejection as `detail`, nothing is created, and the state is unchanged (`docs/specs/protocol.md`: `REJECTED` is refused before acting). Make sure the project network exists (`ensureNetwork`). Clear the name `mg-<app_id>-<release_id>-pre` with the same leftover rule as the candidate's name (`clearName`). Create the container from the `Checked` value and nothing else, start it, and wait for it to exit.
  - The step's spec is the candidate's `appSpec`, except: `Kind` `pre_deploy`; `Image` the candidate's stored image ID; `Cmd` = `args`, never joined; `RestartPolicy` `no`; `AgentLabels` also carry `dev.moonglass.role=pre_deploy`. `Env` stays empty until W4-8.
  - The step has a 15-minute limit, held in an unexported `Executor` field that `New` sets to 15 minutes, so a package test can shorten it. Over it the container is killed and the step fails. Every other Engine call keeps the 60-second limit of `call`.
  - Exit code 0: start the candidate container (with W2-3's `start` and its running check), then record the outcome and answer `SUCCEEDED` with the app state (phase `READY`).
  - Any other exit code, including a kill on the time limit: apply `PreDeployDone(id, false)`, force-remove the candidate container, record the release row as `aborted`, and answer `FAILED` with exactly `pre-deploy step exited with code <n>; its output is in the logs of container mg-<app_id>-<release_id>-pre`.
  - An Engine error at any step after the transition (missing image, a foreign container holding the step's name, create, start, wait or kill failing, or the candidate failing to start after exit 0): the same abort, with `FAILED` and the wrapped error as `detail`.
  - The step container is never removed by this ticket: it stays, stopped, so its logs stay readable. The step's output is never read into the result, the `detail` or the database.
- `internal/agent/state`:
  - A read of one release's stored record (`Record`) by app and release id.
  - One write that records a pre-deploy outcome in one transaction: the app's new release state, `pre_deploy_reversible` = the sent `reversible`, and, on abort, status `aborted`, `error` = the `detail` and `container_id` empty. On success the row stays `candidate`. It refuses, writing nothing, when the given state does not follow from the stored one for that release (the release is not the app's pending candidate).
- `internal/deploy/testdata/server`: whatever modes the tests need from the test binary (print a marker to stdout and stderr, exit with a given code, sleep), selected by its argv. It stays standard library only.
- `docs/specs/release.md`: add to the W2-6 section the three rules this ticket pins down: a policy `Rejection` of the step is `REJECTED` with the state unchanged; a leftover `-pre` container follows the candidate's leftover rule; a candidate that fails to start after exit 0 aborts like an Engine error.

## Acceptance criteria

- `TestPreDeploySpecDerivesFromCandidate` (no Docker): the step's spec equals the candidate's `appSpec` field by field except `Kind` `pre_deploy`, `Image` = the candidate's image ID, `Cmd` = `args`, `RestartPolicy` `no`, and the extra label `dev.moonglass.role=pre_deploy`; `Env`, `Labels`, mounts and every other field are zero.
- `TestRunPreDeploySuccessStartsCandidate`: after a `Deploy` with `has_pre_deploy`, a step that exits 0 answers `SUCCEEDED` with phase `READY`; the candidate container is running; `mg-<app>-<rel>-pre` exists, stopped with exit code 0, runs the candidate's image ID with `Cmd` = `args`, restart policy `no`, the agent labels plus `dev.moonglass.role=pre_deploy`, on `mg-<project>`, with no environment variables beyond the image's own; the row is `candidate` with `pre_deploy_reversible` equal to the sent value, tested for both `true` and `false`.
- `TestRunPreDeployFailureAbortsDeploy`: a step that exits 3 answers `FAILED` with the exact detail of Scope (code 3); `Current` and `Previous` are unchanged and there is no candidate, in the result and in the database; the candidate container is gone; the row is `aborted` with that detail as `error` and an empty `container_id`; the step container is kept, stopped; a new `Deploy` of another release is then `SUCCEEDED`.
- `TestRunPreDeployOutputStaysOutOfResult`: a step that prints a random marker to stdout and stderr and exits 1: the marker is in the step container's logs, and not in the result's `detail`, in any field of the result, or in the release row.
- `TestRunPreDeployTimeoutKillsStep`: with the limit shortened to a few seconds, a step that sleeps longer is killed: the result is `FAILED` with the exit-code detail of the killed container, the step container is not running, the deploy is aborted as above, and the call returns within the limit plus the Engine calls, not after the sleep.
- `TestRunPreDeployEngineErrorAborts`: when the candidate container is removed behind the executor's back, a step that exits 0 still answers `FAILED` (the candidate cannot start), with the deploy aborted and the row `aborted`.
- `TestRunPreDeployRejectsIllegalTransition`, table-driven: an unknown app, a release id that is not the candidate, a `ready` candidate (deployed without `has_pre_deploy`), and a second `RunPreDeploy` after a successful one are each `REJECTED`; no `-pre` container is created for them, the stored state and row are unchanged, and a running candidate is not touched.
- `TestRunPreDeployReplacesLeftoverStepContainer`: a managed container of the same app and release left under `mg-<app>-<rel>-pre` is removed and the step runs and succeeds; a container under that name with other labels makes the step `FAILED`, aborts the deploy, and the foreign container is left in place.
- `TestRecordPreDeployOutcome` (`internal/agent/state`), table-driven: success leaves the row `candidate`, sets `pre_deploy_reversible` and stores phase `ready`; abort sets the row `aborted` with the error and an empty `container_id`, and clears the candidate with `current` and `previous` unchanged; a state that does not follow (unknown app, release not the pending candidate) writes nothing and returns an error.
- Docker tests follow `docs/specs/deploy-suite.md`: imported images, a project name per run, everything labelled and removed afterwards; they skip without an Engine except under `CI`.
- No protocol, `.proto`, migration, storage-schema or `agent.toml` schema change. `make ci` is green.

## Out of scope

- Health gate, switch, draining, the `Abort` transition, retirement and removal of step containers with their release, keep five (W2-4).
- Dispatching `RUN_PRE_DEPLOY` from the connection, request-id records and the `commands` table (W2-10).
- The environment's secrets in the step container (W4-8, W3-5).
- Auto-rollback's use of `pre_deploy_reversible` (W4-3).
- The disk guard's refusals (W3-6), command-class enforcement (W5-3).
- The end-to-end G2 check that a failing step leaves the old release serving (W2-E).

## Security notes

- `docs/threat-model.md` §3 B3 and B5, §6, §8, §9 questions 1, 2, 3, 8 and 9.
- The step container passes `policy.Check`, and the executor creates only the `Checked` value: the same deny list as every container (§6), with no exception for pre-deploy steps. The checked spec is the spec that is sent, command included.
- `args` is an exec argv placed in `Cmd`: never joined, never passed to a host or container shell (§8, "No host shell"). The agent runs nothing on the host.
- The step runs from the candidate's immutable image ID, so the image admitted by its `Deploy` is the image that runs (`docs/specs/local-policy.md`: `RUN_PRE_DEPLOY` is not re-checked).
- The step's output never reaches the `CommandResult`, the `detail`, the database or the agent's logs: an app can print its own environment (ADR-0004 decision 12, §9 question 3).
- A failed, killed or errored step never changes `Current` or `Previous`: the old release keeps serving.

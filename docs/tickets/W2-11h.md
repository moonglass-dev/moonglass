# ResolveTarget names the known project

When the project exists in the org and the named environment does not, `store.ResolveTarget` returns the project's id, an empty environment id and an error matching `ErrNotFound`; for an unknown project it still returns two empty ids (`docs/specs/storage.md`, "`ResolveTarget`"). After this ticket `registry.Invoke` (W2-11c) can tell from one call which name did not resolve, and match a scope row's project column by id (`docs/specs/registry.md`, "Which name did not resolve"). Owner decision of 2026-11-19, split out of W2-11c.

## Scope

- `internal/store/projects.go`: `ResolveTarget` keeps its signature and its one org-bound transaction. On a missing environment it returns the project id it read, `""`, and the existing wrapped `ErrNotFound`. Every other path returns what it returns today: both ids on success, two empty ids with the error for an unknown project or any other failure.
- `internal/store/store.go`: the interface comment states the four cases of the table in `docs/specs/storage.md`.
- `internal/store`: a new conformance function run on both backends as the two named tests. The existing `runProjectsConformance` cases are not changed.
- `docs/specs/storage.md`: already says this; change it only if the built behaviour needs a wording fix.

## Acceptance criteria

- `TestResolveTargetReportsKnownProjectSQLite` and `TestResolveTargetReportsKnownProjectPostgres` run one conformance function that checks, in an org A with project `web` and environment `prod`, and an org B with project `b-only`:
  - `("web", "prod")` returns both ids and nil;
  - `("web", "")` returns the project id, `""` and nil;
  - `("web", "nope")` returns the project id `CreateProject` returned, `""`, and an error matching `ErrNotFound`;
  - `("nope", "prod")` and `("nope", "")` return `""`, `""` and an error matching `ErrNotFound`;
  - `("b-only", "")` and `("b-only", "prod")` asked by org A return `""`, `""` and an error matching `ErrNotFound`: another org's project id is never returned.
  - Each failure message shows the expected and actual triple.
- The Postgres test skips when `MOONGLASS_TEST_POSTGRES` is empty, except under `CI`, where it fails.
- Every existing `internal/store` test passes unchanged.
- `make ci` is green and `scripts/verify check W2-11h` passes.

## Out of scope

- W2-11c: `registry.Invoke` using the returned id, the 404 messages and the scope match.
- W5-5c, W5-8a: leaving deleted rows out of `ResolveTarget`.

## Security notes

- `docs/threat-model.md` §3 B2 and §9.5: the call stays in one transaction bound to the caller's org; RLS on Postgres and the `org_id` predicate on both backends still apply, so the id returned is always the caller's own project.
- §9.4: the returned id lets `Invoke` deny a token scoped to another project in the same way whether or not the environment exists. The error text is never sent to a caller (`docs/specs/registry.md`).

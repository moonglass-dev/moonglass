# Rollback executor

After this ticket the agent can execute `Rollback`: it applies `release.State.Rollback`, makes sure the previous release's container is running and healthy, pushes the complete proxy config with the previous release routed in place of the current one through the agent's one `*deploy.Proxy`, and commits the rollback in one state transaction. A running previous container makes the rollback a route push that finishes in under 5 seconds (G2). This implements `docs/specs/release.md`, "Executor: Switch, drain and rollback (W2-4)", "Rollback" steps 1 to 5, reusing the health gate and `Proxy.PushRouted` of W2-4b.

## Scope

- `internal/agent/state`: one one-transaction write on the existing schema (no migration):
  - `RecordRollback(ctx, appID, next, now)`: refuses, writing nothing, when the app is unknown or `next` does not equal the stored state's `Rollback()` (the `sameState` check `RecordSwitch` uses). Otherwise the restored row (`previous`) becomes `current` with `switched_at` = now and `stop_after` cleared to null, so no later stop is due on the serving release; the row rolled back from (`current`) becomes `retired` with `stop_after` = now + 30 seconds; the candidate row, if any, is untouched; and the `apps` row becomes `next`. Each row update goes through `updateOne` with the expected old status.
- `internal/deploy`: `Executor.Rollback(ctx, *agentv1.Rollback) *agentv1.CommandResult`, in this order:
  1. An unknown app is `REJECTED` (`app <app_id> has no release on this server; deploy it first`). `State.Rollback` illegal (no previous) is `REJECTED` with the machine's error. Nothing else is read or touched.
  2. The previous release's record is read; a missing record is `FAILED`. A record with an empty `container_id`, or a container the Engine does not find, is `FAILED` with exactly `the previous release's container is gone; deploy again`, the stored state unchanged and nothing pushed.
  3. If the container is running, nothing is started and no gate runs. If it is stopped, it is started with the existing `engine.start`, then the existing `healthGate` runs on it with the binding's project. A failed start or gate is `FAILED` with its detail and the stored state unchanged: nothing is pushed, nothing is committed, no row changes, and the container is not removed (it is still the app's previous release).
  4. The config is pushed with the previous release routed in place of the current one through `x.proxy.PushRouted`, with `RecordRollback` as the commit, so it runs inside the push lock. A failed push is `FAILED` with the stored state unchanged; a re-sent `Rollback` can then succeed. A failed commit is `FAILED` with the stored state unchanged, and `PushRouted` clears the last pushed document as it already does.
  5. Success answers `SUCCEEDED` with the new app state.
  - No other push path, gate or start path is added; the rollback reuses those of W2-4b and W2-3.
- `docs/specs/release.md`, "Rollback": the order above, that step 2 routes the previous release in place of the app's stored current release through `Proxy.PushRouted` with the commit inside its lock, that a failed start, gate, push or commit is `FAILED` with the stored state unchanged and the container left in place, and that the restored row's `stop_after` is cleared and its `switched_at` set to now.
- `docs/specs/agent-state.md`, "Rules": a rollback (W2-4d) is one transaction with the statuses and times above; a state that does not follow from the stored one writes nothing.

## Acceptance criteria

- `TestRecordRollbackRestoresPrevious`: after two recorded switches, `RecordRollback` with the state `Rollback()` returned sets the restored row `current` with `switched_at` = now and `stop_after` null, the rolled-back row `retired` with `stop_after` = now + 30 seconds in RFC 3339 UTC, and the `apps` row to `next` with previous null; with a candidate present its row and the `apps` candidate and phase are unchanged; an unknown app, an app with no previous, and a `next` that does not follow from the stored state each write nothing and return an error.
- `TestRollbackRunningPreviousRoutesAndCommits`: against real Docker and the fake admin socket of `proxy_test.go`, after two switches the previous container is still running; `Rollback` answers `SUCCEEDED` with current = the old previous and previous empty, within 5 seconds; the posted `/load` document routes the restored release's container IP and port with its release id in `moonglass_counter`; the stored rows match `RecordRollback`'s rules; the rolled-back container is not stopped or removed by the rollback.
- `TestRollbackStoppedPreviousStartsAndGates`: with the previous container stopped, `Rollback` starts it, runs the gate and then pushes and commits, answering `SUCCEEDED`; with a previous container whose gate fails (the `testdata/server` mode that answers a failing status, with the shortened limit), the answer is `FAILED` with the gate's detail, nothing is posted to `/load`, the stored state and rows are unchanged, and the container still exists.
- `TestRollbackPreviousContainerGone`: with the previous container removed from the Engine, and separately with its `container_id` empty in agent state, `Rollback` answers `FAILED` with `the previous release's container is gone; deploy again`, nothing is posted and the stored state is unchanged.
- `TestRollbackRefusalsAndPushFailure`: an unknown app and an app with no previous (first release only, or right after a rollback) are each `REJECTED` with stored state and rows unchanged, no Engine container call and nothing posted; a `/load` answering non-2xx is `FAILED` with the stored state unchanged and the rows as before, and a re-sent `Rollback` then succeeds.
- `TestRollbackLeavesCandidateUntouched`: with a `ready` candidate present, a successful `Rollback` leaves the candidate id, its phase, its row status `candidate` and its running container unchanged, and the pushed document does not route the candidate.
- No result `detail` or stored `error` contains a health-probe response body.
- `Rollback` starts no goroutine that outlives it, and nothing stops or removes the rolled-back container (that is W2-4).
- `make ci` is green.

## Out of scope

- The stops and removals at `stop_after`, start-up reconcile stops, keep five and retention: W2-4.
- Dispatching `Rollback` from the connection and command records: W2-10.
- `moonglass rollback`, auditing and the control-plane side: W2-5.
- The volume refusal of rollback and the healthcheck gate mode: W6-1c.
- Auto-rollback triggers: W4-3.

## Security notes

- `docs/threat-model.md` §3 B4: the rollback push is a complete JSON config over the admin Unix socket through the one `Proxy`; nothing dials a TCP admin port.
- §3 B5 and §9.2: the rollback creates no container; the only Engine calls are inspect and start of the previous release's container named in agent state, plus the gate's inspects.
- §3 B3 and §8 "Local policy beats remote command": `Rollback` carries only `app_id`; the release it restores comes from agent state, and the probe target is that container's own address on its project network with the stored `port` and `health_path`, never anything from the message.
- §9.3: a probe's response body is never read into a result, a stored `error` or a log line.
- §9.8: one push path (`Proxy.PushRouted`), one gate (`healthGate`), one rollback write (`RecordRollback`), no code for W2-4's stops.

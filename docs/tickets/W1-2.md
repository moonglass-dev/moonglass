# Add the control-plane storage foundation

## Outcome

`internal/store`, `internal/store/pg` and `internal/store/sqlite` open, migrate, and query the first control-plane schema on both backends. The behaviour is `docs/specs/storage.md`, which this ticket writes and may edit, and must stay faithful to ADR-0002 and threat-model boundary B2.

Tables: `orgs`, `memberships`, `servers`, and the lookup tables `user_identities`, `user_orgs`, `agent_keys`, `enrolment_token_hashes`. RLS on Postgres binds the application role; a query that forgets its `org_id` filter cannot return another org's rows. The conformance suite runs the same fixtures and queries against both backends. CI runs `postgres:18` as a service and sets `MOONGLASS_TEST_POSTGRES`.

Pin `github.com/jackc/pgx/v5 v5.13.0` and `modernc.org/sqlite v1.62.0` in `go.mod` and in a new accepted ADR-0010 (storage dependencies), imported only from `internal/store`. Record them in the depguard allow list. Confine the allow to `internal/store` if depguard file globs combine correctly; if they do not (see `docs/harness-followups.md`), allow globally and deny the imports from `cmd/` and `internal/protocol/` as W1-1 did for policy, and do not spend the ticket on tightening depguard.

## Out of scope

- Enrolment flow, `moonglass server` / `moonglass agent enroll`, connection, heartbeat (W1-3, W1-4).
- `LISTEN/NOTIFY`, logical export, backups, the agent's on-server SQLite.
- Sign-in, sessions, API tokens, the operation registry (W4-1, W2-1).
- Choosing the managed Postgres provider (ADR-0002 open question 1). Leave it open.
- Profile names, emails, or other user PII columns.
- A separate `roles` table. Roles are the four ADR-0006 values on `memberships.role`.

## Acceptance tests

- `TestSchemasMatch`: after migrations, Postgres and SQLite describe the same tables and columns (names and nullability).
- `TestLookupTablesMatchSchema`: the lookup-table list in `internal/store` matches the schema on both backends; every non-lookup table has `org_id`; no lookup table has a name, secret, wrapped key, plaintext token, or scope column.
- `TestConformanceSQLite` and `TestConformancePostgres`: the same suite against each backend (Postgres skips locally when `MOONGLASS_TEST_POSTGRES` is empty, and fails in CI if it is empty). Covers org create, minting a user via an external identity, memberships including the four roles and a duplicate rejection, listing a user's orgs, storing a server and finding it by public key, enrolment token insert / lookup / mark-used / replay, and that store methods for org A do not return org B's rows.
- `TestPostgresMissingOrgFilterReturnsNothing`: as the application role, a `SELECT` with the `org_id` filter removed never returns another org's rows; with `app.org_id` unset or set to a nonexistent org it returns nothing. See the spec.
- `TestAppRoleCannotBypassRLS`: the application role does not own the tables and does not have `BYPASSRLS`; a migration is not applied as that role.
- `TestEnrolmentTokenStoredHashedOnly`: inserting a bearer token stores only the SHA-256 hash; a lookup by a different token fails; no table contains the plaintext or the `mg_…` value.
- `TestMigrateIdempotent`: applying an already-applied migration set succeeds and changes nothing.

## Security notes

Threat-model boundary B2 and the store questions in the review checklist: only the storage package writes SQL; RLS plus the application role; lookup tables are the only tables without `org_id` and hold only a lookup key, IDs, expiry and a revoked marker; tokens are stored hashed; no plaintext secret reaches the database.

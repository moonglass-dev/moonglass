# Deploy executor

`internal/deploy` runs a `Deploy` command against the Docker Engine: it resolves the image (pulling a tag, using a digest reference or a server-built `moonglass.local/...` image from the local store), makes sure the project network exists, builds the container spec, sanitizes it with `policy.Check`, creates the candidate container from the `Checked` value only, starts it unless a pre-deploy step follows, and records the release through `internal/agent/state`. Every outcome is a `CommandResult`. Its start-up reconcile removes only the managed containers that are not the current, previous or candidate release of their app. This implements "Executor: Deploy (W2-3)" in `docs/specs/release.md` and ADR-0014; tests run against a real Docker Engine.

## Scope

- `internal/deploy` (new package):
  - **Engine.** A constructor (indicatively `Connect(ctx) (*Engine, error)`) that builds the `github.com/moby/moby/client` client from `DOCKER_HOST`, or `/var/run/docker.sock` when unset, and refuses any non-`unix://` host. It negotiates the API version (the client's default), pings the Engine, and returns the ADR-0014 error `Docker Engine API <v> is older than 1.44 (Docker Engine 25); upgrade Docker Engine` when the negotiated version is below 1.44. Making the agent exit on that error at start is W2-10's wiring.
  - **Executor.** Indicatively `New(engine, *policy.Policy, *state.DB)`, `Deploy(ctx, *agentv1.Deploy) *agentv1.CommandResult` and `Reconcile(ctx) error`. `Deploy` follows "Order" steps 1–8 of `docs/specs/release.md` exactly: binding, transition, image, check, network, create, start, record.
  - **Images** as in the spec's "Images": a digest reference uses the local image when present and pulls otherwise; a tag is always pulled; `moonglass.local/<project>/<service>:<release_id>` is never pulled, fails with `image <ref> is not on this server; build it again` when missing, and is `REJECTED` when `<project>` is not the app's own project. After resolving, the image is inspected for its ID and, for a pulled or digest reference, the `RepoDigests` entry of that repository. Pulls have a 15-minute limit; every other Engine call 60 seconds. No image archive is ever loaded.
  - **The container spec** exactly as the spec's table: `Kind` `app`; project, environment and service from the binding; `Image` = `<repository>@<repo digest>`, or the image ID when there is no digest; empty `Cmd`, `Env`, `Labels`; the six `dev.moonglass.*` agent labels; `Networks` `[mg-<project>]`; `RestartPolicy` `unless-stopped`; `LogConfig` driver `local` with `max-size=10m`, `max-file=3`; everything else zero.
  - **Create from `Checked` only.** The Engine create request (config, host config, networking config) is built from `Checked.Spec()` and nothing else, under the name `mg-<app_id>-<release_id>`, with labels = `Labels` plus `AgentLabels`. A `Checked` field the translation does not carry to the Engine is never dropped silently: a non-zero one fails the step before create.
  - **Name conflicts** as in "The container": a same-name container labelled `dev.moonglass.managed=true` with the same app and release is removed first; any other same-name container fails the step.
  - **The project network** `mg-<project>`: a bridge network labelled `dev.moonglass.managed=true` and `dev.moonglass.project=<project>`, created when missing; a same-name network without those labels fails with `network mg-<project> exists and is not managed by Moonglass`. Networks are never removed.
  - **Failure** as in the spec's "Failure": nothing is created before step 6; a container created in step 6 is force-removed when step 6 or 7 fails; a started container must still be running when the start call returns; a pulled image stays in the store; every `FAILED` or `REJECTED` after step 2 writes a `failed` row via `state.RecordFailed` with the `detail` as `error`; the release state is never changed by a failure. A `CommandResult` always carries the app's state after the command.
  - **Reconcile.** Lists containers labelled `dev.moonglass.managed=true`, looks up each one's app with `state.DB.App`, and force-removes each container whose `dev.moonglass.release` is not the current, previous or candidate release of that app (including containers of an app with no `apps` row). The decision is a pure function over the labels and a `release.State`. Unmanaged containers are never touched. The `stop_after` stops are W2-4.
- `go.mod`, `go.sum`: add `github.com/moby/moby/client v0.6.3` and `github.com/moby/moby/api v1.57.0` (ADR-0014 decision 1).
- `.golangci.yml`: add both modules to the depguard `main` allow list, and a deny rule listing every existing package except `internal/deploy` (as the `age-deps` rule does), including `cmd/`, `internal/agent/**` and `tools/`, so that only `internal/deploy` can import them today (ADR-0014 decision 2).
- `docs/specs/release.md`: only if the implementation shows the W2-3 section is wrong or incomplete; no new behaviour.

## Acceptance criteria

All Docker tests follow `docs/specs/deploy-suite.md`: `DOCKER_HOST` or the default socket; skip when no Engine answers, fail under `CI`; a project `t` + 12 random lowercase hex per run; everything with that `dev.moonglass.project` label (and any unlabelled network a test made) removed at the end, pass or fail; test images are a static Go HTTP server imported under `moonglass.local/<test project>/<service>:<release_id>`; the only pulled image is `registry:2` pinned by digest. Each test uses a fresh `state.Open` in `t.TempDir()` and a `policy.Parse` of an empty `agent.toml`.

- `TestDeployImportedImageStartsCandidate`: a first `Deploy` of an imported image answers `SUCCEEDED` with the image's `image_id`, an empty `repo_digest` and `AppState` candidate = the release, phase `READY`. The network `mg-<project>` exists with both labels. Container `mg-<app_id>-<release_id>` is running, and its inspect shows exactly the six agent labels with the right values, restart policy `unless-stopped`, log driver `local` with `max-size=10m` and `max-file=3`, only the `mg-<project>` network, the image ID as image, and no mounts, published ports, added capabilities or privileged flag. `state.DB.App` returns the binding and the candidate state, and the `releases` row is `candidate` with the image ID and container ID.
- `TestDeployWithPreDeployLeavesContainerCreated`: with `has_pre_deploy` the result is `SUCCEEDED` with phase `PENDING`, and the container exists in state `created`, not running.
- `TestDeployRejectsBeforeActing`, table: (a) a `Deploy` for a bound `app_id` naming another project, environment or service; (b) a `Deploy` while a candidate exists; (c) a `moonglass.local/<other project>/...` image. Each answers `REJECTED`; (a) names the stored triple; no container or network is created by the call and the stored state is unchanged; (a) and (b) write no `releases` row, (c) writes a `failed` row with the detail as `error`.
- `TestDeployFailuresLeaveStateUnchanged`, table: (a) a missing `moonglass.local` image fails with `image <ref> is not on this server; build it again`; (b) an unlabelled network `mg-<project>` fails with `network mg-<project> exists and is not managed by Moonglass`; (c) an image whose process exits at once fails and its container is removed; (d) a same-name container without the managed labels fails, names the container and is left in place. Each answers `FAILED`, writes a `failed` row with the detail as `error`, leaves the release state and binding as they were (no `apps` row on a first deploy), and leaves no container of the release behind except the pre-existing one in (d).
- `TestDeployReplacesLeftoverContainer`: a pre-existing created container `mg-<app_id>-<release_id>` with `dev.moonglass.managed=true` and the same app and release labels is removed, and the deploy succeeds with a new container ID.
- `TestDeployResolvesRegistryImages`: against a local `registry:2` on a `:0` port: (a) a tag is pulled even when a different local image has that tag, and `repo_digest` and the stored row are the digest the registry serves for it, and the container runs `<repository>@<digest>`'s image; (b) a digest reference whose image is already local deploys after the registry has been stopped, so no pull happened.
- `TestReconcileKeepsReferencedReleases`, pure table over the reconcile decision: a container whose release is the current, previous or candidate of its app's `release.State` is kept; any other release, an app with no state, and a container missing the app or release label are removed.
- `TestReconcileRemovesUnreferencedContainers`: after a deploy of release r1, a managed container for an older release of the same app, a managed container for an unknown app, and an unmanaged container exist; `Reconcile` removes the first two and keeps r1's container and the unmanaged one.
- `TestEngineAPIVersionFloor`, table: versions `1.40` and `1.43` give exactly `Docker Engine API <v> is older than 1.44 (Docker Engine 25); upgrade Docker Engine`; `1.44`, `1.47` and `1.57` pass.
- `TestConnectRequiresUnixSocket`, table: `DOCKER_HOST` of `tcp://127.0.0.1:2375`, `ssh://host`, `npipe:////./pipe/docker_engine` and `http://localhost` are refused with an error naming the value, before any network call; a `unix://` path is accepted by the host check.
- Every Engine container-create request in the package is built from a `policy.Checked` value; no other code path creates a container. No result `detail`, error or log line contains an environment value.
- Pulls are bounded by 15 minutes and every other Engine call by 60 seconds.
- Only `internal/deploy` imports `github.com/moby/moby/...`; `make ci` (depguard included) passes, and `CGO_ENABLED=0` builds still pass.
- `testdata/tests.txt` is regenerated with `make test-list`.

## Out of scope

- Switch, health gate, drain, `Abort`, keep-five, retention and the `stop_after` stops in the start-up reconcile: W2-4.
- `RunPreDeploy` and starting a pending candidate: W2-6.
- Wiring the executor, `agent.toml` and the Engine check into the agent's start and command dispatch; `commands` rows and request-id idempotency: W2-10.
- The control plane's one-deploy-per-service queue and CLI: W2-5.
- The deploy-correctness suite and the Engine 25–29 matrix: W2-7.
- Disk refusal at step 2 and image pruning: W3-6. Builds: W3-4. Secret delivery into `Env`: W4-8.
- Domain conflicts between apps at `Deploy` and proxy config: W2-4.

## Security notes

- `docs/threat-model.md` §3 B5: the Engine socket is root-equivalent. Nothing reaches it without passing the sanitizer: every container is created from a `policy.Checked` returned by `policy.Check`, and the checked spec is the exact spec sent (§9 checklist item 2). A field that cannot be carried is a failure, never stripped.
- §3 B3: the control plane is treated as hostile. The binding check stops a control plane from moving an app into another project's `agent.toml` blocks, and the `moonglass.local/<project>/` check stops one project from running another's build. The image reference is never passed to a shell; there is no host shell anywhere (§8).
- §6: the app spec sets no denied field: no mounts, no published ports, no capabilities, no host namespaces, default runtime. `dev.moonglass.*` labels come only from agent code (`AgentLabels`); `Labels` is empty.
- ADR-0004 decision 12 and §9 item 3: no environment value in any `detail`, error, log line or `releases.error`; registry credentials are not handled by this ticket.
- ADR-0014: only the Unix socket; API 1.44 floor; the moby modules are importable only from `internal/deploy` today.
- ADR-0010 / `docs/specs/agent-state.md`: the executor writes only release records through `internal/agent/state`, never key material, and opens no SQL itself.

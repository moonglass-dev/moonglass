# Link-token and step-up tables

The store gains the `link_token_hashes` lookup table and the `step_ups` row-level table on Postgres and SQLite, as `docs/specs/auth.md` ("Storage") specifies. After this ticket, a link token can be stored for a user by the SHA-256 of its `mg_` bearer and marked used exactly once by its row ID. The row ID is what the provider round trip carries for `purpose=link`. A second use fails with `ErrTokenUsed`, and a use after expiry with `ErrTokenExpired`. A step-up row can be created in an org, bound to one user, one credential, one operation, one target and one input digest, and read back by ID only inside that org. Nothing calls these methods yet. Step-up is W4-1c and linking is W4-1.

## Scope

- `internal/store/migrations/pg/` and `internal/store/migrations/sqlite/`: one new migration per backend, numbered after the highest file on `main` when the ticket is built. An applied migration is never edited (`internal/store/migrate.go`). The two schemas stay identical in table, column and nullability. The migration:
  - creates `link_token_hashes` with exactly these columns: `hash` (`TEXT NOT NULL PRIMARY KEY`), `id` (`TEXT NOT NULL UNIQUE`), `user_id` (`TEXT NOT NULL`), `expires_at` (`TEXT NOT NULL`) and `used_at` (`TEXT`, NULL until used). It has no RLS on Postgres;
  - creates `step_ups` with exactly the columns of `docs/specs/auth.md`:
    - `org_id` (`TEXT NOT NULL REFERENCES orgs (id)`);
    - `id` (`TEXT NOT NULL PRIMARY KEY`);
    - `user_id`, `operation`, `input_digest`, `created_at` and `expires_at` (`TEXT NOT NULL`);
    - `token_id`, `session_id`, `project_id` and `environment_id` (`TEXT NOT NULL DEFAULT ''`);
    - `confirm_hash`, `signed_in_at`, `approved_at`, `declined_at` and `used_at` (`TEXT`, NULL until set);
    - a `CHECK` that exactly one of `token_id` and `session_id` is non-empty.

    On Postgres the migration also adds `ENABLE ROW LEVEL SECURITY` and the `org_isolation` policy with the same `USING` and `WITH CHECK` expressions as `rollbacks`.
- `internal/store/lookup.go`: `link_token_hashes` joins `LookupTables`. `step_ups` does not.
- `internal/store/store.go`:
  - `type LinkToken struct { ID, UserID, ExpiresAt string }`. It has no hash field.
  - `type StepUp struct` with `OrgID`, `ID`, `UserID`, `TokenID`, `SessionID`, `Operation`, `ProjectID`, `EnvironmentID`, `InputDigest`, `CreatedAt`, `ExpiresAt`, `SignedInAt`, `ApprovedAt`, `DeclinedAt`, `UsedAt`. An unset NULL column reads back as empty text. It has no confirmation-hash field.
  - `ErrTokenUsed` and `ErrTokenExpired` keep their names and identities. Their text drops "enrolment", because link tokens now return them too: `store: token already used` and `store: token expired`.
  - `Store` gains:
    - `AddLinkToken(ctx, userID, tokenHash string, expires time.Time) (LinkToken, error)`. It mints the ID with `NewID`, stores the row and returns the link token. A repeated hash is `ErrDuplicate`.
    - `UseLinkToken(ctx, linkID string, now time.Time) (LinkToken, error)`. In one `UPDATE` it sets `used_at` to `now` on the row with that ID, only when the row is unused and its `expires_at` is after `now`, and it returns the row. Otherwise nothing changes, and the call returns:
      - `ErrNotFound` for an unknown ID;
      - `ErrTokenUsed` when `used_at` is set, whatever the expiry;
      - `ErrTokenExpired` when the token is unused and `expires_at` is not after `now`.
    - `CreateStepUp(ctx, orgID string, su StepUp, now, expires time.Time) (StepUp, error)`. It mints the ID with `NewID` and stores `su` in the org with `created_at` set to `now` and `expires_at` set to `expires`. It returns the stored row. The caller's `OrgID`, `ID`, times and markers are ignored. These are refused before any SQL runs, with an error that names the rule:
      - an empty `UserID`, `Operation` or `InputDigest`;
      - a `TokenID` and `SessionID` that are both set or both empty.
    - `StepUp(ctx, orgID, id string) (StepUp, error)`. It returns the row inside the org-bound transaction. `ErrNotFound` when no step-up with that ID is in `orgID`, including another org's step-up.
- `internal/store/linktokens.go` (new): the two link-token methods on `SQLStore`. They are plain SQL in the common subset, run through `s.q` on `s.db`, and read without `app.org_id`, like `sessions.go`.
- `internal/store/stepups.go` (new): the two step-up methods on `SQLStore`, through `s.inOrg`, with `org_id` in every `WHERE`, like `rollbacks.go`.
- `internal/store/schema_test.go`: the expected list in `TestLookupTablesMatchSchema` gains `link_token_hashes`. Nothing in it is removed or loosened.
- `docs/specs/storage.md`: the lookup-table list gains `link_token_hashes`. The "Sessions, links and step-ups" section names the step-up columns, the credential `CHECK`, the RLS policy, the four methods and the conformance cases below.
- `docs/specs/auth.md`: changed only if the build finds a statement in "Storage" that the code contradicts.

## Acceptance criteria

- `TestLinkTokensConformanceSQLite` and `TestLinkTokensConformancePostgres` run one shared `runLinkTokensConformance`. Postgres runs as the application role. The suite proves:
  - `AddLinkToken` returns a 32-character ID, the user ID, and the expiry as UTC RFC3339 text.
  - The first `UseLinkToken` before expiry returns that link token.
  - A second `UseLinkToken` of the same ID is `ErrTokenUsed`, and so is a use after expiry of a token already used.
  - An unused token is `ErrTokenExpired` at `now` equal to its expiry and after it, and a later use of it is still `ErrTokenExpired`.
  - An unknown ID is `ErrNotFound`.
  - A second `AddLinkToken` with the same hash is `ErrDuplicate`.
  - Two link tokens of one user are independent: using one leaves the other usable.
- `TestLinkTokenStoredHashedOnly` has a `sqlite` and a `postgres` subtest, in the style of `TestSessionStoredHashedOnly`. After `AddLinkToken` with `store.HashToken` of a fixed `mg_` bearer:
  - some stored cell equals the hex SHA-256;
  - no cell in any table contains the plaintext or an `mg_` value.
- `TestStepUpsConformanceSQLite` and `TestStepUpsConformancePostgres` run one shared `runStepUpsConformance`. Postgres runs as the application role. The suite proves:
  - `CreateStepUp` with a token credential and a project and environment target returns a 32-character ID, the org ID, every input field unchanged, `created_at` and `expires_at` as UTC RFC3339 text, and empty `SignedInAt`, `ApprovedAt`, `DeclinedAt` and `UsedAt`.
  - `StepUp` in that org returns the same row.
  - A step-up with a session credential and an empty target reads back with empty `TokenID`, `ProjectID` and `EnvironmentID`.
  - Input fields the caller sets for `ID`, `OrgID`, times or markers are ignored.
  - `CreateStepUp` is refused, and writes no row, for: both credentials set, neither set, an empty `UserID`, an empty `Operation` and an empty `InputDigest`.
  - `StepUp` of an unknown ID is `ErrNotFound`.
  - `StepUp` by a second org of the first org's ID is `ErrNotFound`, and the first org still reads its row unchanged.
- `TestPostgresRLSOnStepUps` follows `TestPostgresRLSOnRollbacks` and runs as the application role:
  - `SELECT org_id FROM step_ups` with no `WHERE` returns nothing when `app.org_id` is unset, empty or names a nonexistent org;
  - under org A, the same query returns only A's rows;
  - an `INSERT` of a row for org B under `app.org_id` = A is refused with SQLSTATE `42501`, and the same insert for A succeeds;
  - `rowsecurity` is on.
- `TestStepUpConstraintsEnforced` uses raw SQL on a migrated SQLite database, in the style of `TestRollbackConstraintsEnforced`:
  - an insert with both `token_id` and `session_id` set, or both empty, fails with `CHECK constraint failed`;
  - an insert with exactly one set succeeds;
  - the optional text columns default to empty text, and the marker columns are NULL.
- `TestLookupTablesMatchSchema` and `TestSchemasMatch` pass with `link_token_hashes` and `step_ups` on both backends. `link_token_hashes` has no `org_id` and no RLS. `step_ups` has `org_id` and RLS on Postgres.
- `TestMigrateIdempotent`, the enrolment-token conformance cases for `ErrTokenUsed` and `ErrTokenExpired`, and every other existing store, registry, server, agent and API test pass unchanged.
- No package outside `internal/store` changes.
- `make ci` is green and `scripts/verify check W4-1d` passes.

## Out of scope

- Confirming a step-up and acting on it: the 10-minute lifetime, the 11-pending limit and its 429, `confirm_hash` and `signed_in_at` at the callback, approve and decline, the checks that use the row, and marking it used in the same transaction as its audit event. These are W4-1c.
- The `/link/{token}` landing's lookup by hash, writing the `user_identities` row in the same transaction as the token's use, `identities.link` and `--print-owner-link`. These are W4-1.
- Sign-in, sessions in `Registry.Authenticate`, and the audit hash over `session_id` and `step_up_id`. These are W4-1b.
- Session tables: W4-1a, merged.

## Security notes

- Threat model §2 (Tokens): a link token is stored only as the SHA-256 hex of its bearer. No store method takes or returns the plaintext, and `LinkToken` has no hash field. `TestLinkTokenStoredHashedOnly` checks every table on both backends.
- §2, one-time tokens: the token is marked used in a single conditional `UPDATE`, so two concurrent uses cannot both succeed. A replay is `ErrTokenUsed` and an expired token is `ErrTokenExpired`. No method extends `expires_at`.
- ADR-0002 decision 12 and §9.5: `link_token_hashes` is on `LookupTables` and holds only its lookup key, the IDs it maps to, an expiry and a used marker. It never holds a name, scope or secret.
- §9.5: `step_ups` is row-level, not a lookup table. Every read and write runs in the org-bound transaction with `org_id` in the `WHERE`, so another org's step-up is `ErrNotFound`. `TestPostgresRLSOnStepUps` checks the policy without the filter.
- §9 (step-up binding): each row binds exactly one user, one credential (the database `CHECK` and a check before SQL), one operation, one target and one input digest. `StepUp` has no confirmation-hash field. This ticket never writes `confirm_hash`.
- §9.5: the application role still owns no table and lacks `BYPASSRLS`. Its grants on the new tables come from `pg.Migrate`, never from a migration file.

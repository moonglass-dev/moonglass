# Release workflow with provenance

.github/workflows/release.yml, on a release tag, builds the static amd64 and arm64 artifacts, writes the SBOM and SHA256SUMS, copies the units with the glob deploy/systemd/moonglass-* so the revert units of W7-6e join each tar without an edit here, attests each binary and the SBOM, and uploads the unsigned tars to a draft release (steps 1 to 5 of "The workflow" in `docs/specs/update.md` §9); internal/releasetest checks the workflow file statically; signing stays offline on the owner's token, and the publish job is W7-6g (ADR-0007).

After this ticket, pushing a tag `vX.Y.Z` produces a draft GitHub release holding `moonglass-<version>-linux-amd64.tar` and `moonglass-<version>-linux-arm64.tar`, each an unsigned artifact set of `docs/specs/update.md` §2, with build-provenance attestations for each binary and SBOM. Nothing in CI signs, holds a signing key or publishes to the release origin. Because the workflow only runs on a tag, `internal/releasetest` is what `make ci` checks it with.

## Scope

- `.github/workflows/release.yml` (new). Steps 1 to 5 of `docs/specs/update.md` §9, "The workflow", for `GOARCH` `amd64` and `arm64`:
  1. `CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags "-s -w -X main.version=<tag>" -o <dir>/moonglass ./cmd/moonglass`. `main.version` is the variable the Makefile already sets (`cmd/moonglass/main.go`). The tag reaches the shell through an `env:` value set from `github.ref_name`, never as a `${{ }}` expression inside a `run:` script.
  2. `moonglass.sbom.json`, SPDX JSON, with `anchore/sbom-action@66cbf4bc1f1c0d2edc94016e65bc221b6bb0ad6c # v0.24.3`, in each arch's set.
  3. The units copied with the glob `deploy/systemd/moonglass-*` into each arch's set, then `SHA256SUMS` in the `sha256sum` format with one line per other artifact of that set (§2).
  4. `actions/attest-build-provenance@4d101475d8b20a2381f78447822ac1eab6504dd8 # v4.2.2` with each arch's `moonglass` and `moonglass.sbom.json` as subjects.
  5. `moonglass-<version>-linux-<arch>.tar`, holding the set at its top level, uploaded unsigned to a draft GitHub release for the tag.
  - Checkout and Go setup use the same pinned actions as `.github/workflows/ci.yml`, with `persist-credentials: false` and `go-version-file: go.mod`.
  - Permissions are exactly `id-token: write`, `attestations: write` and `contents: write` (§9 step 4).
- `internal/releasetest/` (new, test files only, like `internal/installtest`): acceptance tests that read `.github/workflows/release.yml` from the repository root and check it as text with the standard library. No YAML module is imported: `go.yaml.in/yaml` is only indirect and no ADR names it.
- `docs/specs/update.md` §9, "The workflow": step 1 names `main.version` in place of `<version var>`, and step 3 names the glob `deploy/systemd/moonglass-*`. Nothing else in the spec changes.

## Acceptance criteria

- `TestReleaseWorkflowTriggersOnVersionTagsOnly`: the `push` trigger has `tags` with exactly the one pattern `v[0-9]+.[0-9]+.[0-9]+` and no `branches`; there is no `pull_request`, `pull_request_target`, `schedule` or `workflow_run` trigger.
- `TestReleaseWorkflowBuildsStaticBinariesPerArch`: for each of `amd64` and `arm64` the workflow runs `go build` of `./cmd/moonglass` with `CGO_ENABLED=0`, `GOOS=linux`, that `GOARCH`, `-trimpath`, and `-ldflags` holding `-s -w` and `-X main.version=` followed by the tag from the environment; the output is a file named `moonglass`.
- `TestReleaseWorkflowWritesSPDXSBOM`: `anchore/sbom-action` runs with format `spdx-json` and writes `moonglass.sbom.json` into each arch's set.
- `TestReleaseWorkflowPackagesArtifactSet`: the units are copied with the glob `deploy/systemd/moonglass-*` and no unit file is named one by one; `SHA256SUMS` is written by `sha256sum` over every other file of the set; each arch produces `moonglass-<version>-linux-<arch>.tar`.
- `TestReleaseWorkflowAttestsBinariesAndSBOM`: `actions/attest-build-provenance` runs with `subject-path` covering `moonglass` and `moonglass.sbom.json` of both arches, and runs before the upload.
- `TestReleaseWorkflowUploadsToDraftRelease`: both tars are uploaded to a release for the tag that is created as a draft; no step publishes the release, marks it latest, or uploads anything other than the two tars.
- `TestReleaseWorkflowPinsEveryAction`: every `uses:` is `owner/repo@<40 lowercase hex> # vN…`; the only actions are `actions/checkout` and `actions/setup-go` at the pins in `ci.yml`, and `anchore/sbom-action` and `actions/attest-build-provenance` at the pins in §9.
- `TestReleaseWorkflowGrantsOnlyReleasePermissions`: every `permissions:` block in the file grants only `id-token: write`, `attestations: write` and `contents: write`, together they grant all three, and none is `write-all` or `read-all`.
- `TestReleaseWorkflowHoldsNoSecretOrSigningStep`: the file has no `secrets.` expression and no `environment:` key, no `${{ }}` expression inside a `run:` script, and no `ssh-keygen`, `.sig`, `aws` or `workflow_dispatch`.
- Each test's failure message names the expected and the actual line or value.
- `make ci` is green, and the tests need no network, Docker, `gh` or GitHub runner.
- `testdata/tests.txt` gains the nine lines.

## Out of scope

- The `workflow_dispatch` publish job, verifying with `scripts/install`, and the upload to the release origin with its secrets: W7-6g.
- The revert units and `scripts/install --state-dir`: W7-6e. This ticket's glob picks the units up once they exist, with no edit here.
- The in-process verifier (W7-6a), the update messages (W7-6d), channels and rollout (W7-6f).
- Signing, the channel pointer, and making the repository public before the first tag: the owner's steps (`docs/specs/update.md` §9).

## Security notes

- `docs/threat-model.md` §2, release signing keys: CI never holds a signing key and never signs; the workflow contains no `ssh-keygen` and produces no `.sig` (ADR-0007 d1).
- `docs/threat-model.md` §3, the ninth boundary: the tars are unsigned and stay in a draft release; nothing installs them until the owner signs each artifact and W7-6g verifies them with the pinned keys.
- Checklist 3: the workflow references no secret and names no GitHub environment; only the publish job of W7-6g names the environment `release` (§9, "The secret pair"). The draft release is written with the job's own token under `contents: write`.
- Checklist 6: every action is pinned by commit SHA, and the tag reaches shell scripts only through `env:`, so a ref name cannot inject a command.
- Checklist 8: one build path; the version variable is the Makefile's `main.version`, not a second one.

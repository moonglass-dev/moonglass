# Store the agent age recipient

The control plane checks the length of `EnrollRequest.agent_age_recipient` at enrolment and then throws it away (R-1 finding 2). `docs/specs/secrets.md` ("Granting") and ADR-0003 make that key the recipient of every agent-wrapped environment key, so W4-8 and W3-3 have nothing to wrap to. After this ticket each enrolled server's age recipient is stored as text on `servers` in the age Bech32 form (`age1…`, `docs/specs/secrets.md`: "The agent's recipient and identity are the age Bech32 encoding of the public and private halves of `agent-agree.key`"). Enrolment stores it, and the store reads it back on every server read. This changes the storage schema, which is a contract, so the owner must approve it before the build starts.

## Scope

- `internal/store/migrations/sqlite/0007_agent_age_recipient.sql` and `internal/store/migrations/pg/0007_agent_age_recipient.sql`: `ALTER TABLE servers ADD COLUMN agent_age_recipient TEXT NOT NULL DEFAULT '';`, identical on both backends. `servers` already has RLS and the `org_isolation` policy on Postgres. Grants stay in `pg.Migrate`, unchanged.
- `internal/store/store.go`: `Server` gains `AgeRecipient string`. The interface method becomes `AddServer(ctx context.Context, orgID, publicKey, ageRecipient string) (Server, error)`. The old two-argument form is deleted, not kept next to the new one.
- `internal/store/sqlstore.go`: `AddServer` refuses an empty `ageRecipient` with an error before any SQL runs, then inserts it into `servers` in the same transaction as the `agent_keys` row. `ServerByPublicKey` and `Servers` read it back. The store copies the text it is given and does not parse it, just as it copies `PublicKey`. `agent_keys` and `LookupTables` do not change. A lookup row never holds anything beyond its key and IDs (`docs/specs/storage.md`, "Lookup tables"), so the recipient goes on `servers`, the row-level table.
- `internal/store` tests: a new `runServerAgeRecipientConformance` file, a migration test, and the existing `AddServer` calls in the conformance, projects, releases, rollbacks and RLS tests updated to the new signature with a non-empty recipient. Their assertions stay the same.
- `internal/server/enroll.go`: right after the 32-byte length check, and before `UseEnrolmentToken`, `handleEnroll` turns the raw key into a recipient with `keys.AgreeRecipient`. If that fails, the answer is HTTP 400 with a plain-text error and the token is not used. `enrol` passes `recipient.String()` to `AddServer`. `internal/server/agent_test.go` updates its `AddServer` call.
- `docs/specs/storage.md`: under "Row-level tables", `servers` lists `agent_age_recipient` with its meaning and default, and a short "Agent age recipients (FR1-2)" section gives the rules below. `docs/specs/enrolment.md` ("HTTP endpoint"): on `ACCEPTED` the server also stores the age recipient, and the "Out of scope" line "Changing W1-2 store schema" names FR1-2 as the amendment.

## Acceptance criteria

- `TestServerAgeRecipientConformanceSQLite` and `TestServerAgeRecipientConformancePostgres` (one `runServerAgeRecipientConformance`; the Postgres one skips without `MOONGLASS_TEST_POSTGRES` and fails under `CI`): `AddServer` returns the recipient it was given. `ServerByPublicKey` and `Servers` read the same recipient back. Two servers in one org each keep their own recipient. An empty recipient returns an error, and after that `Servers` for the org is unchanged and `ServerByPublicKey` for that public key is `ErrNotFound`. A second org's `Servers` does not include the first org's server or its recipient.
- `TestServerAgeRecipientMigration`: on SQLite, a database migrated with files `0001` to `0006` only holds a server. Applying the full `migrations.SQLite()` set leaves that row with `agent_age_recipient` equal to `''`, and `ServerByPublicKey` returns it with an empty `AgeRecipient`. On the migrated schema, a raw `INSERT` that sets `agent_age_recipient` to `NULL` is refused.
- `TestEnrollStoresAgeRecipient`: after an `ACCEPTED` enrol, the org's only server has `AgeRecipient` equal to `keys.AgreeRecipient(req.AgentAgeRecipient).String()`, which starts with `age1`, through both `Servers` and `ServerByPublicKey` with the hex signing key.
- `TestEnrollDuplicateKeyStoresNoRecipient`: a second enrol that reuses a signing key already on record, sent with a fresh token and a different age recipient, answers `TOKEN_INVALID`. The org still has one server, and its `AgeRecipient` is the first recipient.
- `TestSchemasMatch` and `TestLookupTablesMatchSchema` pass unchanged: the column has the same name and nullability on both backends, and `LookupTables` is not edited.
- Every existing `internal/store` and `internal/server` test still passes. The only change to each is the extra `AddServer` argument.
- No package outside `internal/store` writes SQL, and no package other than `internal/keys` imports `filippo.io/age`.
- `docs/specs/storage.md` and `docs/specs/enrolment.md` describe the column, its `age1…` form, its empty default for servers enrolled before this migration, and enrolment storing it.

## Out of scope

- Using the recipient: granting the first server and delivering secrets (W4-8), and rotation and re-wrapping (W3-3).
- Re-enrolment flows and agent key rotation (ADR-0003 decision 7).
- Server deploy keys on `servers` (W3-8).
- Enrolment and REST over TLS (FR1-1), and agent key files in `internal/keys` (FR1-3).
- One token generator for enrolment (FR1-6).
- Any change to `proto/` or `EnrollRequest`: the field already exists.

## Security notes

- `docs/threat-model.md` §2 (Assets): the age recipient is a public key and may be stored, shown and returned. The agent's private keys still never leave the server, and no private material is stored. The column holds only the `age1…` public recipient.
- §3 B3 (control plane ↔ agent) and §4 (full control of the control plane): a control plane that is taken over can swap a stored recipient. That is why `docs/specs/secrets.md` has the owner's CLI show the server's fingerprint before it wraps to the recipient. This ticket adds no path that wraps to a stored recipient without that check, and makes no claim beyond it.
- §7 (Trusted core) and §9 (Reviewer checklist): `internal/store` migrations and RLS. `servers` keeps `org_isolation` on Postgres. The recipient is read only through org-bound store methods, or after the org is resolved from `agent_keys`. `agent_keys` stays a lookup table holding only its key and IDs.
- §8: no secret or token is logged. Enrolment still writes no logs, and the new 400 path has a fixed message that contains neither the token nor key bytes.

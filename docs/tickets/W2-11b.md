# Releases on the control plane

The control plane records every release of a service in the `releases` table of `docs/specs/storage.md` "Projects, environments, services and releases (W2-11)". After this ticket the store queues a release, keeps at most one `running` and one `queued` release per service (a newer request marks the queued one `superseded`, `docs/specs/registry.md` "One deploy per service"), starts the queued release when none is running, records the step in flight with its request id (`docs/specs/connection.md`), the image the agent actually ran, and the final status with its detail, lists a service's history newest first, and returns the queued and running releases of one server in one org, so W2-5 can re-send a step after a restart. The same conformance suite runs on SQLite and Postgres, and Postgres enforces row-level security on the new table (ADR-0002).

## Scope

- `internal/store/migrations/pg/0004_releases.sql` and `internal/store/migrations/sqlite/0004_releases.sql`: the table `releases`, with the same columns and nullability on both backends, every column `NOT NULL`:
  - `id` (primary key), `org_id` (references `orgs`), `service_id` (references `services`), `image_ref`, `git_repository`, `git_commit`, `port` (integer), `health_path`, `domains` (a JSON array, `[]` for none), `pre_deploy` (a JSON argv, empty text for none), `pre_deploy_reversible` (boolean, read and written as a Go `bool` on both backends), `status`, `step`, `request_id`, `image_id`, `repo_digest`, `detail`, `created_at`, `finished_at` (empty text until the release reaches a final status). Text columns other than `id`, `org_id`, `service_id`, `domains`, `status` and `created_at` default to empty text when unknown.
  - `CHECK` on `status` (`queued`, `running`, `succeeded`, `failed`, `rejected`, `superseded`) and on `step` (empty, `build`, `deploy`, `pre_deploy`, `switch`), as `memberships.role` is checked.
  - Two partial unique indexes, identical on both backends: `(org_id, service_id) WHERE status = 'queued'` and `(org_id, service_id) WHERE status = 'running'`. They are the database's guarantee of at most one queued and one running release per service.
  - Postgres only: `ENABLE ROW LEVEL SECURITY` and the `org_isolation` policy of `docs/specs/storage.md`. No grants in the file (`pg.Migrate` grants). No new lookup table: `LookupTables` is unchanged.
- `internal/store/store.go`: the type `Release` (`OrgID`, `ID`, `ServiceID`, `ImageRef`, `GitRepository`, `GitCommit`, `Port`, `HealthPath`, `Domains []string`, `PreDeploy []string`, `PreDeployReversible`, `Status`, `Step`, `RequestID`, `ImageID`, `RepoDigest`, `Detail`, `CreatedAt`, `FinishedAt`); the typed constants `ReleaseStatus` (the six statuses) and `ReleaseStep` (the four steps); the sentinel `ErrReleaseState` for a release not in a status that allows the call; and these `Store` methods, each run through `inOrg` with an `org_id` predicate in every query:
  - `EnqueueRelease(ctx, orgID string, r Release, now time.Time) (Release, error)`: reads the service inside the org-bound transaction (`ErrNotFound` when it is not the org's), mints the id with `NewID`, and in one transaction marks the service's `queued` release `superseded` with `finished_at` = `now` and inserts the new one as `queued` with `created_at` = `now`. The caller's `Status`, `Step`, `RequestID`, `ImageID`, `RepoDigest`, `Detail` and times are ignored. A lost race for the queued slot shows up as a duplicate on the partial index and is retried with a fresh transaction, bounded, as `AppendAudit` retries.
  - `StartRelease(ctx, orgID, releaseID string) error`: `queued` to `running`. `ErrReleaseState` when the release is not `queued` or another release of its service is `running`.
  - `SetReleaseStep(ctx, orgID, releaseID string, step ReleaseStep, requestID string) error`: records the step in flight and its envelope request id on a `running` release.
  - `SetReleaseImage(ctx, orgID, releaseID, imageID, repoDigest string) error`: records what the agent's `CommandResult` reported on a `running` release.
  - `FinishRelease(ctx, orgID, releaseID string, status ReleaseStatus, detail string, now time.Time) error`: a `queued` or `running` release ends as `succeeded`, `failed` or `rejected` with `detail` and `finished_at` = `now`.
  - `Release(ctx, orgID, releaseID string) (Release, error)`: one release, `ErrNotFound` when it is not the org's.
  - `Releases(ctx, orgID, serviceID string) ([]Release, error)`: the service's releases newest first, at most 50, ordered by `created_at` descending, then `id` descending.
  - `InFlightReleases(ctx, orgID, serverID string) ([]Release, error)`: the `queued` and `running` releases of every service of the org on that server, oldest first (`created_at`, then `id`). A server that is not the org's returns none.
  - The three updates return `ErrNotFound` for a release that is not the org's and `ErrReleaseState` for a release in another status, and change nothing in either case. An unknown step, or a finish status outside the three final ones, returns an error naming the allowed values and changes nothing. All ids come from `NewID`, timestamps from `formatTime`.
- `internal/store/`: the four named tests. `TestSchemasMatch`, `TestLookupTablesMatchSchema` and `TestMigrateIdempotent` already cover the new table and must pass unchanged.
- `docs/specs/storage.md`: under "Projects, environments, services and releases (W2-11)", record the queue rules above (the partial unique indexes, supersede in the enqueue transaction with retry, which statuses each update accepts, `finished_at` empty until final, the history order and its cap of 50, the in-flight read per org and server) and name the conformance cases this ticket adds. The services release columns and `rollbacks` stay as written for W2-11e.

## Acceptance criteria

- `TestReleasesConformanceSQLite` and `TestReleasesConformancePostgres` run one shared suite (`runReleasesConformance`) against each backend, migrated first. It proves:
  - a release enqueued on a service of the org comes back from `Release` and `Releases` with a 32-hex id, status `queued`, `created_at` from `now`, empty `finished_at`, and every input field unchanged, including `domains`, the `pre_deploy` argv (and none for an empty argv) and `pre_deploy_reversible`;
  - `EnqueueRelease` for an unknown service or a service of another org returns `ErrNotFound` and writes nothing;
  - `StartRelease` moves the queued release to `running`; a second release then queues beside it; a third supersedes the second (status `superseded`, `finished_at` from its `now`) and leaves exactly one `queued` release; `StartRelease` on the queued release while one is running, and on a superseded release, returns `ErrReleaseState`;
  - `SetReleaseStep` and `SetReleaseImage` record `step`, `request_id`, `image_id` and `repo_digest` on a running release, and return `ErrReleaseState` on a queued or finished one; an unknown step returns an error and changes nothing;
  - `FinishRelease` ends a running release as `succeeded`, `failed` or `rejected` with its `detail` and `finished_at`; after it the queued release starts; finishing a finished release returns `ErrReleaseState`; a finish status of `queued`, `running` or `superseded` returns an error and changes nothing;
  - `Releases` lists newest first and returns the 50 newest of 51;
  - `InFlightReleases` returns the queued and running releases of services on that server in the org, oldest first, and leaves out finished releases and releases of services on another server;
  - eight concurrent `EnqueueRelease` calls on one service all succeed and leave exactly one `queued` release, the other seven `superseded`;
  - a second org gets `ErrNotFound` from `Release`, `StartRelease`, `SetReleaseStep`, `SetReleaseImage` and `FinishRelease` on the first org's release, which stays unchanged, and gets no rows from `Releases` and `InFlightReleases` with the first org's service and server ids.
- `TestPostgresRLSOnReleases`: under the application role, with `app.org_id` unset, empty or naming a nonexistent org, `SELECT org_id FROM releases` without a `WHERE` returns no rows; with `app.org_id` A it returns only A's rows; an `INSERT` of an org B row under `app.org_id` A fails; `pg_tables.rowsecurity` is true for `releases`.
- `TestReleaseConstraintsEnforced` (table-driven, SQLite, raw SQL on a migrated database): an unknown `status` and an unknown `step` are refused by the `CHECK`; a second `queued` and a second `running` row for one service are refused by the partial unique indexes; any number of finished rows for one service, and a queued and a running row for different services, are accepted.
- Every store error wraps its cause with context; not-found and wrong-status cases are testable with `errors.Is` against `ErrNotFound` and `ErrReleaseState`.
- The cross-org service check is an explicit `SELECT … WHERE id = $1 AND org_id = $2` inside the org-bound transaction, not the foreign key alone: Postgres referential checks do not apply RLS. `InFlightReleases` joins `services` with `org_id` and `server_id` predicates and never reads across orgs.
- Each status change is a single `UPDATE … WHERE id = $1 AND org_id = $2 AND status IN (…)`, so a concurrent change cannot move a release out of a final status.
- `make ci` is green; `testdata/tests.txt` lists the four tests.

## Out of scope

- `services.current_release_id` and `previous_release_id`, the write that copies a `CommandResult`'s app state, `ServiceByName`, and the `rollbacks` table with its reads: W2-11e. The `docs/specs/storage.md` wording on which ticket adds the services release columns is W2-11e's.
- The `deploy`, `rollback` and `releases.list` operations, the step driver, re-sending after a restart, the offline check, and validating `deploy` inputs against `docs/specs/protocol.md`: W2-5. The store stores the fields it is given.
- Marking which releases are current and previous in the history: W2-11e and W2-5.
- Leaving deleted services out of release reads: W5-5c.
- Retention or deletion of release rows: not specified.

## Security notes

- `docs/threat-model.md` §3, boundary B2: `releases` carries `org_id`, has RLS with the `org_isolation` policy on Postgres, and is not a lookup table. Only `internal/store` writes its SQL. The application role gets its grants through `pg.Migrate` and never migrates.
- §9 reviewer checklist: no table is added without `org_id`; `LookupTables` gains nothing.
- A release on another org's service would let one org deploy into another org's app on another org's server. `EnqueueRelease` checks the service inside the caller's org-bound transaction and refuses it with `ErrNotFound`, so another org's service id is not revealed.
- The in-flight read decides which commands the control plane re-sends to an agent. It is per org and server, so a reconnecting agent is never sent another org's step.
- `detail` is agent-reported text and is stored as data, never interpreted. `pre_deploy` is an argv stored as a JSON array, never a shell string (`AGENTS.md`, security rules).
- No secret, key or token is stored in `releases`.

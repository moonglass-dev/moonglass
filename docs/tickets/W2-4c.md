# Agent proxy flags

`moonglass agent connect` gains `--proxy-socket PATH` and `--tls-issuer acme|acme-staging|internal`, opens the Docker Engine and agent state, and runs the W2-4a proxy push (`deploy.Proxy.Run`) for as long as it runs, so the proxy gets the complete config at start and again after every proxy restart (`docs/specs/connection.md`, "Commands"; `docs/specs/release.md`, "Proxy config"). The `agent connect` synopsis in `registry.LocalCommands` names the two flags. This was split out of W2-4a (owner decision, 2026-11-19) because the synopsis is in trusted core.

## Scope

- `cmd/moonglass` (`runAgentConnect`), and `internal/agent` if the wiring belongs beside `agent.Connect`:
  - `--proxy-socket PATH`, default `/run/moonglass-proxy/admin.sock`. An empty value prints the usage and exits 2.
  - `--tls-issuer`, default `acme`; `acme-staging` and `internal` are the other values. Any other value prints the usage and exits 2.
  - Both are checked before anything is opened or dialled.
  - Before connecting, the command opens the Engine with `deploy.Connect` and the state database at `<data-dir>/agent.db` with `internal/agent/state`, as `docs/specs/agent-state.md` says. Either failing stops the command with that error on stderr and exit code 1.
  - It builds one `deploy.NewProxy(engine, db, deploy.ProxyConfig{Socket, Issuer})` and runs `Proxy.Run` in its own goroutine for the life of the command, beside `agent.Connect`. A push error is written to stderr through the same `OnError` path as connection errors; it never stops the command. When the context ends, the command waits for `Run` to return, then closes the database and the Engine.
- `internal/registry/routes.go`: the `agent connect` synopsis becomes `agent connect [--data-dir DIR] [--proxy-socket PATH] [--tls-issuer ISSUER] --url URL`. Nothing else in the file changes.
- `docs/specs/connection.md`: already says this; change it only if the built behaviour needs a wording fix.

## Acceptance criteria

- `TestAgentConnectProxyFlagDefaults`: with neither flag, the proxy is configured with `/run/moonglass-proxy/admin.sock` and `acme`; with both flags, with the values given. The test reads the values through the function that parses the flags, not by dialling the default path.
- `TestAgentConnectRejectsBadProxyFlags`: an empty `--proxy-socket`, and a `--tls-issuer` of `letsencrypt`, each exit 2 with the usage on stderr, and nothing is opened: no `agent.db` appears in the data directory.
- `TestAgentConnectRunsProxyPush`: with an enrolled temp data directory, a control-plane URL that refuses connections, and a Unix-socket `httptest` server standing in for the admin socket (answering `GET /config/admin`, `/config/storage` and `/config/` and recording `POST /load`), the command posts one complete config to `/load` within 5 seconds and keeps running; after the context is cancelled it exits 0 (or the exit code it uses today for a cancelled connect) and the database file is closed. It needs a Docker Engine: it skips without one, except under `CI`, where it fails.
- `TestAgentConnectSynopsisNamesProxyFlags`: the `agent connect` entry of `registry.LocalCommands` has exactly the synopsis above.
- Every existing test in `cmd/moonglass` and `internal/registry` passes unchanged.
- `make ci` is green and `scripts/verify check W2-4c` passes.

## Out of scope

- W2-4a: `deploy.NewProxy`, `Proxy.Run` and `Proxy.Push` themselves.
- W2-10: `--policy`, loading `agent.toml`, and dispatching commands to the executor.
- W2-4b, W2-4d: the switch and rollback pushes.

## Security notes

- `docs/threat-model.md` §3 B4: the admin socket is reached only through the path given, which systemd makes group-readable for `moonglass-proxy-admin` only (W2-12). The command never opens a TCP admin port and never creates the socket.
- §3 B5 and ADR-0014: the Engine is opened only through `internal/deploy`; `cmd/moonglass` does not import the Docker client.
- No flag value is a shell string; nothing is run through a shell. Private keys and tokens stay out of every error printed.

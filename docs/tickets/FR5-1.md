# One owner per domain at switch and rollback

Today only `Deploy` checks domains, and it checks them only against other apps' current releases. `SwitchRelease` and `Rollback` route a release through `Proxy.PushRouted` with no check. So two apps can each push a `terminal` route for the same host, and whichever comes first in `app_id` order serves it (R-5 finding 1). This happens when two apps' candidates for one domain both switch. It also happens when an app rolls back onto a domain another app now routes. After this ticket, `Proxy.PushRouted` refuses such a routed release while it holds its push lock. The answer is `REJECTED` with `domain <name> is already routed to app <app_id>`. Nothing is pushed or committed, and the candidate or previous release stays as it was. `Deploy` uses the same check, so there is one rule for who owns a domain (`docs/specs/release.md`).

## Scope

- `internal/deploy`:
  - Move the conflict rule out of `Executor.checkDomains` (`deploy.go`) into one plain function over a list of current releases, an app id and its domains.
  - The function answers with `rejected(fmt.Errorf("domain %s is already routed to app %s", …))` for the first conflicting domain, in the routed release's stored domain order. Another app's current release holds its domains. The app's own releases never conflict.
  - `Deploy` keeps calling it at step 3 of "Order" with what it reads from `CurrentReleases`. Its behaviour does not change.
  - `Proxy.push` calls the same function when `routed` is set. It runs on the current releases it has just read, before `withRouted` and before any route is built or `POST /load` is sent. It runs inside the `PushRouted` lock, so a concurrent switch or rollback of another app cannot slip between the check and the push.
  - When `push` refuses, `PushRouted` returns that error without running `commit`. The last pushed document is left untouched, because nothing was posted.
  - `SwitchRelease` and `Rollback` answer `REJECTED` with that detail and the stored state when the `PushRouted` error is a refusal. Any other `PushRouted` error is still `FAILED`.
  - A refused switch does not abort the candidate and writes no row. The candidate stays `ready`, its row stays `candidate` and its container keeps running.
  - A refused rollback writes nothing. The previous release's container stays in place as the app's previous release, as after a failed gate.
  - There is one check and one refusal type. Nothing else in the package compares domains.
- `docs/specs/release.md`:
  - "SwitchRelease" step 3 and "Rollback" step 4 say the refusal happens inside the push lock, with its detail and the unchanged state.
  - "Proxy config" says a domain another app's current release routes is refused at `Deploy`, at `SwitchRelease` and at `Rollback`, by one check, and that `PushRouted` refuses before posting.

## Acceptance criteria

- `TestSwitchReleaseRejectsDomainRoutedByAnotherApp` (real Engine, `fakeAdmin`). Apps A and B have no current release. Each deploys a candidate with domain `x.example`, and `Deploy` allows both. A's switch is `SUCCEEDED`. B's switch is `REJECTED` with detail exactly `domain x.example is already routed to app <A>`. It also checks that:
  - the fake admin socket gets no `POST /load` during B's switch;
  - B's stored state equals what it was before (candidate `ready`, no current);
  - B's row is still `candidate`, and B's container still exists and is running;
  - the last pushed document routes `x.example` only to A's release.
- `TestRollbackRejectsDomainRoutedByAnotherApp` (real Engine). A deploys and switches r1 with `x.example`, then r2 with `y.example`, so r1 is previous and still running. B then deploys and switches a release with `x.example`. A's `Rollback` is `REJECTED` with detail exactly `domain x.example is already routed to app <B>`. It also checks that:
  - the fake admin socket gets no `POST /load` during the rollback;
  - A's stored state is unchanged (current r2, previous r1), r1's row is still `previous`, and r2's row is still `current`;
  - r1's container still exists.
- `TestRollbackStoppedPreviousRejectedForDomain` (real Engine). Same as the rollback test, but A's previous container is stopped first, so the rollback starts it and runs the gate. The answer is `REJECTED` with the same detail. A's state and rows are unchanged, no `POST /load` is sent, and the container is still there as A's previous release.
- `TestSwitchReleaseKeepsOwnDomains` (real Engine). A's current release routes `x.example`, and B's current release routes `z.example`. A deploys r2 with `x.example` and `z2.example` and switches. The answer is `SUCCEEDED`, and the pushed document routes `x.example` and `z2.example` to r2 and `z.example` to B. An app's own current release never conflicts with its candidate.
- `TestProxyPushRoutedRejectsDomainBeforePosting` (real Engine, `fakeAdmin`). App A's stored current release routes `x.example`. `Proxy.PushRouted` is called with a routed release of app B that has `x.example`. It returns an error whose text is `domain x.example is already routed to app <A>` and for which `errors.As` finds the package's refusal type. `commit` is never called, no `POST /load` reaches the fake, and the last pushed document is the one from before the call.
- The existing `TestDeployRejectsDomainRoutedByAnotherApp`, switch, rollback and proxy tests stay green, unchanged.
- `internal/deploy` has exactly one function that decides a domain conflict. `checkDomains` either calls it or is replaced by it.
- `docs/specs/release.md` "SwitchRelease", "Rollback" and "Proxy config" state the refusal as above.
- `make ci` is green and `scripts/verify check FR5-1` passes.

## Security notes

- `docs/threat-model.md` §3 B3: the agent treats the control plane as possibly hostile. A switch or rollback the control plane sends must not let one app's release take over a domain another app on the server is serving. The agent decides this from its own state inside the push lock, not from anything in the message.
- §3 B4: the pushed document is still the complete config. A refused switch or rollback posts nothing, so the running proxy config and the last pushed document stay as they were.
- §9.3: the refusal's detail names only the domain and the app id, never container output or a probe body.

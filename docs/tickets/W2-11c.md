# Operation targets and refusals

`registry.Target` carries names, and `registry.Invoke` resolves them with `store.ResolveTarget` after the role check; an unknown target within scope is not found and audited `not found`; one outside scope is denied like any other target out of scope; the handler gets `Call.ProjectID` and `Call.EnvironmentID`; `registry.Refuse` has the kinds `ErrInvalidInput`, `ErrNotFound` and `ErrConflict` and their audit reasons (`docs/specs/registry.md`, "Inputs and errors": "Targets, authorisation and audit" and "Handler refusals"). After this ticket a handler never sees a project or environment name it has to resolve itself, a scoped token cannot learn which names exist outside its scope, and a handler can say why it refused a request in a form `internal/api` (W2-11f) maps to 400, 404 or 409.

## Scope

- `internal/registry/registry.go`:
  - `Target` has the name fields `Project` and `Environment`, replacing `ProjectID` and `EnvironmentID`. Both empty is an org-level call.
  - `Call` gains `ProjectID` and `EnvironmentID`, the resolved ids. It still has no methods.
  - `Invoke` runs, in order: the role check; then, when `Target.Project` is not empty, exactly one `store.ResolveTarget(ctx, p.OrgID, t.Project, t.Environment)` call; then the scope-row match against the resolved ids; then the destructive gate. A role denial reads nothing from the store. An org-level call (empty target) makes no store call and matches only a `*` row, as today.
  - When `ResolveTarget` returns `store.ErrNotFound`, the unresolved column stands for an id no scope row names, so only `*` in that column matches it. No matching row: denied exactly as for a known target out of scope (`ErrDenied`, outcome `denied`, the same reason text). A matching row: `Invoke` returns the refusal `registry.Refuse(registry.ErrNotFound, ...)` with the message `project "<name>" not found` or `environment "<name>" not found in project "<project>"`, the handler does not run, and the event has outcome `error` and reason `not found`.
  - Any other `ResolveTarget` error is wrapped with context and returned; it is not a refusal and the handler does not run.
  - On success the handler gets `Call{OrgID, UserID, ProjectID, EnvironmentID}`.
- A refusal (new file in `internal/registry`, or `registry.go`):
  - Sentinels `ErrInvalidInput`, `ErrNotFound` and `ErrConflict`, distinct from the store's sentinels.
  - `Refuse(kind error, message string) error`: the result matches `kind` with `errors.Is`, and its `Error()` is exactly `message`. It wraps no other error.
  - `Invoke` audits a handler error that matches one of the kinds with outcome `error` and reason `invalid input`, `not found` or `conflict`; every other handler error keeps outcome `error` and reason `the handler returned an error`. The error itself is returned unchanged.
- `internal/registry/registry_test.go`, `audit_test.go`, `token_test.go`: the existing tests that build a `Target` use names; `TestRoleAndScopeAreEnforced` creates the project and environment it targets in the store and keeps every case it has today.
- `docs/specs/registry.md`: changed only if the built behaviour needs a wording fix; the behaviour is already specified there.
- `internal/api/api.go` passes `registry.Target{}` for `servers.list` and needs no change.

## Acceptance criteria

- `TestInvokeResolvesTargetAfterRoleCheck`: a call with a named target refused by the role check makes no `ResolveTarget` call (a store wrapper counts calls) and is denied; an allowed role makes exactly one call.
- `TestInvokeUnknownTargetInScopeIsNotFound`: for an unknown project, and for an unknown environment in a known project, under a `*` scope row, `Invoke` returns an error that matches `registry.ErrNotFound` with the exact message from the spec, the handler does not run, and the one audit event has outcome `error` and reason `not found`.
- `TestInvokeUnknownTargetOutOfScopeIsDenied`: an unknown project under a scope row naming another project's id returns `ErrDenied` with the same error text, outcome and audit reason as a known project out of scope, and the handler does not run.
- `TestInvokePassesResolvedIDsToHandler`: for a project-level and an environment-level target, the handler's `Call` holds the ids `CreateProject` and `CreateEnvironment` returned (empty `EnvironmentID` for project-level), and a scope row naming those ids allows the call.
- `TestRefusalKindsAndAuditReasons`: table over the three kinds: the handler's `Refuse(kind, msg)` comes back from `Invoke` matching its kind and no other, with `Error()` equal to `msg`, and the audit reason is `invalid input`, `not found` or `conflict`.
- `TestUnmappedStoreErrorIsNotARefusal`: a handler returning a wrapped `store.ErrNotFound`, `store.ErrDuplicate` or `store.ErrInvalidName` yields an error matching none of the three refusal kinds, and the audit reason `the handler returned an error`.
- Every existing `internal/registry` test still passes with name targets; none is deleted or weakened.
- No audit reason holds a name, a token or a wrapped error's text; the reasons are the fixed strings above and the existing denial reasons.
- `make ci` is green and `scripts/verify check W2-11c` passes.

## Security notes

- `docs/threat-model.md` §3 B1 and §8: authorisation and audit stay in `Invoke` only; resolution is part of the scope check, never middleware and never a caller-set flag.
- §9.4 (token scope holes): a scoped token must get the same denial for a name that does not exist as for a name outside its scope, so it cannot probe for names; only a token whose scope row covers the column learns `not found`.
- §9.5: every store call runs in the caller's org (`ResolveTarget` with `p.OrgID`); a name in another org does not resolve.
- §9.3 and the audit rule in `docs/specs/registry.md`: an audit reason and a refusal message never carry a token, a secret or another error's text.

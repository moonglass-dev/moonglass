# Owner token hook

`moonglass server --print-owner-token NAME` mints one owner token named `NAME`, expiring 90 days after issue, for the owner of the server's org, prints it once to stdout and keeps serving (owner decision D27, `docs/specs/enrolment.md` "Commands", `docs/specs/registry.md` "Tokens"). When the org has no owner yet, it first mints a user through the external identity `local:owner` and gives it the owner role. It is the walking-skeleton hook that gives the owner a token for the CLI and for CI until sign-in (W4-1), built the same way as `--print-enroll-token`.

## Scope

- `internal/server`: `Server.IssueOwnerToken(ctx, orgID, name)` rejects an empty name before any write, finds the org's owner in `Memberships`, and when there is none calls `UserForIdentity(ctx, "local:owner")` and `AddMembership(..., store.RoleOwner)`; then it calls the existing `Server.MintOwnerToken` with `s.now().Add(90 * 24 * time.Hour)` and returns the text. `Run` takes the owner-token name (empty means not requested); when set, it resolves the org with the existing `firstOrg`, issues the token and prints it as one line to stdout before listening, exactly as it does for the enrolment token. With both flags the enrolment token line is printed first. The package still writes no logs, and no error it returns contains the token.
- `cmd/moonglass`: `runServer` adds the string flag `--print-owner-token NAME` and passes it to `server.Run`. A flag given with an empty value (`--print-owner-token ""` or `--print-owner-token=`) prints usage to stderr and exits 2, like a missing `--url`; detect "given" with `fs.Visit`.
- `internal/registry/routes.go`: the `server` entry of `LocalCommands` gets the usage `server [--data-dir DIR] [--listen ADDR] [--agent-listen ADDR] [--print-enroll-token] [--print-owner-token NAME]`. No operation, route or generated file changes.
- `docs/specs/enrolment.md`: under "Commands", state the empty-name rule (usage, exit 2) and that the printed line goes to stdout, so the owner runs the hook from a shell and not under the systemd unit, whose stdout is the journal. `docs/specs/registry.md` changes only if the wording of "Tokens" or "Routes and commands that are not operations" no longer matches the code.

## Acceptance criteria

- `TestIssueOwnerTokenCreatesLocalOwner`: on an org with no members and a fixed clock, `IssueOwnerToken(ctx, org, "ci")` returns an `mg_` token of 55 characters; the org then has exactly one membership, role `owner`, whose user is `UserForIdentity("local:owner")`; `Registry.Authenticate` on the token returns that org and user, role `owner`, scopes exactly `[* * *]`; the stored token has name `ci` and `ExpiresAt` equal to the clock plus 90 days in RFC 3339; the plaintext appears nowhere in the store's token rows (only its `store.HashToken` and last four).
- `TestIssueOwnerTokenUsesExistingOwner`: on an org whose owner was added through another identity, two calls return two different tokens, both authenticate as that existing owner, and the org still has exactly that one membership (no `local:owner` user is added).
- `TestIssueOwnerTokenRejectsEmptyNameWithoutWrites`: `IssueOwnerToken(ctx, org, "")` returns an error that says the name is empty, and the org has no memberships afterwards.
- `TestRunPrintsOwnerTokenOnce`: `server.Run` on a temp data dir with listeners on `127.0.0.1:0` and owner-token name `ci` writes exactly one line to stdout, the token; after the context is cancelled and `Run` returns nil, reopening `DIR/server.db` and authenticating the token gives role `owner` in the org named by `DIR/org`, with an expiry within 90 days of the window around the call. A second `Run` on the same data dir with the same name prints a different token and leaves the org with one owner membership.
- `TestServerOwnerTokenFlagNeedsName`: table-driven over `--print-owner-token ""` and `--print-owner-token=`: `run` returns 2, stderr equals the usage text and stdout is empty; no `server.db` is created in the data dir.
- `TestUsageListsOwnerTokenFlag`: the usage text contains `[--print-owner-token NAME]` on the `server` line.
- `TestUsageOnMissingOrUnknownCommand` and every existing test pass unchanged.
- No new dependency, operation, route, storage column or migration. The token text is never passed to a logger, an error string or an audit event; minting is not a registry `Invoke`, so it writes no audit event (`docs/specs/registry.md` "Audit").
- `make ci` is green and `scripts/verify check W3-10` passes.

## Out of scope

- Sign-in, sessions and step-up (W4-1). Scoped tokens, agent identities and the authz matrix (W5-1). Token list and revoke operations (later tickets).
- The build-in-CI template that consumes this token (W3-4).
- Hosted bootstrap and the first-admin registration window (W7-1, ADR-0005).

## Security notes

- `docs/threat-model.md` §2 (Tokens): the token is 256 bits from `crypto/rand`, written `mg_…`, stored only as its SHA-256 with name, expiry, owner and last four, shown once; it carries an expiry (90 days) and an owner, and its one scope row is `* * *`, as every token is until W5-1.
- §8 and the §9 checklist item on leaks: the token must not reach a log line, an error string, an audit event or stderr. The only place it appears is the one stdout line. Printing to stdout of a service under systemd lands in the journal; the spec says to run the hook from a shell.
- §9 item 4 (token scope holes): the token cannot act above its holder's role. The `local:owner` user is created only when the org has no owner, so the hook never adds a second owner to an org that has one.
- Anyone who can run `moonglass server` against the data dir can mint an owner token; that is the same trust as reading the data dir and the control-plane key, and no remote path reaches this hook.

# Self-update spec

Write `docs/specs/update.md`, the behaviour spec for agent self-update, release channels and staged rollout. W7-6c, W7-6d, W7-6e and W7-6f are built from it. It turns ADR-0007 (decisions 1 to 6), stack §3.14 and threat-model checklist items 6 and 7 into behaviour that those tickets can write named acceptance tests against. The owner approves the spec before it merges, because it fixes the shape of later contract changes (protocol messages, registry operations, storage tables, systemd units).

## Scope

One new file, `docs/specs/update.md`, in the style of the existing specs: short sections, tables for fields and states, exact names, and a reference to the ADR or spec behind each rule. It covers each of these, in its own section:

1. **Discovery.** How the agent learns that a release exists for its channel (`update.channel` in `agent.toml`, `docs/specs/container-policy.md`). This covers what the control plane offers, what the agent fetches itself, and when it checks. It also covers the self-hosted path of ADR-0007 decision 5: the same signed artifacts for the channel in `agent.toml`, with no percentage rollout. The control plane never replaces itself, and the operator updates `moonglass server` and the CLI with the signed install.
2. **Artifact URL layout.** The URL of each artifact and its `.sig` per channel and per architecture (amd64, arm64), using the same artifact set and names as `docs/specs/install.md` ("Artifacts and verification"). It also says how `https://moonglass.dev/releases/latest` (the install default) relates to the channels.
3. **Verification before install.** The order of steps: download into a private staging directory, verify each `.sig` with the W7-6a verifier, check the binary's SHA-256 against the signed `SHA256SUMS`, and only then switch. It also covers what the agent does and reports when any step fails.
4. **Binary layout under `ProtectSystem=strict`.** Where the current and previous binaries live, and which user can write each path. The agent runs as `moonglass` with an empty capability set, `NoNewPrivileges=true` and a read-only `/usr`. The proxy runs as `moonglass-proxy` and must not be able to write the agent's binary or keys. The section also covers how both units find the binary they run, and exactly which changes W7-6e makes to `deploy/systemd/` and `scripts/install`, each with the reason it is needed.
5. **The systemd revert.** The names of any revert unit or timer. How the five-minute window is measured and from when. What counts as "not restarted", in terms systemd or the agent can observe (for example `NRestarts`, the main PID, or start time). Who starts the previous binary, and how. What happens when the previous binary is also bad.
6. **The self-check.** The four conditions of ADR-0007 decision 4, each stated as something a test can observe. How the result reaches the control plane: which message, when it is sent, what it carries. W7-6d defines the message, so the spec states its fields and rules and leaves the `.proto` to W7-6d. No field may carry a host path or a shell string.
7. **The drained proxy upgrade** (ADR-0007 decision 6). How a release marks that it changes the proxy. The order in which the agent drains, upgrades and restarts the proxy. How this keeps the agent and the running proxy on the same Caddy config shape and counter module. How the self-check's proxy condition applies in each case.
8. **Rollout state on the control plane.** The canary and stable channels. The 10%, 50% and 100% stages, 24 hours apart. The 72 hours on canary before stable. The halt criteria of ADR-0007 decision 3, stored as data (thresholds and windows in rows, not constants spread through the code). Which agents count as "updated in the current stage". The states a rollout moves through. The `resume` and `withdraw` operations, each with its scope, lowest role and `destructive` flag as `docs/specs/registry.md` requires, and its effect on agents already updated. The tables or columns W7-6f adds, named as `docs/specs/storage.md` names them.
9. **Release workflow and signing hand-off.** The attestation action W7-6c uses, pinned by commit SHA. What the workflow builds (static amd64 and arm64 binaries and the SBOM) and from which trigger. How the unsigned artifacts reach the owner for offline signing with `ssh-keygen -Y sign -n moonglass-release` on the FIDO2 token. How the signed set is published to the URL layout in section 2.
10. **Owner decisions.** A closing list of every choice the spec makes that no ADR or existing spec already fixes, one line each, so the owner can approve or change each one before merge.

## Acceptance criteria

- `docs/specs/update.md` exists and has a section for each of items 1 to 10 in Scope.
- Every rule that comes from ADR-0007 or stack §3.14 agrees with it exactly: the namespace `moonglass-release`, hash `sha512`, flags 0x01 and 0x04, either of the two pinned keys, five minutes, 10/50/100%, 24 hours, 72 hours, at least 2 agents and at least 1%, 10 minutes to reconnect, the first hour, and halted until resumed or withdrawn.
- Each named unit, timer, path, file mode, owner and message field is concrete enough that W7-6c to W7-6f can name acceptance tests against it. No "TBD", no open questions, and no choice between alternatives left to the implementer.
- The binary layout gives the proxy user no write access to any path the agent executes. It adds no capability to either unit, and it does not relax `ProtectSystem=strict` beyond named `ReadWritePaths` or state directories. Every unit change it asks W7-6e to make carries a one-line reason.
- No message the spec describes carries a host path, a command line or a shell string. The agent never sends plaintext secrets or key material in a self-check or rollout report.
- `resume` and `withdraw` each state their scope, lowest role and `destructive` flag.
- The spec claims no more than `docs/threat-model.md` §5 supports, and never says "audited".
- Every decision not fixed by an ADR or existing spec appears in the Owner decisions list.
- The owner approves the spec before it merges.
- No other file changes.

## Security notes

This is a docs-only ticket, but the spec governs trusted-core work, so the following must hold.

- **Threat-model §2, release signing keys:** nothing is installed or run unless its own `.sig` verifies against a pinned key, with both flags set. Signing stays offline on the owner's token, and CI never holds a signing key.
- **Threat-model §3, the ninth boundary and B3:** the agent treats update offers from the control plane as untrusted. A hostile control plane can at most delay an update or offer a signed release. It can never get an unsigned binary installed or name a path or a command.
- **Threat-model §3, B4:** the proxy upgrade keeps the admin socket reachable only through `moonglass-proxy-admin`.
- **Threat-model §8:** the control plane never replaces itself.
- **Threat-model §9, checklist 1:** new message fields carry no host path or shell string.
- **Threat-model §9, checklist 5:** `resume` and `withdraw` carry authz declarations.
- **Threat-model §9, checklist 6:** the self-check compares the running executable's SHA-256 with the verified file.
- **Threat-model §9, checklist 7:** no unit gains a capability or a writable path without a stated reason.
- **`agent.toml`:** it stays local policy. The control plane cannot change `update.channel`.

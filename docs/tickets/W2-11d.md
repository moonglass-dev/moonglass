# Project, environment and service operations

The registry ships the six operations of `docs/specs/registry.md` ("Operations added in weeks 2 and 3", ticket W2-11): `projects.create`, `projects.list`, `environments.create`, `environments.list`, `services.create` and `services.list`. Each is a `Spec` and a handler over the store methods W2-11a added, authorised and audited by `registry.Invoke` with the targets of W2-11c, served over REST by `internal/api` with the inputs and errors of W2-11f, and generated into the CLI by W2-11g. After this ticket an owner token can create a project, an environment in it and a service on one of the org's servers, and list each.

## Scope

- `internal/registry`
  - `operations.go`: the six `Spec` values exactly as the spec's table gives them (name, method, path, `MinRole`, `Destructive: No`), each with a one-line `Summary`; their `In` and `Out` types; all six added to `Operations()` with their `In` types, after `servers.list`.
  - Inputs, every field a required string with a `json` and `doc` tag:
    - `projects.create`: `name`. `projects.list`: none.
    - `environments.create`: `project`, `name`. `environments.list`: `project`.
    - `services.create`: `project`, `environment`, `name`, `server` (a server id of the caller's org). `services.list`: `project`, `environment`.
  - Outputs: a create returns the created row; a list returns `projects`, `environments` or `services`, an array in the store's name order, empty and never null when there are none. A project and an environment are `id`, `name`, `created_at`; a service is `id`, `name`, `server` (its server id), `created_at`.
  - `registry.go`: one `Registry` field per operation, registered in `New` like `ServersList`. Handlers use only `Call` and the store: `projects.create` calls `CreateProject(c.OrgID, name)`; `environments.create` calls `CreateEnvironment(c.OrgID, c.ProjectID, name)`; `environments.list` calls `Environments(c.OrgID, c.ProjectID)`; `services.create` calls `CreateService(c.OrgID, c.EnvironmentID, name, server)`; `services.list` calls `Services(c.OrgID, c.EnvironmentID)`. No handler resolves a project or environment name.
  - Refusals, built with `registry.Refuse` from the inputs and fixed text, never from the store's error text:
    - `store.ErrInvalidName` → `ErrInvalidInput`, `<kind> name "<name>" must be 1 to 63 bytes of [a-z0-9-], starting and ending with a letter or digit`, with `<kind>` `project`, `environment` or `service`.
    - `store.ErrDuplicate` → `ErrConflict`: `project "<name>" already exists`; `environment "<name>" already exists in project "<project>"`; `service "<name>" already exists in environment "<environment>" of project "<project>"`.
    - `store.ErrNotFound` from `CreateService` → `ErrNotFound`, `server "<server>" not found`; from `CreateEnvironment` → `ErrNotFound`, `project "<project>" not found`.
    - Any other store error is wrapped with context and returned unmapped (500).
- `internal/api`: `build` mounts the six operations; `openapi.json` regenerated with `make generate`; `routes_test.go` changed only as the acceptance criteria below say.
- `internal/cli`: `generated.go` regenerated with `make generate`. No hand-written command.
- `docs/specs/registry.md`: under the W2-11 rows, the inputs of each of the six operations, their outputs and the refusal messages above.

## Acceptance criteria

- `TestProjectEnvironmentServiceSpecs`: `registry.Operations()` holds each of the six with the `Spec` of the spec's table and its `In` type, and each `In` has exactly the input fields above, all required strings.
- `TestProjectsCreateAndList`: an owner principal creates projects `web` and `api` through `registry.Invoke`; the create returns the new id, name and `created_at`; `projects.list` returns both in name order; a second org's `projects.list` returns an empty, non-nil list.
- `TestEnvironmentsCreateAndList`: `environments.create` with a target project creates the environment in the resolved `Call.ProjectID`, and `environments.list` returns that project's environments in name order with id, name and `created_at`.
- `TestServicesCreateAndList`: `services.create` on a server of the org creates the service in the resolved environment and returns its id, name, `server` and `created_at`; `services.list` returns the environment's services in name order with the same fields.
- `TestCreateRefusalsFromStoreErrors`, table-driven over the three creates: an invalid name is `ErrInvalidInput`, a duplicate name `ErrConflict`, and an unknown or another org's server on `services.create` `ErrNotFound`; each error's text is exactly the message above, contains no `store:` text, and is not wrapped; the audit event has outcome `error` and reason `invalid input`, `conflict` or `not found`; nothing is written.
- `TestListsStayInTheirTarget`: `environments.list` names only the target project's environments, `services.list` only the target environment's services, even when another project or environment of the org has rows of the same names; an unknown project or environment on a list or create is the 404 refusal of W2-11c and runs no handler.
- `TestProjectEnvironmentServiceRoutes`: through `api.New` over a SQLite store and an owner token, `POST /v1/projects`, `POST /v1/environments` and `POST /v1/services` with JSON bodies answer 200 with the created rows; `GET /v1/projects`, `GET /v1/environments?project=…` and `GET /v1/services?project=…&environment=…` answer 200 with them; a repeated project name is 409 with `project "web" already exists`; an unknown project on `GET /v1/environments` is 404; a missing `server` on `POST /v1/services` is 400 with location `body.server`.
- `TestGeneratedProjectEnvironmentServiceCommands`: the generated commands are `projects create --name`, `projects list`, `environments create --project --name`, `environments list --project`, `services create --project --env --name --server` and `services list --project --env`, all flags required; `services list` sends a GET with `project` and `environment` query parameters and `services create` a POST with one JSON body.
- `TestGeneratedOpenAPIIsCurrent` and `TestGeneratedCLIIsCurrent` pass: both generated files are rewritten by `make generate`, never by hand.
- `TestEveryMountedRouteIsOperationOrAllowlisted` (`internal/api/routes_test.go`, which the owner allowed this ticket to edit, 2026-11-20) seeds, through the store before its route loop, a project, an environment in it and a server of the org (`AddServer`), and calls each operation with valid inputs over those rows: a GET with its inputs as query parameters, a POST with a JSON body whose names are fresh, so the owner token answers 200 for every operation; the no-token and bad-token cases send the same valid inputs and still answer 401. Its other checks are unchanged.
- The other existing tests pass unchanged.
- No handler calls `ResolveTarget`, reads the target's names, or writes an audit event.
- `make ci` is green.

## Security notes

- Threat model, control-plane API and authorisation (ADR-0006): every one of the six runs only through `registry.Invoke`, so role, scope and audit apply; no handler bypasses them, and authorisation stays declared on each `Spec`.
- Tenant isolation: every store call passes `c.OrgID` and the ids `Invoke` resolved in that org; a server id of another org is `not found`, the same answer as an unknown one, so it reveals nothing about other orgs. A scoped token sees only what its scope rows cover; org-level `projects.*` match only a `*` row.
- Error disclosure: refusal messages hold only the caller's own inputs and fixed text, never the store's error text; any other failure is the fixed 500 detail with the error logged.
- None of the six is destructive or touches secrets, keys or protocol messages.

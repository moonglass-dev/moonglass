# Generated CLI inputs

After this ticket every generated subcommand takes one flag per field of its operation's `In`, checks required flags before it sends anything, sends the inputs as query parameters for `GET` and one JSON body for `POST` and `PUT`, and prints a refused call's `detail` and `errors` entries to stderr. `make generate` reads each operation's `In` type from `registry.Operations()`, fails on an input kind that has no flag, and writes no subcommand for an operation whose subcommand is a local command. This implements "Generated CLI" and "Input fields" in `docs/specs/registry.md` (owner decision of 2026-11-18, ADR-0006 decisions 2, 7 and 9).

## Scope

- `internal/registry` (`operations.go` and its tests; no other production file): `Operations()` returns `[]registry.Declaration`, where `Declaration` embeds `Spec` and has `In reflect.Type`, the type of the operation's input. Embedding keeps every existing caller that reads `.Name`, `.Method` or `.Path` (`internal/server/server.go`, `internal/api` tests) compiling unchanged. `servers.list` declares `reflect.TypeFor[ServersListIn]()`. No operation is added, removed or changed.
- `internal/cli/gen.go`: `Generate(ops []registry.Declaration, local []registry.LocalCommand) ([]byte, error)` replaces `Generate()`; `TestGeneratedCLIIsCurrent` calls it with `registry.Operations()` and `registry.LocalCommands`, so `make generate` (unchanged Makefile) uses it. For each operation whose subcommand (name with dots turned into spaces) is not a local command's name, it reads the exported fields of `In`: each needs a `json` tag naming the input (snake_case) and is required unless the tag has `omitempty`; its kind is string, boolean, integer (`int64`) or list of strings. Any other kind, or a field with no `json` name, is an error naming the operation and the field and saying to use one of the four kinds or make the subcommand a local command. The emitted `command` literal carries its flags in field order: flag name (`--` plus the tag with `_` turned into `-`; `environment` becomes `env`), the `json` name, the kind, required, and the `doc` text.
- `internal/cli/cli.go`: `command` gains its flags; `runGenerated` parses them with a `flag.FlagSet` (standard library, `ContinueOnError`, no aliases, no short flags):
  - an integer flag parses decimal `int64`, and anything else exits 2 with `--<flag> must be an integer` on stderr;
  - a list flag appends one element per repetition, in order; a boolean is `--name` or `--name=false`;
  - an unknown flag or any positional argument exits 2 with the subcommand's usage on stderr, listing its flags, required ones first, each with its `doc`;
  - a missing required flag exits 2 with `moonglass: <subcommand>: --<flag> is required` for the first missing one in field order, before any request;
  - only the flags given are sent: for `GET` as query parameters named by the `json` tag (a list repeated, a boolean `true` or `false`, an integer in decimal); for `POST` and `PUT` as one JSON object with those keys, sent with `Content-Type: application/json`, and no query string;
  - a 2xx prints the body to stdout and exits 0; any other status reads the `application/problem+json` body and prints `moonglass: <subcommand>: <detail>`, then one line `  <location>: <message>` per `errors` entry, to stderr, and exits 1. A body with no `detail` prints the status code and text in its place.
  - The bearer token, `MOONGLASS_URL` handling and the missing-environment exit 2 stay as they are.
- `internal/cli/generated.go`: regenerated by `make generate`, never edited by hand.
- `docs/specs/registry.md`: name `registry.Declaration` (its `Spec` and `In`) in the sentence on `registry.Operations()`, and the W2-11g test list gains `TestOperationsListInTypes`. No other behaviour in the spec changes.

## Acceptance criteria

- `TestOperationsListInTypes`: every entry of `registry.Operations()` has a non-nil struct `In`; `servers.list` has `reflect.TypeFor[registry.ServersListIn]()` and its existing `Spec` values.
- `TestGeneratedFlagNames`: for a test operation with fields `project`, `environment`, `health_path` and `pre_deploy_reversible`, the subcommand accepts `--project`, `--env`, `--health-path` and `--pre-deploy-reversible`; `--environment`, `--health_path` and a one-letter short flag each exit 2 with the usage, and nothing is sent.
- `TestGeneratedFlagsSentAsQueryOrBody`: a `GET` test operation sends the given flags as query parameters named by their `json` tags with an empty body; a `POST` and a `PUT` test operation send one JSON object of exactly the given flags with `Content-Type: application/json` and no query string; an optional flag not given is absent from both.
- `TestGeneratedRepeatedBooleanAndIntegerFlags`: `--domain a.example --domain b.example` sends the list in order (repeated query parameter for `GET`, a JSON array for `POST`); `--flag` sends true and `--flag=false` sends false; `--port 8080` sends the integer 8080; `--port 8x` exits 2 with `--port must be an integer` and sends nothing; `--name=-v` sends `-v`.
- `TestGeneratedMissingRequiredFlagExits2`: with two required flags missing, the exit is 2, stderr has `moonglass: <subcommand>: --<first missing flag> is required`, and the test server receives no request.
- `TestGeneratedRefusesPositionalAndUnknownFlags`: a positional argument and an unknown flag each exit 2 with the subcommand's usage on stderr, listing every flag with required ones before optional ones and each flag's `doc`; nothing is sent.
- `TestGeneratedPrintsErrorDetail`: a 400 problem body with `detail` and two `errors` entries prints `moonglass: <subcommand>: <detail>` and one `  <location>: <message>` line per entry to stderr, nothing to stdout, and exits 1; a 404 with only `detail` prints that one line and exits 1; a 200 prints the body to stdout and exits 0.
- `TestGenerateRefusesInputWithoutFlag`: `Generate` on a test operation with a list-of-objects field (and, separately, an `int` field) returns an error naming the operation and the field, and no output.
- `TestGenerateSkipsLocalCommands`: `Generate` on the same operation, with its subcommand name on the local list passed in, returns no error and output with no command of that name.
- The test operations are registered with `registry.Register` (on `registry.New(nil, time.Now)`) and paired with their `In` types; the generator tests generate from that test list, not from `registry.Operations()`.
- `TestGeneratedCLIIsCurrent`, `TestGeneratedRunnerSendsBearerToken`, `TestEverySubcommandIsGeneratedOrLocal` and every `internal/api` and `internal/server` test pass unchanged; `generated.go` is the output of `make generate`.
- No file outside `allowed_paths` changes; no new dependency; `make ci` is green and `testdata/tests.txt` lists the new tests.

## Security notes

- §9.3 (secret plaintext): the runner never prints the token, and on an error prints only the server's `detail` and each entry's `location` and `message`, never a flag value, so a ciphertext or other input given in the wrong place is not echoed by the CLI. Nothing is logged.
- §9.5 and ADR-0006 decisions 2 and 7: every subcommand is still generated from the registry or on `registry.LocalCommands`; the generated file is regenerated, never edited; an operation with an input that has no flag cannot generate unless its subcommand is a local command.
- §8 (enforcement on the server): the required-flag check is a client convenience only; `internal/api` and `registry.Invoke` keep every check, and no flag or input changes authorisation.

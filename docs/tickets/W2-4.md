# Stops and retention

The last piece of the switch-and-drain executor. W2-4b's switch and W2-4d's rollback write `stop_after` on the `previous` and `retired` rows, but nothing acts on it yet. After this ticket the agent carries out every stop when its `stop_after` comes: a `previous` container is stopped and kept, so a rollback within its 10-minute window is only a route push (D11), and a `retired` container is stopped and removed after its 30-second drain. The start-up reconcile carries out the stops already due. Retention keeps five releases per app with their images, and runs at start and every hour (`docs/specs/release.md`, "SwitchRelease" step 5, "Keep five", "Failure"; `docs/specs/agent-state.md`, "Retention"). Draining (Caddy's graceful reload with `grace_period` 30s) and the unrouted previous release are already in place from W2-4a and W2-4b. This ticket adds the stops that end them.

## Scope

- `internal/agent/state`
  - `DB.DueStops(ctx, now)` returns every `previous` or `retired` row whose `stop_after` is at or before `now`, with its app, release, status and `container_id`, ordered by `stop_after`, then `app_id`, then `release_id`.
  - `DB.RecordStopped(ctx, appID, releaseID, now)` records a carried-out stop in one transaction. For a `previous` row it clears `stop_after` and keeps `container_id`. For a `retired` row it clears `stop_after` and empties `container_id`. It writes nothing and returns an error when the row is no longer `previous` or `retired`, or its `stop_after` is unset or later than `now`.
  - `DB.Retain(ctx, now)` applies "Retention" in one transaction, and returns the image IDs of the deleted `retired` rows that no remaining `candidate`, `current`, `previous` or `retired` row of any app names. Per app it keeps the current row, the previous row and the three newest `retired` rows, newest by `created_at` and then by insertion order. It deletes older `retired` rows only once their stop has run (`stop_after` unset and `container_id` empty). It deletes `failed` and `aborted` rows whose `created_at` is more than 7 days before `now`. It never touches `apps` rows.
- `internal/deploy`
  - The stop of one due row: check that the recorded container carries `dev.moonglass.managed=true` with that app and release, then stop it with SIGTERM and a 30-second wait before SIGKILL. For `retired`, also force-remove it and the release's pre-deploy step container `mg-<app_id>-<release_id>-pre`, which is removed only when it carries the same managed labels. Then `RecordStopped`. A container the Engine no longer has counts as stopped and removed.
  - One lock per app in the `Executor`, held by `SwitchRelease`, `Rollback` and each stop of that app. That way a stop never runs between a rollback reading the previous container as running and its commit. A stop re-reads its row under the lock and skips a row that is no longer due.
  - `Executor.Reconcile` also carries out the stops due at the time it runs, after removing unreferenced containers.
  - Retention: call `Retain`, then remove each returned image by ID without force. If the Engine refuses because the image is in use, or does not have it, the image is left for the disk guard, and that is not an error.
  - `Executor.Run(ctx, onError)`: at start, `Reconcile` and then retention; then the due stops every second and retention at every retention interval (one hour; an `Executor` field like `healthLimit`, so tests can shorten it). A step that fails is reported through `onError` (optional) and retried at its next turn. It never stops `Run`, which returns only when `ctx` ends.
- `docs/specs/release.md` and `docs/specs/agent-state.md`: say what "newest" means for retention, the per-app lock, that a carried-out stop clears `stop_after` (and, for `retired`, `container_id`), that a retired release's pre-deploy step container goes with it, and that `moonglass agent connect` runs `Executor.Run` for its whole life from W2-10.

## Acceptance criteria

- `TestDueStopsListsPreviousAndRetiredPastStopAfter`: after switches and a rollback recorded at past times, `DueStops` lists exactly the `previous` and `retired` rows whose `stop_after` is at or before `now`, in the stated order. It does not list the current row (including one a rollback restored, whose `stop_after` is cleared), the candidate, failed or aborted rows, or a row not yet due.
- `TestRecordStoppedClearsStopAfter`: a due `previous` row keeps its `container_id` and loses `stop_after`, and a due `retired` row loses both. For a row that is `current`, `candidate`, not yet due, already recorded as stopped, or unknown, it returns an error and every row and the `apps` row are byte-for-byte unchanged.
- `TestRetainKeepsFiveAndPrunesOldRows`: for an app with a current, a previous and five retired releases, `Retain` deletes the two oldest retired rows and keeps the other five. A retired row outside the five whose stop is still due is kept. `failed` and `aborted` rows created more than 7 days before `now` are deleted, and newer ones are kept. Another app's rows are judged separately. The returned image IDs are those of the deleted retired rows, minus any image ID that a kept row of any app still names.
- `TestStopPreviousStopsAndKeepsContainer` (Docker): after a real switch recorded 11 minutes ago, the stop leaves the old current's container stopped but present, its row `previous` with the same `container_id` and no `stop_after`. A following `Rollback` starts it, gates it and succeeds, as in W2-4d.
- `TestStopRetiredRemovesContainerAndPreDeployStep` (Docker): a due `retired` release's container and its `-pre` step container are removed, and the row is `retired` with an empty `container_id` and no `stop_after`. The current and previous containers and the project network are untouched.
- `TestStopNeverStopsRestoredRelease` (Docker): if a rollback commits after a `previous` row became due but before its stop ran, the restored release keeps running and serving, and the release rolled back from is stopped and removed when its own `stop_after` comes. A stop and a `Rollback` of the same app never run at the same time.
- `TestStopRefusesUnmanagedContainer` (Docker): if the recorded `container_id` names a container without the managed labels of that app and release, that container is not stopped or removed, the row is unchanged, and the error names the container, the app and the release.
- `TestReconcileCarriesOutDueStops` (Docker): `Reconcile` removes managed containers that no release references, as before, and carries out every stop due at the time it runs. A stop not yet due stays pending.
- `TestRetainRemovesImagesOutsideFive` (Docker, imported images): after retention deletes retired rows, their images are removed. An image that a kept release names, or that a container still uses, stays in the store, and that is not an error. No volume and no network is removed.
- `TestExecutorRunStopsAndRetainsUntilCancelled` (Docker): `Run` reconciles and retains at start, carries out a stop within 2 seconds of its `stop_after`, runs retention again at its shortened interval, reports a failing step through `onError` and keeps running, and returns when `ctx` ends.
- Stop and remove calls keep the 60-second Engine call limit, and the stop's own wait is 30 seconds. No other Engine call is added beyond container stop, inspect, remove and image remove.
- `make ci` is green. Both specs say what is above. No code for W2-10's command records.

## Out of scope

- Running `Executor.Run` from `moonglass agent connect`, which W2-10 does when it builds the agent's executor from the loaded `agent.toml` (`agent connect` has no executor before then).
- Deleting `commands` rows after 7 days: W2-10, which creates that table.
- Newest-wins deploy supersession, which is the control plane's queue: W2-5 (`docs/specs/registry.md`).
- Disk-guard pruning of images and build cache: W3-6.
- The deploy-correctness suite and the Docker matrix: W2-7.
- Volumes and the volume rule: W6-1c. Retention and stops never remove a volume.

## Security notes

- `docs/threat-model.md` §3 B5: every container stop or remove targets only a container recorded in agent state that carries `dev.moonglass.managed=true` with the same app and release, checked right before the call. Images are removed only by an image ID taken from a deleted row, never by a reference from a message, and never with force. No container is created, so `internal/policy` is not bypassed. No network or volume is removed.
- §3 B3: nothing here is triggered by a protocol message, and no message field reaches a stop, a retention step or an image removal.
- §3 B4: unchanged. Stops never push. The previous release stays unrouted, and Caddy's 30-second `grace_period` drains the old route.
- §9.3: errors and `onError` reports name containers, apps, releases and images only. They never include container output or environment.
- Docs claim no more than this: draining is Caddy's graceful reload, and a stopped previous release needs a start and a health gate before a rollback can serve it (W2-4d).

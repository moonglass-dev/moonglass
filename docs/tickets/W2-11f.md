# REST inputs and errors

query inputs for GET and one JSON body for POST and PUT, unknown inputs refused, every schema failure answered 400 (never 422) with no `value` echoed, refusals as 400, 404 and 409, anything else 500 (`docs/specs/registry.md`)

After this ticket `internal/api` serves any `*registry.Operation[In, Out]` by one generic path, built from the operation's `Spec` and the `json` and `doc` tags of its `In`, as `docs/specs/registry.md` "Inputs and errors" ("REST inputs", "Errors", "Targets, authorisation and audit") specifies. W2-11c made `registry.Invoke` resolve named targets and gave handlers `registry.Refuse`; this ticket turns those, and Huma's validation failures, into the spec's status table. W2-11d then adds the real operations on top of it.

## Scope

- `internal/api`:
  - One generic registration for any `*registry.Operation[In, Out]`; `servers.list` goes through it and the current hand-written path is deleted. Tests register test operations with `registry.Register` and mount them through the same path (tests in package `api` may reach it unexported).
  - Inputs from the `In` struct's `json` tags (snake_case names, `omitempty` means optional, otherwise required) for the four kinds string, boolean, `int64` and list of strings. `In` types carry no Huma tags: `internal/api` derives the parameters and body from the `json` and `doc` tags.
  - `GET`: every input is a query parameter named as its `json` tag; a list is the parameter repeated (`explode`), a comma is part of a value; a boolean is `true` or `false`. `POST` and `PUT`: one `application/json` object body holding every input, and no query parameters.
  - Unknown query parameters refused (`RejectUnknownQueryParameters`) and unknown body fields refused (no additional properties), both 400.
  - An absent optional input takes its zero value.
  - `registry.Target` filled from the input's `project` and `environment` fields when the `In` has them; empty otherwise. `internal/api` never resolves a name.
  - Error mapping: every schema or decode failure is 400 with detail `invalid input for <operation>` and `errors` entries of `location` and `message` only (never `value`), Huma's 422 never sent; refusal kinds `registry.ErrInvalidInput` 400, `registry.ErrNotFound` 404, `registry.ErrConflict` 409, each with the refusal's message; 401 and 403 as today, with the 401 detail `the token is missing, unknown, expired or revoked: mint a new one` also for a missing or non-Bearer header; 413 for a body over Huma's 1 MiB limit; anything else 500 with the fixed message and the error logged, never sent.
  - The shape check runs before authentication, so a malformed request is 400 even without a valid token, and writes no audit event.
  - Regenerate `internal/api/openapi.json` (`make generate`).
- `docs/specs/registry.md`: changed only if the implementation must correct a statement in "Inputs and errors"; no behaviour beyond it is added.

## Acceptance criteria

- `TestQueryInputsDecoded`: a test `GET` operation whose `In` has string, boolean, `int64` and list-of-strings fields receives `?domain=a&domain=b,c` as `["a", "b,c"]` in order, `true`/`false` as booleans, a decimal integer as `int64`, and an absent optional input as its zero value.
- `TestBodyInputsDecoded`: a test `POST` and a test `PUT` operation receive every field of one JSON body, including a list in order and absent optional fields as zero values.
- `TestUnknownInputsRefused`: an unknown query parameter on a `GET` and an unknown body field on a `POST` are each 400, the handler does not run and no audit event is written.
- `TestSchemaFailuresAre400`: a missing required input (query and body), a wrong type (such as a string for an integer or boolean) and a body that is not JSON are each 400 with detail `invalid input for <operation>`, `errors` naming each `location` (such as `query.project`, `body.name`) with a `message`; no response is ever 422; no `errors` entry has a `value` key and the response body does not contain the sent value; a malformed request with no token is 400, not 401; no audit event is written.
- `TestRefusalStatuses`: a handler returning `registry.Refuse` of `ErrInvalidInput`, `ErrNotFound` and `ErrConflict` is answered 400, 404 and 409 respectively, with the refusal's message as `detail`.
- `TestUnmappedHandlerErrorIs500`: a handler returning a plain wrapped error, and one returning a store sentinel it did not map (such as `store.ErrDuplicate`), are 500 with `the control plane could not complete the call; see its logs and retry`, and the response does not contain the error's text.
- `TestTargetFilledFromInputs`: for a test operation with required `project` and `environment` inputs called by an owner token, an unknown project is 404 `project "<name>" not found`, an unknown environment in a known project is 404 `environment "<name>" not found in project "<project>"`, and a known pair reaches the handler with `Call.ProjectID` and `Call.EnvironmentID` set to the store's ids; an operation without those fields gets an empty `registry.Target`.
- `TestMissingTokenIs401WithSpecDetail`: a well-formed request with no `Authorization` header, a non-Bearer header and an unknown token are each 401 with detail `the token is missing, unknown, expired or revoked: mint a new one`.
- `TestBodyOverLimitIs413`: a `POST` body over 1 MiB is 413 and the handler does not run.
- Every response body is `application/problem+json` for errors; no error message carries a token, an input value or a wrapped error's text.
- `servers.list` is served through the generic path; `TestEveryMountedRouteIsOperationOrAllowlisted`, `TestServerErrorIsLoggedWithoutTheToken`, `TestHumaConfinedToAPI` and `TestGeneratedOpenAPIIsCurrent` still pass; `openapi.json` is regenerated, not hand-edited.
- No new operation is added to `registry.Operations()`; no file outside `allowed_paths` changes; `make ci` is green.

## Security notes

- `docs/threat-model.md` §3 B1: authorisation stays only in `registry.Invoke`. The 400 conversion, input decoding and target filling decide no access; no middleware or caller-set value changes authorisation. A schema failure answered before `Invoke` writes no audit event, as the spec says, and reveals only the public schema in `openapi.json`.
- §8 "Enforcement is on the server": `internal/api` passes names only; the registry resolves them, so a scoped token cannot learn which names exist outside its scope (unknown out-of-scope targets stay 403 from `Invoke`).
- §9 checklist 3 (secret plaintext): no `errors` entry echoes an input `value`, so a ciphertext or token sent in the wrong place never comes back; a 500 logs the error but sends only the fixed message; no log line or response carries the bearer token.
- §9 checklist 4 (token scope holes): the 404 for an unknown target is only what `Invoke` returns after a matching scope row; `internal/api` adds no lookup of its own.

# Projects, environments and services on the control plane

The control plane stores an org's projects, their environments and the services in each environment, as `docs/specs/storage.md` "Projects, environments, services and releases (W2-11)" specifies. After this ticket the store can create and list each of them, resolve a project and environment name to their ids in an org, and refuses a service on a server of another org, a duplicate name, and a name outside the protocol's name format. The same conformance suite runs on SQLite and Postgres, and Postgres enforces row-level security on the three new tables (ADR-0002).

## Scope

- `internal/store/migrations/pg/0003_projects.sql` and `internal/store/migrations/sqlite/0003_projects.sql`: the tables, with the same columns and nullability on both backends:
  - `projects` — `id` (primary key), `org_id` (references `orgs`), `name`, `created_at`; unique `(org_id, name)`.
  - `environments` — `id` (primary key), `org_id`, `project_id` (references `projects`), `name`, `created_at`; unique `(org_id, project_id, name)`.
  - `services` — `id` (primary key), `org_id`, `project_id` (references `projects`), `environment_id` (references `environments`), `name`, `server_id` (references `servers`), `created_at`; unique `(org_id, environment_id, name)`.
  - All columns `TEXT NOT NULL`. Postgres only: `ENABLE ROW LEVEL SECURITY` and the `org_isolation` policy of `docs/specs/storage.md` on all three. No new lookup table: `LookupTables` is unchanged.
- `internal/store/store.go`: the types `Project` (`OrgID`, `ID`, `Name`, `CreatedAt`), `Environment` (adds `ProjectID`) and `Service` (adds `ProjectID`, `EnvironmentID`, `ServerID`); the sentinel `ErrInvalidName`; and these `Store` methods, each run through `inOrg` with an `org_id` predicate in every query:
  - `CreateProject(ctx, orgID, name) (Project, error)` and `Projects(ctx, orgID) ([]Project, error)`.
  - `CreateEnvironment(ctx, orgID, projectID, name) (Environment, error)` and `Environments(ctx, orgID, projectID) ([]Environment, error)`.
  - `CreateService(ctx, orgID, environmentID, name, serverID) (Service, error)` and `Services(ctx, orgID, environmentID) ([]Service, error)`. `CreateService` takes `project_id` from the environment row.
  - `ResolveTarget(ctx, orgID, project, environment string) (projectID, environmentID string, err error)`: the name-to-id resolution the registry needs before its scope check (`docs/specs/registry.md` "Targets"). An empty `environment` resolves the project only and returns an empty `environmentID`.
  - Lists are ordered by `name`. Ids come from `NewID`, timestamps from `formatTime`.
- `internal/store/names.go`: the name check of `docs/specs/storage.md` "Names": 1 to 63 bytes of `[a-z0-9-]`, a letter or digit at both ends. A failing name returns an error wrapping `ErrInvalidName` that quotes the name and the expected format.
- `internal/store/`: the four named tests. `TestSchemasMatch` and `TestLookupTablesMatchSchema` already cover the new tables and must pass unchanged.
- `docs/specs/storage.md`: record that `services.current_release_id` and `services.previous_release_id` are added by W2-11b together with `releases`, and name the conformance cases this ticket adds.

## Acceptance criteria

- `TestProjectsConformanceSQLite` and `TestProjectsConformancePostgres` run one shared suite (`runProjectsConformance`) against each backend, migrated first. It proves:
  - a project, an environment in it and a service in that environment on a server of the same org are created and listed back with their ids, names, parent ids and `server_id`;
  - `CreateService` with a server id of another org returns `ErrNotFound` and writes nothing; so do an unknown server id, an environment id of another org, and, for `CreateEnvironment`, a project id of another org;
  - a second project with the same name in the org, a second environment with the same name in the project, and a second service with the same name in the environment return `ErrDuplicate`; the same environment name in another project, the same service name in another environment and the same project name in another org succeed;
  - `ResolveTarget` returns the ids for a known project and environment, the project id alone for an empty environment, and `ErrNotFound` for an unknown name or a name that exists only in another org;
  - a second org lists no projects, environments or services of the first, whichever parent id it passes.
- `TestPostgresRLSOnProjectTables`: under the application role, with `app.org_id` unset, empty or naming a nonexistent org, `SELECT org_id` from `projects`, `environments` and `services` without a `WHERE` returns no rows; with `app.org_id` A it returns only A's rows; an `INSERT` of an org B row into each table under `app.org_id` A fails; `pg_tables.rowsecurity` is true for all three.
- `TestProjectNamesValidated` (table-driven, SQLite): `CreateProject`, `CreateEnvironment` and `CreateService` accept `a`, `a-1` and a 63-byte name, and return `ErrInvalidName` for the empty name, a 64-byte name, upper case, `_`, `.`, a space, a leading `-` and a trailing `-`, without writing a row.
- Every store error wraps its cause with context; not-found, duplicate and invalid-name cases are testable with `errors.Is` against `ErrNotFound`, `ErrDuplicate` and `ErrInvalidName`.
- The cross-org server, environment and project checks are explicit `SELECT … WHERE id = $1 AND org_id = $2` reads inside the org-bound transaction, not foreign keys alone: Postgres referential checks do not apply RLS.
- `make ci` is green; `testdata/tests.txt` lists the four tests.

## Out of scope

- `releases`, `rollbacks`, and the services release columns `current_release_id` and `previous_release_id`, with the methods that write them: W2-11b.
- Operation inputs and the 400, 404 and 409 mapping of `ErrInvalidName`, `ErrNotFound` and `ErrDuplicate`: W2-11c.
- The `projects.*`, `environments.*` and `services.*` operations: W2-11d.
- `environments.protected`: W4-2. Environment keys and secrets: W3-2. `servers.deploy_key`: W3-8.
- A service-by-name lookup for deploys: W2-11b or W2-5, whichever first needs it.
- Renaming or deleting projects, environments or services: never renamed (owner decision D1); deletion is not specified.

## Security notes

- `docs/threat-model.md` §3, boundary B2: the three tables carry `org_id`, have RLS with the `org_isolation` policy on Postgres, and are not lookup tables. Only `internal/store` writes their SQL. The application role gets the same grants through `pg.Migrate` and never migrates.
- §9 reviewer checklist: no table is added without `org_id`; `LookupTables` gains nothing.
- A service on another org's server would let one org deploy to another org's machine. `CreateService` must check the server inside the caller's org-bound transaction and refuse it with `ErrNotFound`, so the existence of another org's server id is not revealed.
- Names reach the agent as `agent.toml` path elements and Docker names (`docs/specs/protocol.md`); the store refuses any name outside the format, so a stored name is always one the protocol accepts.
- No secret, key or token is stored in these tables.

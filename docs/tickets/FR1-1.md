# Enrolment and REST over TLS

The owner decision of 2026-11-18 (`docs/specs/enrolment.md`, "Transport security"; `docs/specs/connection.md`, "Transport") is built: `moonglass server` serves `POST /v1/enroll` and the registry REST routes on `--listen` over TLS 1.3 only, presenting its Ed25519 control-plane key in a `keys.SelfSignedCert` carrier, and prints that key's fingerprint at start. `moonglass agent enroll` takes `--server-fingerprint FP`, refuses `http://`, checks the TLS leaf key against FP before the token is sent, and pins only that verified key. The generated CLI refuses an `http://` `MOONGLASS_URL` unless the host is localhost. This closes R-1 finding 1: the enrolment token and owner tokens no longer cross the network in clear, and the first pin is authenticated.

## Scope

- `internal/keys`: `ListenerTLSConfig(priv)`, a TLS 1.3-only server config presenting `SelfSignedCert(priv)` with no client certificate requested and session tickets disabled. `EnrolClientTLSConfig(fingerprint)`, a TLS 1.3-only client config that skips chain verification and, in `VerifyPeerCertificate`, accepts only a leaf whose `PeerPublicKey` gives `Fingerprint(key) == fingerprint`; no session cache.
- `internal/server`: `Run` wraps the `--listen` listener in `keys.ListenerTLSConfig` with the control-plane key; the plain-HTTP serve path is deleted. A `Server.Fingerprint()` (the `keys.Fingerprint` of the control-plane public key). `Run` prints the fingerprint as the first stdout line on every start, before any token line. Existing tests that read `Run`'s stdout line by line are updated for the new first line; existing enrolment tests serve `Handler()` through an `httptest` TLS server configured with `keys.ListenerTLSConfig`.
- `internal/agent`: `Enroll(ctx, dataDir, url, serverFingerprint, token)` builds its own client from `keys.EnrolClientTLSConfig` (the `*http.Client` parameter is removed). A URL that is not `https://` is refused before keys are generated or any request is made. Redirects are not followed. After an `ACCEPTED` response, the response's `control_plane_public_key` must equal the TLS leaf key the fingerprint check verified (`res.TLS.PeerCertificates[0]`); otherwise nothing is written.
- `internal/cli`: the generated runner parses `MOONGLASS_URL`; scheme `https` is used with Go's standard certificate verification (`http.DefaultClient`, no `InsecureSkipVerify`); scheme `http` is allowed only when the host is `localhost` or a loopback IP literal; anything else exits 2 with a message naming `MOONGLASS_URL`, and sends nothing.
- `cmd/moonglass`: `agent enroll` gains `--server-fingerprint FP`; a missing one prints usage and exits 2, like a missing `--url`. The `--listen` help text says TLS 1.3, not plain HTTP.
- `internal/registry/routes.go`: the `agent enroll` synopsis becomes `agent enroll [--data-dir DIR] --url URL --server-fingerprint FP TOKEN`. No other registry change.
- `docs/specs/enrolment.md`: remove the stale plain-HTTP sentences in "HTTP endpoint" (TLS not required, the token over plain HTTP until W1-4); "Commands" names `--server-fingerprint`, the fingerprint line `moonglass server` prints first, and the agent's `https://`-only rule; "Transport security" states that the pinned key is the TLS leaf key verified against FP and equal to `control_plane_public_key`, and that "localhost" means the host `localhost` or a loopback IP literal. `docs/specs/registry.md`: the generated runner's `MOONGLASS_URL` rule. `docs/specs/connection.md` only if its FR1-1 paragraph needs the same wording.

## Acceptance criteria

- `TestListenerTLSConfigNeedsNoClientCert`: a client with no certificate completes a TLS 1.3 handshake against `ListenerTLSConfig(priv)`, the leaf key it sees equals `priv.Public()`, and a client limited to TLS 1.2 fails the handshake.
- `TestEnrolClientTLSConfigChecksFingerprint`: table-driven over a server presenting key K: the fingerprint of K connects; the fingerprint of another key, an empty string and an uppercase copy of K's fingerprint each fail the handshake; a TLS 1.2-only server fails.
- `TestRunServesListenOnlyOverTLS`: with `Run` on `127.0.0.1:0` listeners, a plain-HTTP request to the `--listen` address gets no HTTP response; over TLS 1.3, `POST /v1/enroll` and one registry route answer, and the presented leaf key equals the control-plane key in `--data-dir`.
- `TestRunPrintsControlPlaneFingerprintFirst`: the first stdout line is `keys.Fingerprint` of the control-plane public key, with no other text; it is the first line with and without `--print-enroll-token` and `--print-owner-token`, the token lines keep their order after it, and a second start on the same data dir prints the same fingerprint.
- `TestEnrollPinsFingerprintVerifiedKey`: an enrol over TLS with the server's fingerprint answers `ACCEPTED`, and `control-plane.pub` equals the TLS leaf key.
- `TestEnrollFingerprintMismatchSendsNoToken`: with a wrong fingerprint the enrol fails, the server's handler is never called, the token is still unused (a later enrol with the right fingerprint succeeds) and no file is written in the data dir.
- `TestEnrollRefusesPlainHTTP`: table-driven over `http://` URLs, including `http://localhost:PORT` and `http://127.0.0.1:PORT` pointing at a live listener: the enrol fails with an error naming `https://`, the listener sees no request, and the data dir holds no file.
- `TestEnrollRejectsResponseKeyOtherThanTLSKey`: a TLS server presenting key A whose fingerprint is given, answering `ACCEPTED` with control-plane key B, makes the enrol fail, and neither `control-plane.pub` nor `fingerprint` is written.
- `TestGeneratedRunnerRefusesPlainHTTPExceptLocalhost`: table-driven: `http://localhost`, `http://127.0.0.1` and `http://[::1]` reach a loopback test server; `http://` with a non-loopback host exits 2, stderr names `MOONGLASS_URL` and does not contain the token, and no request is made; an `https://` server whose certificate is not trusted by the system roots fails with exit 1 and receives no request with the bearer.
- `TestAgentEnrollNeedsServerFingerprint`: `moonglass agent enroll --url URL TOKEN` without `--server-fingerprint` prints the usage text to stderr, exits 2 and creates no data dir file; the usage line for `agent enroll` contains `--server-fingerprint FP`.
- No plain-HTTP listener remains in `internal/server`; `net/http` `Serve` on `--listen` is reached only through the TLS listener.
- The token never appears in an error, in stderr or in stdout, on every refusal path above.
- Existing tests keep passing; changed ones change only the transport (TLS test servers, the fingerprint argument) and the stdout line count, never an assertion about tokens, keys or files.
- `make ci` is green.

## Out of scope

Revocation and the agent listener `/v1/agent`, already TLS 1.3 with mutual keys (W1-4). A CA-issued certificate or a TLS front for the CLI and browser, and certificate rotation on a long-running listener. Install-time port and listen choices (W1-6). The agent age recipient in storage (FR1-2). Moving the agent key files (FR1-3). Token generation (FR1-6). The `/v1/agent` authorisation text (FR1-7).

## Security notes

- §B3 (control plane ↔ agent): the first pin is no longer trust in whatever answers the URL. The agent sends the token only after the TLS 1.3 handshake proved possession of a key whose SHA-256 matches the fingerprint the operator copied from `moonglass server`, and it pins only that key. Chain, subject, SAN and expiry of the carrier certificate are not trusted; the fingerprint is the whole check. No session resumption may bypass `VerifyPeerCertificate` (no client session cache, server session tickets disabled).
- Tokens (assets table, ADR-0005): the enrolment bearer and owner tokens cross the network only inside TLS 1.3. `http://` is refused before any request by the agent, and by the CLI except on localhost, so a token is never sent in clear off the machine. Redirects are not followed by the agent. Tokens are never printed or logged; refusals redact them.
- The CLI uses standard certificate verification; it must not skip verification or accept the self-signed control-plane certificate.
- Docs claim no more than this: a wrong fingerprint copied by the operator, or a compromised control plane holding the real key, is outside what this check protects against (threat-model §4, full control of the running control plane).

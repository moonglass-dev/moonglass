# Rollbacks and service release state on the control plane

The control plane keeps each service's release state and records every rollback, as `docs/specs/storage.md` "Projects, environments, services and releases (W2-11)" specifies. After this ticket `services` carries `current_release_id` and `previous_release_id`, written by one store call that copies the `app` state of a `CommandResult` (`docs/specs/protocol.md`); a service is found by name in its environment; and the `rollbacks` table records a rollback's start with its envelope request id, its final status and detail, and returns the running rollbacks of one server in one org, so W2-5 can re-send a `ROLLBACK` after a restart, as it re-sends release steps from `InFlightReleases`. The same conformance suites run on SQLite and Postgres, and Postgres enforces row-level security on the new table (ADR-0002).

## Scope

- `internal/store/migrations/pg/0006_rollbacks.sql` and `internal/store/migrations/sqlite/0006_rollbacks.sql`, with the same columns and nullability on both backends:
  - `services` gains `current_release_id` (`TEXT NOT NULL DEFAULT ''`) and `previous_release_id` (`TEXT`, nullable, as `docs/specs/storage.md` lists it; `NULL` when the app has no previous release). No foreign key on either: the spec names none.
  - The table `rollbacks`: `id` (primary key), `org_id` (references `orgs`), `service_id` (references `services`), `request_id`, `status`, `detail`, `created_at`, `finished_at`. Every column is `NOT NULL`; `request_id`, `detail` and `finished_at` default to empty text, as the release columns do. `CHECK` on `status` (`running`, `succeeded`, `failed`, `rejected`), as `releases.status` is checked.
  - Postgres only: `ENABLE ROW LEVEL SECURITY` on `rollbacks` and the `org_isolation` policy of `docs/specs/storage.md`. No grants in the file (`pg.Migrate` grants). No new lookup table: `LookupTables` is unchanged.
- `internal/store/store.go`:
  - `Service` gains `CurrentReleaseID` and `PreviousReleaseID` (strings; empty for none, whether the column holds empty text or `NULL`).
  - The type `Rollback` (`OrgID`, `ID`, `ServiceID`, `RequestID`, `Status ReleaseStatus`, `Detail`, `CreatedAt`, `FinishedAt`). A rollback's status uses the existing `ReleaseStatus` constants `running`, `succeeded`, `failed` and `rejected`; no second status type.
  - The sentinel `ErrRollbackState` for a rollback not in a status that allows the call.
  - These `Store` methods, each run through `inOrg` with an `org_id` predicate in every query:
    - `ServiceByName(ctx, orgID, environmentID, name string) (Service, error)`: the service of that name in the environment, with every field including the two release ids. `ErrNotFound` when no service of that name is in that environment of the org.
    - `SetServiceReleases(ctx, orgID, serviceID, currentReleaseID, previousReleaseID string) error`: one `UPDATE … WHERE id = $n AND org_id = $m` that writes both columns from a `CommandResult`'s `app.current_release_id` and `app.previous_release_id`; an empty previous id is stored as `NULL`. `ErrNotFound` when the service is not the org's, and nothing changes. The store copies the ids it is given and does not interpret them.
    - `StartRollback(ctx, orgID, serviceID, requestID string, now time.Time) (Rollback, error)`: reads the service inside the org-bound transaction (`ErrNotFound` when it is not the org's, nothing written), mints the id with `NewID`, and inserts the rollback as `running` with `request_id` and `created_at` = `now`. Returns the stored row.
    - `FinishRollback(ctx, orgID, rollbackID string, status ReleaseStatus, detail string, now time.Time) (Rollback, error)`: a `running` rollback ends as `succeeded`, `failed` or `rejected` with `detail` and `finished_at` = `now`, in one `UPDATE … WHERE id = $n AND org_id = $m AND status = 'running'`; returns the finished row. `ErrNotFound` for a rollback that is not the org's, `ErrRollbackState` for one already final; nothing changes in either case. A status outside the three final ones returns an error naming them before any SQL runs.
    - `InFlightRollbacks(ctx, orgID, serverID string) ([]Rollback, error)`: the `running` rollbacks of every service of the org on that server, oldest first (`created_at`, then `id`). It joins `services` with `org_id` predicates on both tables, as `InFlightReleases` does. A server that is not the org's returns none.
  - All ids come from `NewID`, timestamps from `formatTime`.
- `internal/store/projects.go`: `Services` returns the two release ids; `CreateService` returns a service with both empty.
- `internal/store/`: the six named tests. `TestSchemasMatch`, `TestLookupTablesMatchSchema`, `TestMigrateIdempotent` and the existing projects and releases suites cover the changed schema and must pass unchanged.
- `docs/specs/storage.md`, under "Projects, environments, services and releases (W2-11)":
  - the `services` paragraph says W2-11e, not W2-11b, adds `current_release_id` and `previous_release_id`, together with `rollbacks`;
  - a W2-11e paragraph records the rules above: the column nullability and defaults, the `status` check, `ServiceByName`, the copy of a `CommandResult`'s app state, which status `FinishRollback` accepts, `finished_at` empty until final, the in-flight read per org and server, and that `rollbacks` is not a lookup table and has the `org_isolation` policy on Postgres;
  - it names the conformance cases and the two other tests this ticket adds.

## Acceptance criteria

- `TestServiceReleaseStateConformanceSQLite` and `TestServiceReleaseStateConformancePostgres` run one shared suite (`runServiceReleaseStateConformance`) against each backend, migrated first. It proves:
  - a new service has empty `CurrentReleaseID` and `PreviousReleaseID` from `CreateService`, `Services` and `ServiceByName`;
  - `ServiceByName` returns the service with its id, names, parent ids, `server_id` and `created_at`, and `ErrNotFound` for an unknown name, for the name in another environment of the org, and for the name asked by another org;
  - `SetServiceReleases` with a current and a previous id is read back by `ServiceByName` and `Services`; a second call with a new current and an empty previous is read back with an empty previous;
  - `SetServiceReleases` on an unknown service or another org's service returns `ErrNotFound`, and the first org's service keeps its ids.
- `TestRollbacksConformanceSQLite` and `TestRollbacksConformancePostgres` run one shared suite (`runRollbacksConformance`) against each backend, migrated first. It proves:
  - `StartRollback` on a service of the org returns a rollback with a 32-hex id, status `running`, the request id, `created_at` from `now` and empty `detail` and `finished_at`;
  - `StartRollback` on an unknown service or another org's service returns `ErrNotFound` and writes nothing (no rollback appears in `InFlightRollbacks`);
  - `FinishRollback` ends a running rollback as each of `succeeded`, `failed` and `rejected`, returning its `detail` and `finished_at` from `now`; a second finish returns `ErrRollbackState`; a finish status of `queued`, `running` or `superseded` returns an error and leaves the rollback running;
  - `InFlightRollbacks` returns the running rollbacks of services on that server in the org, oldest first, and leaves out finished rollbacks and rollbacks of services on another server;
  - a second org gets `ErrNotFound` from `FinishRollback` on the first org's rollback, which stays running, and gets no rows from `InFlightRollbacks` and `InFlightReleases` with the first org's server id while the first org has a running rollback and a queued release there.
- `TestPostgresRLSOnRollbacks`: under the application role, with `app.org_id` unset, empty or naming a nonexistent org, `SELECT org_id FROM rollbacks` without a `WHERE` returns no rows; with `app.org_id` A it returns only A's rows; an `INSERT` of an org B row under `app.org_id` A fails; `pg_tables.rowsecurity` is true for `rollbacks`.
- `TestRollbackConstraintsEnforced` (table-driven, SQLite, raw SQL on a migrated database): an unknown rollback `status` (including `queued` and `superseded`) is refused by the `CHECK`; each of the four statuses is accepted; a `services` row inserted without the release columns reads back `current_release_id` as empty text and `previous_release_id` as `NULL`.
- Every store error wraps its cause with context; the not-found and wrong-status cases are testable with `errors.Is` against `ErrNotFound` and `ErrRollbackState`.
- The cross-org service check in `StartRollback` is an explicit `SELECT … WHERE id = $1 AND org_id = $2` inside the org-bound transaction, not the foreign key alone: Postgres referential checks do not apply RLS.
- `make ci` is green; `testdata/tests.txt` lists the six tests.

## Out of scope

- The `rollback`, `deploy` and `releases.list` operations, sending `ROLLBACK`, re-sending in-flight steps and rollbacks after a restart, deciding which `CommandResult` is the latest, and marking current and previous in the history: W2-5.
- Refusing a second running rollback of one service: not specified; one command at a time per app is the server's rule (`docs/specs/connection.md`, W2-10 and W2-5).
- Checking that the copied release ids name releases of the service: not specified.
- Leaving deleted services out of `ServiceByName` and the rollback reads: W5-5c.
- Retention or deletion of rollback rows: not specified.

## Security notes

- `docs/threat-model.md` §3, boundary B2: `rollbacks` carries `org_id`, has RLS with the `org_isolation` policy on Postgres, and is not a lookup table. Only `internal/store` writes its SQL. The application role gets its grants through `pg.Migrate` and never migrates. The two new `services` columns sit under the existing `services` policy.
- §9 reviewer checklist, item 5: every new query runs inside the caller's org and is covered by the conformance suites on both backends; no table is added without `org_id`; `LookupTables` gains nothing.
- A rollback started on another org's service would send a `ROLLBACK` to another org's app on another org's server. `StartRollback` checks the service inside the caller's org-bound transaction and refuses it with `ErrNotFound`, so another org's service id is not revealed. `SetServiceReleases` and `ServiceByName` are bound to the org the same way.
- The in-flight reads decide which commands the control plane re-sends to a reconnecting agent. They are per org and server, so an agent is never sent another org's step or rollback.
- `detail` and the copied release ids are agent-reported data (boundary B3) and are stored as data, never interpreted. No secret, key or token is stored in `rollbacks` or the new columns.

# Service settings on the control plane

`deploy` takes a service's settings, `command`, `volume`, `label`, `restart` and `healthcheck` with its timings, checks each by the protocol's rules, stores them on the release, and sends them in `DEPLOY`; `services.restore` copies them from the current release (`docs/specs/registry.md`, "Service settings on `deploy`"; `docs/specs/storage.md`, "Service settings on releases"; `docs/specs/delete.md`). The owner approved the inputs and the columns on 2026-11-19. Nothing here is specific to databases or Compose.

## Scope

- `internal/store`: one migration per backend adding `command`, `volumes`, `labels`, `restart` and `healthcheck` to `releases`, `TEXT NOT NULL` with the defaults of the storage table; `Release` gains the fields; `EnqueueRelease` stores them and every release read returns them. A conformance function run as the two named conformance tests.
- `internal/registry`: the `deploy` operation's `In` gains the inputs, with `json` and `doc` tags; the handler parses `volume` (`<name>:<target>[:ro]`) and `label` (`<key>=<value>`, split at the first `=`), builds the protocol values and checks them with `internal/protocol`'s validation, and refuses a failure with `Refuse(ErrInvalidInput, …)` naming the input, before a release is minted. The healthcheck inputs follow the required-together rule. A refusal message never includes a label value or a command entry.
- `internal/server`: the deploy driver puts the stored settings into `DEPLOY`; the restore path of W5-5d copies the current release's settings into the new release.
- `internal/api/openapi.json` and `internal/cli/generated.go`: regenerated with `make generate`, never edited by hand.
- The three specs: already say this; change them only if the built behaviour needs a wording fix.

## Acceptance criteria

- `TestReleaseSettingsConformanceSQLite` and `TestReleaseSettingsConformancePostgres`: a release enqueued with every setting reads back equal through the history and the in-flight read; one enqueued with none reads back `''`, `'[]'`, `'{}'`, `''` and `''`; a second org reads none of them.
- `TestReleaseSettingsDefaults`: on a migrated SQLite database, raw SQL shows the five columns `NOT NULL` with those defaults, and an `INSERT` that omits them stores the defaults.
- `TestDeploySettingsInputsValidated`: a table with one row per malformed input (a volume without a target, with a relative target, with a fourth part; a label without `=`, with a `dev.moonglass.` key; a restart of `always`; healthcheck timings without a test; a test without timings; a timing out of bounds); each is refused as `ErrInvalidInput`, audited `invalid input`, and mints no release.
- `TestDeployCommandCarriesSettings`: a `deploy` with every input sends one `DEPLOY` whose settings equal the inputs, in order, as an agent stub in the test receives it.
- `TestRestoreCopiesReleaseSettings`: restoring a deleted service whose current release has every setting sends a `DEPLOY` with the same settings, and the new release row holds them.
- `TestGeneratedOpenAPIIsCurrent`, `TestGeneratedCLIIsCurrent` and every existing test pass unchanged.
- `make ci` is green and `scripts/verify check W6-1d` passes.

## Out of scope

- W6-4b: `compose_hash`. W6-1c: the agent side. W6-1: `databases create`.

## Security notes

- `docs/threat-model.md` §3 B2 and §9.5: the columns are on `releases`, a row-level table under `org_isolation`; every read and write runs in the caller's org. No setting is a secret: secrets travel only as ciphertext (`docs/specs/secrets.md`), and a label value is not one.
- §9.1: the control plane checks the inputs with the protocol's own rules, so a malformed value is refused before it is stored; the agent checks again when it opens the `DEPLOY`.
- §9.5: `deploy` keeps its role, scope and `destructive` flag; no authz-matrix line changes.

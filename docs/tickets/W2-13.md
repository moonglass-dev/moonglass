# Agent state database

`internal/agent/state` opens `<data-dir>/agent.db` (mode 0600, with the pragmas in `docs/specs/agent-state.md`) and migrates it with `store.Migrate`. It creates the `apps` and `releases` tables and writes three records, each in one transaction: the binding, the candidate release and the failed release. These are the records the W2-3 deploy executor needs for "Record" and "Failure" in `docs/specs/release.md`. Afterwards the agent has a database that holds release records only, under the ADR-0010 amendment of 2026-11-17.

## Scope

- `internal/agent/state` (new package):
  - `Open(ctx, dataDir string) (*DB, error)` opens `<dataDir>/agent.db` with `modernc.org/sqlite`, then applies the embedded migrations with `store.Migrate` from `internal/store`. Opening creates the file with mode 0600, and the file is mode 0600 once `Open` returns. It never creates `dataDir`. Every connection gets the pragmas `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout=5000`, `foreign_keys=ON` and `cache_size=-2000`. It uses one open connection, as `internal/store/sqlite` does. Every error from opening or migrating includes the full path of `agent.db`. `(*DB).Close` closes the database.
  - `migrations/0001_releases.sql`, embedded with `embed.FS`, holds the `apps` and `releases` tables with exactly the columns in `docs/specs/agent-state.md`, "Schema". Timestamps are UTC RFC 3339 text with a `Z`. `domains` is a JSON array. The `release_id` columns of `apps` and `stop_after`, `switched_at` and `pre_deploy_reversible` in `releases` are nullable. `phase` is constrained to `none`, `pending` or `ready`, and `status` to the six statuses the spec lists. The `commands` table is not created here.
  - `(*DB).App(ctx, appID)` returns the stored binding (`project`, `environment`, `service`) and the app's `release.State`. Each `release.Release` carries its `release_id` and its `image_ref`. A separate result says whether the app is unknown.
  - `(*DB).RecordCandidate(ctx, binding, release, state, now)` writes all of the following in one transaction: the `apps` row with the binding on the app's first deploy, the `releases` row with status `candidate`, and the app's current, previous and candidate release ids and phase taken from `state`. It returns an error and writes nothing when any of these holds:
    - the stored binding of the `app_id` differs from `binding`. The error names the stored project, environment and service.
    - `state.Candidate` is not the release being recorded.
    - a row already exists for that `(app_id, release_id)`.
  - `(*DB).RecordFailed(ctx, release, detail, now)` writes the `releases` row with status `failed` and `error` = `detail`, in one transaction. It never creates or changes an `apps` row, so the binding and the release state stay as they were (`docs/specs/release.md`, "Failure"). A row that already exists for that `(app_id, release_id)` is an error, and nothing is written.
  - The release record holds `app_id`, `release_id`, `image_ref`, `image_id`, `repo_digest`, `port`, `health_path`, `domains`, `has_pre_deploy` and `container_id`. A value that a failed step never reached is empty.
- `go.mod`: `modernc.org/sqlite` moves from indirect to direct, at the version pinned in ADR-0010 (v1.62.0). No other module is added.
- `.golangci.yml`: a lax depguard rule, `sqlite-deps`, denies `modernc.org/sqlite` in the files of every package that exists today except `internal/store` and `internal/agent/state`. That includes `**/internal/agent/*.go`, the agent's own top-level files. The deny list follows the `age-deps` pattern, which lists each package because depguard does not apply file exclusions. This enforces the ADR-0010 consequence "Only `internal/store/sqlite` and `internal/agent/state` import modernc".
- `docs/specs/agent-state.md`: the introduction says W2-13 creates the database with the release tables, W2-3 uses it, and W2-10 adds the command records. "Rules" says that a failed release row never creates or changes an `apps` row.

## Acceptance criteria

- `TestOpenCreatesFileMode0600`: after `Open` in a fresh temporary directory, `agent.db` is mode 0600. So is each `agent.db-wal` and `agent.db-shm` that exists after a write.
- `TestOpenSetsPragmas`: on the opened database, `PRAGMA journal_mode` is `wal`, `synchronous` is 2 (FULL), `busy_timeout` is 5000, `foreign_keys` is 1 and `cache_size` is -2000. The check runs after a `Close` and a second `Open` too.
- `TestOpenMigratesSpecSchema`: the database holds exactly the tables `apps`, `releases` and `schema_migrations`. The columns of `apps` and `releases` are exactly those in the spec, so there is no column for key material, a token or a secret. A second `Open` of the same file succeeds and keeps the rows already written.
- `TestOpenErrorNamesPath`: table-driven, with a data directory that does not exist and with an applied migration whose recorded checksum was altered. `Open` returns an error that contains the full path of `agent.db`.
- `TestRecordCandidateFirstDeployWritesBinding`: on an unknown app, `RecordCandidate` creates the binding, the `candidate` row with every column that was sent, and the state (candidate id, phase `pending` or `ready`). `App` then returns the same binding and a `release.State` equal to the one that was recorded. Before the write, `App` reports the app as unknown.
- `TestRecordCandidateKeepsBinding`: the first candidate is recorded, `release.State.Switch` is applied to it, and a second candidate is recorded with the same binding. The binding and `created_at` of the `apps` row are unchanged. The current, previous and candidate ids follow the new state.
- `TestRecordCandidateRejectsOtherBinding`: table-driven over a different project, environment and service. Each case returns an error that names the stored triple, and the `apps` and `releases` rows are byte-for-byte unchanged.
- `TestRecordCandidateIsAtomic`: table-driven over a duplicate `(app_id, release_id)` and a state whose candidate is a different release. Each case returns an error, and no `apps` or `releases` row is added or changed.
- `TestRecordFailedLeavesStateUnchanged`: the app is tested both unknown and known. `RecordFailed` writes one `failed` row with `error` equal to the detail. The `apps` row is unchanged for the known app and absent for the unknown one. `App` returns the same state as before.
- Every SQL statement takes its values as parameters. No value is formatted into the SQL text.
- No package outside `internal/store` and `internal/agent/state` imports `modernc.org/sqlite`, and `make ci` (lint included) is green.
- `internal/agent/state` imports nothing from `internal/keys`, `internal/protocol` or `internal/deploy`.
- No error or log line contains an environment value. `detail` is stored exactly as given and is never logged.

## Out of scope

- W2-3 covers the deploy executor, the binding check before acting, calling `RecordCandidate` and `RecordFailed`, and the start-up reconcile.
- W2-4 covers the `current`, `previous`, `retired` and `aborted` updates, `switched_at`, `stop_after`, retention and keep-five.
- W2-6 covers `pre_deploy_reversible` and the `aborted` rows of failed pre-deploy steps.
- W2-10 covers the `commands` table, writing a command's row and its state change in one transaction, and opening the database at agent start, where a failure stops the agent.

## Security notes

- `docs/threat-model.md` §2 says the agent keys, deploy key, tokens and secrets never go in this database. Per ADR-0010 (amended) and `docs/specs/agent-state.md`, it holds release records only, and `TestOpenMigratesSpecSchema` pins the column list. The package is not trusted core. It must not import `internal/keys`.
- §8, "Local policy beats remote command": a binding is never updated. `RecordCandidate` refuses a different project, environment or service, so a control plane cannot use this database to move an app into another project's `agent.toml` blocks (`docs/specs/protocol.md`, "Identity binding").
- §9, the reviewer checklist on secrets: the file is mode 0600 and so are its WAL files. `error` holds only the command's `detail`, which never contains an environment value (ADR-0004 decision 12). No statement is built from untrusted text.

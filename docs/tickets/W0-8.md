# Fetch ticket dependencies in the harness, allow go version and go env, ask for single Bash commands

## Outcome

Three harness fixes found while running W1-1:

1. **The harness, not the model, fetches authorized modules.** Model sessions run with `GOFLAGS=-mod=readonly` and `go get` denied, so a ticket that needs a module could not add it. At the start of `cmd_impl`, before the first model call and on every retry from `impl_blocked` or `verify_failed`, `scripts/ticket` runs `go get <module>@<version>` for each entry of the ticket's `dependencies`, then `go mod tidy`, then `go get` again, in the ticket worktree under the scrubbed environment plus the caller's Go network settings (`GOPROXY`, `GOSUMDB`, `GOPRIVATE`, `GONOPROXY`, `GONOSUMDB`, `GOINSECURE`, `GOMODCACHE`, `GOPATH`) and without `GOFLAGS=-mod=readonly`.
   - An entry is `module/path v1.2.3` or `module/path@v1.2.3`. The version starts with `v` and a digit, so `latest` and a missing version are refused. A bad entry gives `impl_blocked` with the entry named, and no model session starts. `run --dry-run` refuses it too.
   - Only the ticket's own `dependencies` are fetched. A module named only in an ADR, or only in the plan, is not.
   - The ticket's `allow` must list `go.mod` and `go.sum`; otherwise `impl_blocked`, because `verify` would reject the change.
   - If `go get` or `go mod tidy` fails, `impl_blocked` with the reason and the tail of `.ticket/<ID>/deps.log`.
   - The second `go get` is needed because `go mod tidy` drops a module that no code imports yet, which is every module of a standard ticket at this point. `go.mod` and `go.sum` are left modified and uncommitted; the impl session commits them. Modules already present at the requested version make the fetch a no-op.
   - The impl prompt no longer tells the model to add a dependency. It says the harness did, that `go get`, `go install` and `go mod tidy` are not available, to commit `go.mod` and `go.sum`, and that a module outside the ticket's list is a new dependency and a stop.
   - `Bash(go get *)`, `go install *`, `go run *` and `go * -mod *` stay denied.
2. **`go version` and `go env` are allowed.** `Bash(go version)`, `Bash(go env)` and `Bash(go env *)` (for `go env GOPATH` and similar). `go env *-w*` and `go env *-u*` are denied, so no configuration can be written. `go version -m <file>` is not allowed.
3. **One Bash command at a time.** The tests, impl and fix prompts tell the model to run exactly one command per Bash call and never chain with `;`, `|` or `&&`; to retry a denied command as a simpler allowed single command and not treat Bash as unavailable; and to report blocked only after several distinct allowed commands have failed. The plan and review prompts are unchanged: plan has no Bash, and review has only `git diff`, `git log` and `git show`.

`docs/harness.md` and `docs/tickets/TEMPLATE.md` describe all three.

## Out of scope

Fetching in the tests stage (a core ticket's tests that import a new module fail to compile there, which counts as red). Fetching or tidying on `main`. Committing from the harness. Resolving `latest`. Changing the verify gates or `is_protected`. Product code. New ADRs. Widening any model permission beyond `go version` and `go env`.

This ticket edits the guard (`.claude/settings.json`, `scripts/ticket`), which the harness cannot do for itself, so it runs out of band.

## Acceptance tests

`make test-harness` covers, with a local file module proxy and no network:

- A dependency with no version, `latest`, a non-`v` version, a leading `-`, or an extra token gives `impl_blocked` naming the entry; the fake model session never starts. `run --dry-run` reports it as an error.
- Dependencies without `go.mod` and `go.sum` in `allow` give `impl_blocked`.
- A module the proxy does not have makes `go get` fail: `impl_blocked`, no model session.
- With `module v1.0.0` and `module@v1.2.3` entries, impl run from `impl_blocked` leaves both in `go.mod` and `go.sum` of the worktree, uncommitted (HEAD unchanged, both files modified), before the fake session starts; a module named only in an ADR is not in `go.mod`; a second run leaves both files byte-identical.
- A ticket with no dependencies runs no fetch.
- `.claude/settings.json` allows `go version`, `go env` and `go env *`; `go env`, `go env GOPATH` and `go env -json` are not denied; `go env -w ...`, `go env -u ...`, `go env GOFLAGS -w` and `go env --w ...` are denied; `go get`, `go install`, `go run` and `go * -mod *` stay denied; `go version -m` and `go mod tidy` are not allowed.
- The generated tests, impl and fix prompts contain the one-command, retry-when-denied and block-after-several rules; the impl prompt says the harness fetches and the model must not run `go get`, does not tell the model to add dependencies, and still stops on an unlisted one.

All earlier harness tests still pass unchanged. `make ci` stays green.

## Security notes

Touches the agent permission boundary and runs `go get` on the owner's machine outside any model session. The fetch runs only the ticket's own, owner-written dependency list, which is read from `.ticket/<ID>/ticket.md`, copied at `start`; module paths and versions are checked against a strict pattern and passed as arguments, never through a shell. Module code is downloaded but not built or run by `go get` and `go mod tidy`. The first build of it happens in the verify gates and model sessions, as for any dependency, under the existing rule that agents run code with the owner's privileges. The model still cannot add a module: `go get`, `go install`, `go run` and `-mod` stay denied, and `GOFLAGS=-mod=readonly` still applies to model sessions. `go env` is allowed only for reads: `-w` and `-u` are denied, and `go env` cannot be used to change `GOFLAGS`. `go version -m` is not allowed because it reads arbitrary files. The prompt change asks for one command per call; it is guidance, not a control.

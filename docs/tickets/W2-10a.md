# Command records and executor request ids

After this ticket every result the executor returns for `Deploy`, `SwitchRelease`, `Rollback` and `RunPreDeploy` is stored in agent state under the envelope's request id. It is written in the same transaction as the release-state change it reports, or alone when the command wrote nothing else. A request id that already has a row is answered with its stored `CommandResult`, and nothing runs. This is the agent-state half of "Each request id runs once" (`docs/specs/connection.md`), implementing `docs/specs/agent-state.md`, `commands` and "Executor API (W2-10a)". W2-10b connects it to the live connection.

## Scope

- `internal/agent/state/migrations`: a new numbered migration `0002_commands.sql` creating `commands` with `request_id TEXT NOT NULL PRIMARY KEY`, `type TEXT NOT NULL`, `app_id TEXT NOT NULL`, `result BLOB NOT NULL`, `received_at TEXT NOT NULL`, `finished_at TEXT NOT NULL`. `0001_releases.sql` is not edited. There is no `CHECK` on `type`, because W3-7 and W5-5b add types.
- `internal/agent/state`:
  - A `Command` value: request id, type (`deploy`, `switch_release`, `rollback` or `run_pre_deploy`), app id, received time and the `*agentv1.CommandResult`. The state package encodes the result with `proto.Marshal` and is the only place that encodes or decodes `commands.result`.
  - `RecordCandidate`, `RecordPreDeploy`, `RecordSwitch`, `RecordRollback`, `RecordAbort` and `RecordFailed` each take a `Command` and insert its row inside their existing transaction, with `finished_at` from the time they are given. When the write is refused, nothing is written, the command row included.
  - `RecordCommand(ctx, Command, finished)` writes the row alone, in its own transaction.
  - `CommandResult(ctx, requestID) (*agentv1.CommandResult, bool, error)` returns the decoded stored result and whether there is one.
  - `Retain` also deletes `commands` rows whose `finished_at` is more than 7 days before `now`, in its one transaction. It still never writes an `apps` row, and the image list it returns is unchanged.
- `internal/deploy`:
  - `Deploy`, `SwitchRelease`, `Rollback` and `RunPreDeploy` take the envelope's request id as their second argument, before the message.
  - Each first refuses an empty request id, then reads `DB.CommandResult`. A stored result is returned unchanged, and the method writes nothing and touches no container. `received_at` is the executor clock (`x.now`) when the method starts.
  - Every path that calls a `Record*` state change passes the `Command` carrying the exact result the method then returns. Every other return (a rejection before any write, a failed read, a failed push, a failed commit, a failed record) writes the row alone with `RecordCommand` before returning. Each returned result is recorded exactly once.
  - A failed lone-row write appends `; recording the command also failed: <error>` to the returned detail, following the existing convention of `fail` and `abortSwitch`.
  - The existing tests in both packages are updated to the new signatures; no assertion is weakened.
  - Owner exception (2026-11-20, `docs/pipeline/children/build.md`): in `internal/agent/state/state_test.go`, `TestPackageImportsReleaseAndStoreOnly` permits exactly `moonglass.dev/moonglass/internal/protocol/agentv1` (every other path at or under `internal/protocol`, and `internal/keys` and `internal/deploy`, stays forbidden), and `TestOpenMigratesSpecSchema` wants the tables `[apps commands releases schema_migrations]` and the migration `0002_commands.sql`. No other assertion changes.
- `docs/specs/agent-state.md`: changed only if the implementation shows a statement there is wrong; the expected behaviour is already written.

## Acceptance criteria

- `TestCommandsResultIsNotNull`: after `Open`, inserting a `commands` row with a null `result` fails with a `NOT NULL` constraint error, and the migration list holds `0002_commands.sql` after `0001_releases.sql`.
- `TestStateChangeWritesCommandRowInOneTransaction`: table over the six `Record*` writes. On success, both the release or app change and the `commands` row are present, and `CommandResult` returns the given result. When the write is refused (a state that does not follow, a release already recorded, or a request id that already has a row), neither the state change nor a new or changed command row is present.
- `TestCommandResultReturnsStoredResult`: `RecordCommand` then `CommandResult` returns a result `proto.Equal` to the one written, with `found` true. An unknown request id returns `found` false and no error. `received_at` and `finished_at` are RFC 3339 UTC with `Z`.
- `TestRetainPrunesCommandsAfterSevenDays`: rows with `finished_at` 7 days plus a second before `now` are deleted, and rows at 7 days minus a second are kept. The release rows and returned images are the same as they would be with no command rows.
- `TestEveryCommandResultIsRecorded`: against a real Engine, a table over `Deploy` (with and without pre-deploy), `RunPreDeploy` (success and a failing step), `SwitchRelease` (success and a failed health gate) and `Rollback`. After each call, `DB.CommandResult(requestID)` is `proto.Equal` to the returned result, the stored type and app id match, and a `SUCCEEDED` row was written in the same transaction as its state change (the release state read back equals `result.app`).
- `TestCommandWithNothingElseWrittenIsRecordedAlone`: table over a rejection before any write for each of the four methods (identity mismatch, illegal transition, unknown app, policy rejection). The returned result is stored under its request id, and the `apps` and `releases` rows are unchanged.
- `TestStoredRequestIDIsNotRunAgain`: a `Deploy` that succeeded, sent again with the same request id (and also with a different message and type under that id), returns the first stored result unchanged. The Engine shows no new container for the app, and the `apps`, `releases` and `commands` rows are unchanged byte for byte.
- `TestEmptyRequestIDRunsNothing`: each of the four methods, given an empty request id, returns `REJECTED` with a detail that names the request id, creates no container and writes no row in any table.
- No `commands` column or `CommandResult.detail` holds an environment value, secret or key: the only text stored is the result the method returns.
- `make ci` is green, and `testdata/tests.txt` is updated with `make test-list`.

## Out of scope

- The agent session's dispatch, the in-memory set of running request ids, sending and replaying results on the connection, `--policy`, and `TestResentCommandReturnsStoredResult`: W2-10b.
- The control plane's request ids, waits, timeouts and re-sends: W2-10.
- `BUILD`, `STOP_APP` and `REMOVE_APP` command rows: W3-7 and W5-5b, which add those commands.
- Auto-rollback events and the auto-rollback commit through `RecordRollback`: W4-3b.

## Security notes

- `docs/threat-model.md` §9 checklist item 1, "Can a re-sent command run twice?": a stored request id never reaches the Engine, and no state change is committed without its row. So after a restart, a re-sent command either returns its stored result or runs against state that holds no committed change from its first run (`docs/specs/connection.md`, "Each request id runs once").
- §9 item 3 and the ADR-0010 amendment: `internal/agent/state` still holds only release and command records. No key material, token, secret value, ciphertext or registry credential is written to `commands`. `result` is the `CommandResult`, whose `detail` never carries an environment value (ADR-0004 decision 12). Nothing new is logged.
- §2 "Host root": no new path to the Engine; every container still passes `internal/policy` exactly as before.

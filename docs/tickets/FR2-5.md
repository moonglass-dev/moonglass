# session_hashes.revoked_at is NULL when live

The Storage section of `docs/specs/auth.md` says that `session_hashes.revoked_at` is "empty when live". The migrations say otherwise. On both backends (`internal/store/migrations/sqlite/0005_sessions.sql`, `internal/store/migrations/pg/0005_sessions.sql`), `revoked_at` is a nullable `TEXT` with no default. `internal/store/sessions.go` treats a session as live only while `revoked_at IS NULL`, and it sets the column once with `COALESCE`. After this ticket, the spec describes the stored schema as it is (R-2 finding 5).

## Scope

- `docs/specs/auth.md`, Storage section, the `session_hashes` bullet: replace "`revoked_at` (empty when live)" with wording saying that `revoked_at` is NULL while the session is live and is set to the revocation time once, when the session is revoked.
- No other line changes. No code, migration or test changes.

## Acceptance criteria

- The `session_hashes` bullet in `docs/specs/auth.md` says `revoked_at` is NULL when the session is live. The words "empty when live" no longer appear there.
- The bullet's other columns (`hash`, `id`, `user_id`, `expires_at`) and every other Storage bullet are unchanged.
- The wording agrees with both `0005_sessions.sql` migrations and with `revoked_at IS NULL` in `internal/store/sessions.go`.
- `git diff --stat main` touches only `docs/specs/auth.md` and this ticket's own docs.
- `make ci` is green.

## Out of scope

- FR2-1, FR2-2, FR2-3 and FR2-4, the other R-2 findings.
- `link_token_hashes` and `step_ups` columns, which W4-1d builds and specifies.
- Any change to the migrations or to `internal/store`. The code is correct, and only the spec drifted.

## Security notes

None. This is a docs-only change. It must not change the documented revocation rule (`docs/threat-model.md`, sessions): a revoked or expired session is refused, and revocation is recorded once.

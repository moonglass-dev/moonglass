# Session authentication

A request authenticates with either a bearer token or the `__Host-mg_session` cookie with `Moonglass-Org`, never both; a session's principal carries its session id, the user's role in that org and the scope row `* * *`; every audit event records `session_id` and `step_up_id` and its hash covers them; and every route on the control plane's HTTP listener goes through `http.CrossOriginProtection` (`docs/specs/auth.md`, "Sessions" and "Storage"). It is the first piece of the W4-1b split (owner decision, 2026-11-19). Sessions are minted by W4-1f; this ticket only accepts them.

## Scope

- `internal/registry`:
  - `Principal` gains `SessionID`, empty for a bearer.
  - `Registry.AuthenticateSession(ctx, session, orgID string) (Principal, error)`: the session must have the `mg_` form; `store.SessionByHash` (W4-1a) must return it live at the registry's clock; the user must be a member of `orgID`. The principal has `OrgID`, `UserID`, `SessionID`, the member's role, empty `TokenID`, `Agent` false and the one scope `* * *`. Every refusal is `ErrUnauthenticated`, with no session text in the error.
  - `Registry.Authenticate(ctx, bearer)` is unchanged.
  - `Invoke` writes `SessionID` from the principal into the audit event, and an empty `StepUpID` (W4-1c fills it).
  - `audit.go`: the hash is `SHA-256(JSON [prev_hash, org_id, seq, id, at, principal_kind, user_id, token_id, session_id, step_up_id, operation, outcome, reason])`, and `VerifyAudit` uses the same function.
- `internal/api`: `principal` reads `Authorization`, the `__Host-mg_session` cookie and `Moonglass-Org`:
  - both a bearer and a session cookie: 401 `send a bearer token or a session cookie, not both`, before either is checked;
  - a bearer: `Authenticate`; a present `Moonglass-Org` that differs from the token's org is 401;
  - a session: `Moonglass-Org` is required, then `AuthenticateSession`; missing header, not a member, or a bad session is 401;
  - neither: 401 as today.
  The 401 detail for a session failure never echoes the cookie or the header.
- `internal/server`: the handler that serves the HTTP listener (`Server.Handler`) is wrapped once in `http.CrossOriginProtection`, so every route, `/v1/enroll` included, refuses a cross-site browser request with an unsafe method with 403 before any handler runs.
- `docs/specs/auth.md`: already says this; change it only if the built behaviour needs a wording fix.

## Acceptance criteria

- `TestAuthenticateSession`: a live session of a member gives the principal above for each of two orgs the user belongs to; an unknown, expired and revoked session, a malformed value, and an org the user is not a member of each return `ErrUnauthenticated`. A table, with expected and actual principals in failures.
- `TestSessionCallAuditsSessionID`: an operation invoked with a session principal writes one event whose `session_id` is the session's id and whose `token_id` and `step_up_id` are empty; a bearer call's event has an empty `session_id`.
- `TestAuditHashCoversSessionAndStepUp`: changing an event's `session_id` or `step_up_id` makes `VerifyAudit` name that event's sequence number, and the hash of an event equals the SHA-256 of the 13-element JSON array above.
- `TestBearerAndSessionTogetherIs401`: a request with both is 401 with that exact detail, and neither `Authenticate` nor `AuthenticateSession` runs (no audit event is written).
- `TestSessionNeedsMemberOrg`: a session without `Moonglass-Org`, and with an org the user is not a member of, is 401; with a member org the operation runs and returns 200.
- `TestBearerWithOtherOrgHeaderIs401`: a valid bearer with `Moonglass-Org` naming another org is 401; with its own org, or no header, it is 200.
- `TestCrossOriginWriteRefused`: a `POST` with `Sec-Fetch-Site: cross-site` is 403 on `/v1/enroll` and on a registry route, and the handler does not run; the same `POST` with no `Origin` or `Sec-Fetch-Site` (the CLI) reaches the handler; a cross-site `GET` reaches it.
- Every existing test in `internal/registry`, `internal/api` and `internal/server` passes unchanged.
- `make ci` is green and `scripts/verify check W4-1e` passes.

## Out of scope

- W4-1f: `internal/auth`, the provider round trip, minting sessions, sign-out, the `/auth` routes and `Store.UserByIdentity`.
- W4-1b: Google.
- W4-1c: step-up, which fills `step_up_id`.

## Security notes

- `docs/threat-model.md` §3 B1 and §8: authentication stays in the registry and `internal/api`'s one `principal` function; authorisation stays in `Invoke`. No middleware decides a role or scope; `CrossOriginProtection` only refuses cross-site writes.
- §9.4: a session is a 256-bit `mg_` bearer stored only as SHA-256 (W4-1a). Both credentials at once are refused, so a request can never be authorised by one and audited as the other.
- §9.3: no session value, cookie or token appears in an error, a log line or an audit reason.
- The audit hash change has no compatibility code: a development database made before W4-1a is recreated (`docs/specs/auth.md`, "Storage").

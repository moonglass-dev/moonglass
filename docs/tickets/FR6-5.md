# Correct the audit hash in registry.md

The "Audit" section of `docs/specs/registry.md` still gives the 11-field hash `SHA-256(JSON [prev_hash, org_id, seq, id, at, principal_kind, user_id, token_id, operation, outcome, reason])`. Since W4-1e, `eventHash` in `internal/registry/audit.go` hashes 13 fields, with `session_id` and `step_up_id` after `token_id`. `docs/specs/auth.md` ("Storage", `audit_events`) says the same. W4-1e's paths did not include `registry.md`, so the registry's own spec gives a base that matches no stored event (R-6 finding 5). After this ticket, `registry.md` gives the hash the code computes.

## Scope

- `docs/specs/registry.md`, "Audit", the hash line: the JSON array becomes exactly `[prev_hash, org_id, seq, id, at, principal_kind, user_id, token_id, session_id, step_up_id, operation, outcome, reason]`. "hex encoded" and the rest of the paragraph stay.
- `docs/specs/registry.md`, "Audit", first paragraph: the sentence listing what each event names also names the session id and step-up id, which are empty when they don't apply (as `docs/specs/auth.md` says), and points to `docs/specs/auth.md` for the session and step-up that set them.
- No other line changes. No code, test or other spec changes.

## Acceptance criteria

- The hash line in `docs/specs/registry.md` "Audit" lists the 13 fields in the same order as `eventHash` in `internal/registry/audit.go` and the `audit_events` hash in `docs/specs/auth.md`: `prev_hash, org_id, seq, id, at, principal_kind, user_id, token_id, session_id, step_up_id, operation, outcome, reason`.
- The 11-field array no longer appears anywhere in `docs/specs/registry.md`.
- The "Audit" first paragraph names `session_id` and `step_up_id` as event fields that are empty when they don't apply. It makes no other change to the described behaviour: event outcomes, when an event is written, and the rule that `reason` never holds a token or handler error text all stay as they are.
- The W5-1b / W5-5 paragraph (`agent_id`, `project_id`, `environment_id`, `system`, `audit.list`, `moonglass audit verify`) is unchanged.
- `git diff --stat main` touches only `docs/specs/registry.md` and this ticket's own docs.
- `make ci` is green.

## Out of scope

- FR6-1, FR6-2, FR6-3, FR6-4, FR6-6, FR6-7, FR6-8: the other R-6 findings. That includes the HTTPS sentence in `registry.md` "Tokens" (FR6-1).
- FR1-7: the "Ed25519 challenge" text in `registry.md`.
- W5-1b (`agent_id`) and W5-5 (`project_id`, `environment_id`, `system`), which change the hash again in their own tickets.
- Any change to `internal/registry` or `docs/specs/auth.md`. The code and auth.md are correct; only `registry.md` drifted.

## Security notes

`docs/threat-model.md` §2, "Audit trail": the chain is written only by the registry and recomputed by `VerifyAudit` and, from W5-5, `moonglass audit verify`. The spec must state exactly the fields and order the code hashes, so anyone recomputing the chain from the spec gets the same hashes. The change must not claim more for the audit trail than §2 and §5 support.

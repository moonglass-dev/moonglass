# Builds and git sources

Builds on the server from a GitHub repository and commit, using the server's own deploy key, plus the build-in-CI template. Specified by the weeks 2–3 preflight (owner decision D16). Sources: stack §3.5, §3.11; ADR-0003 decision 10; ADR-0004 decision 2; ADR-0014.

## Which ticket builds what

| Ticket | Builds |
|---|---|
| W3-7 | The `BUILD` message and the `deploy_key` heartbeat field (`docs/specs/protocol.md`) |
| W3-8 | The server's deploy key: generated by the agent, reported in `Heartbeat`, stored by the control plane, printed by `moonglass servers deploy-key` |
| W3-4 | `moonglass deploy --git <owner>/<repo>@<commit>`, the build on the server, `moonglass.toml`, and the build-in-CI template |
| W4-10 | The GitHub App: created from a manifest in a signed-in session, a push webhook that deploys, and adding the deploy key to the repository. It depends on W4-1 because creating an App from a manifest is a browser redirect that needs a signed-in session |

Until W4-10, `git push` goes live only through the build-in-CI template (G3), and the owner adds the deploy key to the repository by hand.

## Deploy key (W3-8)

- The agent generates one Ed25519 SSH key the first time it starts without one. `internal/keys` owns it, in its own file under the agent's data directory: `<data-dir>/deploy-key` (the OpenSSH private key, mode 0600) and `<data-dir>/deploy-key.pub`. It never goes into agent state (`docs/specs/agent-state.md`) and never leaves the server.
- The agent sends the public line in every `Heartbeat` (`deploy_key`). The control plane stores it on the server row (`docs/specs/storage.md`).
- `moonglass servers deploy-key --server S` prints it, with one line saying to add it as a read-only deploy key on each repository that server builds.

## A git deploy (W3-4)

1. `moonglass deploy --project P --env E --service S --git <owner>/<repo>@<commit>` calls `deploy` with `git`. The repository and commit follow the `Build` rules in `docs/specs/protocol.md`; a branch or tag name is refused.
2. The control plane sends `BUILD`, then, on `SUCCEEDED`, `DEPLOY` with `image` = `moonglass.local/<project>/<service>:<release_id>`.
3. The agent clones and builds as below, and answers with the image ID.

### Clone

- The agent runs the host's `git` with an argv, never a shell: `git clone --no-checkout --filter=blob:none -- git@github.com:<owner>/<repo>.git <dir>`, then `git -C <dir> checkout --detach <commit>`. The URL is built by the agent from the validated fields, so no text from a message becomes a git option or transport.
- The environment for `git` is `GIT_SSH_COMMAND=ssh -i <data-dir>/deploy-key -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<data-dir>/github_known_hosts` and `GIT_TERMINAL_PROMPT=0`. `github_known_hosts` holds GitHub's published SSH host keys, written by the agent from a constant in `internal/build`.
- The work directory is `<data-dir>/builds/<release_id>`. It is removed when the build ends, whether it succeeded or not.
- A clone failure that looks like an authentication failure says to add the deploy key, naming `moonglass servers deploy-key`.

### Build

- The agent runs the host's `docker buildx build` with an argv: the context is the checkout, the Dockerfile is `Dockerfile` at its root, `--tag moonglass.local/<project>/<service>:<release_id>`, `--load`, and never `--allow`. BuildKit's default denies the entitlements `security.insecure` and `network.host`, so a Dockerfile that asks for them fails.
- Before the build, the agent calls `policy.Check` with `Kind` `build`, the project, environment and service, and empty `BuildEntitlements`. Builds never request entitlements, so no allow block applies (`docs/specs/container-policy.md`, open question 1).
- `DOCKER_CONFIG` is `<data-dir>/docker-config`, because the agent's user has no home directory (`docs/specs/install.md`).
- **One build at a time** per server. A second `BUILD` waits for the first.
- A build has a 30-minute limit; over it, the build is killed and the step fails.
- The build's output is not put in the result. Its last 200 lines are written to `<data-dir>/builds/<release_id>.log`, mode 0600, kept for 7 days, for live logs (W4-4).
- The build cache is capped by the disk guard (`docs/specs/disk.md`).
- Pull requests from forks are never built: only a commit named by an authorised `deploy` call is.

### Host requirements

`git` 2.30 or later, and the Docker CLI with the buildx plugin, on the server. The agent checks both at start and logs one clear error when either is missing; deploys of images still work without them. `scripts/install` prints the same check.

### Tests

The builder takes its clone URL as a field that the agent always sets to the `git@github.com:<owner>/<repo>.git` form above; no message reaches it. Tests set it to a local bare repository, so CI needs no GitHub access. W3-E covers the build-in-CI path end to end (a deploy by digest from a local registry).

## `moonglass.toml` (W3-4)

The CLI reads `./moonglass.toml` when it exists and sends its keys as the `deploy` inputs. Giving a key both in the file and as a flag is an error. Unknown keys are an error.

```toml
port        = 8080
health_path = "/healthz"
domains     = ["app.example.com"]
pre_deploy  = ["bin/migrate"]
reversible  = false        # the pre-deploy step; stack §3.13
```

## The build-in-CI template (W3-4)

`examples/ci/github-actions.yml`: a GitHub Actions workflow that, on a push to the default branch, builds the image, pushes it to GHCR, and runs `moonglass deploy --image ghcr.io/<owner>/<repo>@<digest>` with `MOONGLASS_URL` and `MOONGLASS_TOKEN` from repository secrets. Actions are pinned by commit SHA. Pulling a private GHCR image needs a `registry` secret (`docs/specs/secrets.md`), which works once W3-5 and W4-8 land; until then the template deploys public images.

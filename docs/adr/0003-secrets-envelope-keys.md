# ADR-0003: Secrets, envelope keys and the recovery key

- **Status:** Accepted
- **Date:** 2026-11-16

## Context

The control plane must never hold a readable secret (V§1). A new or replacement server still has to receive secrets, and a dead server must not take its backups with it (S§3.9, S§3.11). All cryptography is reused: age (X25519), with the reference Go library on servers and in the CLI and the same author's TypeScript implementation in the browser (S§2).

## Decision

**Keys** (S§3.11)

| Key | Where it lives | Purpose |
|---|---|---|
| Agent key (X25519 + Ed25519) | Generated on each server at enrolment; never leaves it | Identity, and the recipient for wrapped environment keys |
| Environment key (an age X25519 pair per environment) | Public half: control plane, browser, CLI. Private half: only ever stored wrapped | Secret values and database backups are encrypted to it |
| Owner recovery key (one age identity) | Generated by `moonglass keys init` in the CLI. The owner saves it as a file and can print the same text; there is no second format. Up to two owners can hold one | Recovering, granting and rotating without a surviving server |

1. **`moonglass keys init` is required before the first secret is saved.** Once a quarter the UI asks for a recovery-key check: the CLI proves it can unwrap a test value without revealing anything.
2. **Environment key pairs are generated in the owner's CLI** when the environment is created. The CLI wraps the private half to the recovery key, and to the first server after the owner checks that server's fingerprint, then uploads the public half and the wrapped copies. The private half never exists in JavaScript the control plane serves. Creating an environment therefore needs the CLI.
3. **Wrapping.** Each value is encrypted to the environment public key. The environment private key exists only as wrapped copies, one per authorised agent and one per recovery key. The control plane holds only ciphertext and wrapped copies.
4. **Backups and exports** are encrypted to the environment public key. Exports carry ciphertext plus wrapped keys and are readable with stock `age` once the owner unwraps the environment key. **Bucket credentials are an environment secret**, encrypted to the environment key like any other, so a restore onto a new server needs only the recovery key (S§3.9, M§3 week 6).
5. **Grant.** Every grant is a recipient change: owner-only, with step-up (ADR-0006).
   - *First server:* granted by the CLI at environment creation (decision 2); no `RewrapEnvKey`.
   - *Unprotected environment:* after the owner confirms the enrolment in the UI, the control plane asks an online agent there to re-wrap the key to the new agent (`RewrapEnvKey`).
   - *Protected environment:* agents refuse `RewrapEnvKey`. The owner runs `moonglass secrets grant --env <name> --server <name>`; the CLI unwraps with the recovery key and shows the new server's fingerprint; the owner checks it against the one `moonglass agent enroll` printed; only then does the CLI wrap the key.
6. **Rotate:** `moonglass secrets rotate --env <name>` creates a new environment key, re-encrypts every value and re-wraps, with one executor per case. It is a recipient change: owner-only, with step-up.

   | Case | Executor | Rule |
   |---|---|---|
   | Protected environment | The owner's CLI | Unwraps with the recovery key; re-wraps to recipients the owner confirms by fingerprint |
   | Unprotected environment | An online agent in it | Re-wraps only to recipients already stored for that environment, never to one named in the request |
   | Recovery key | The owner's CLI, with the old recovery key | Unwraps every environment key, current and retained, and wraps each to the new recovery key |

   Rotation deletes the agent-wrapped copies of the old environment key and keeps its recovery-wrapped copy, so old backups stay readable through the recovery key. Rotation does not un-leak, so the UI lists the values to rotate at their source.
7. **Agent key rotation** is on demand at launch: the agent makes a new key and re-wraps the environment keys it holds to itself.
8. **One reveal path:** `moonglass secrets reveal` has the agent re-encrypt the value to a one-time CLI key; the control plane relays only ciphertext. It is owner-only, requires step-up, and is refused for any token owned by an agent identity, whatever its scope. Every reveal is audited. The recovery key is never used for everyday reads. Values are write-only in the web UI.
9. **The CLI pins each environment's public key** on first use and warns if it changes.
10. **Git access** uses a deploy key generated on the server; the control plane holds no repository credentials after setup.

**What browser-side encryption does and does not protect** is the table in `docs/threat-model.md` §5, taken from S§3.11. In one sentence: our database never holds a readable secret; if our running service were taken over, protected environments stay sealed and unprotected ones do not.

## Consequences

- A stolen database or backup yields ciphertext and wrapped keys only (S§4).
- **If every server in an environment is gone and no recovery key exists, nobody can decrypt its secrets or backups, including us.** The UI says so at `keys init`, on the pricing page and in the docs.
- The web UI cannot show a value after it is saved. The CLI is the stronger path and can do everything the UI can.
- A takeover of the running control plane can still serve altered JavaScript or a substitute environment key to a browser, and can enrol a server into an unprotected environment.
- `internal/keys` is trusted core. Its test vectors must be readable by the stock `age` tool (B W3-1).

## Alternatives rejected

- **Encrypting backups to the server's key:** a dead server would take its backups with it (S§3.9).
- **A control plane that can decrypt:** a stolen database plus one credential exposes everything (S§4).
- **Reading secrets with the recovery key day to day:** that key is only for granting, rotating and recovering (S§3.11).
- **Generating environment keys in the browser:** the private half would pass through JavaScript we serve.
- **Generating them on the first agent:** a server would be needed before the first secret, chosen by the control plane.
- **An agent rotating a protected environment:** it would re-wrap to recipients the control plane names, which the `RewrapEnvKey` refusal exists to stop.
- **Reveal by agent identities:** a leaked token could pull plaintext with no human involved.
- **Bucket credentials only in a file on the server:** they would die with the server, and restore would need more than the recovery key.

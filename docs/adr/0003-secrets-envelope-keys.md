# ADR-0003: Secrets, envelope keys and the recovery key

- **Status:** Accepted
- **Date:** 2026-11-16

## Context

The control plane must never hold a readable secret (V§1). A new or replacement server still has to receive secrets, and a dead server must not take its backups with it (S§3.9, S§3.11). All cryptography is reused: age (X25519), with the reference Go library on servers and in the CLI and the same author's TypeScript implementation in the browser (S§2).

## Decision

**Keys** (S§3.11)

| Key | Where it lives | Purpose |
|---|---|---|
| Agent key (X25519 + Ed25519) | Generated on each server at enrolment; never leaves it | Identity, and the recipient for wrapped environment keys |
| Environment key (an age X25519 pair per environment) | Public half: control plane, browser, CLI. Private half: only ever stored wrapped | Secret values and database backups are encrypted to it |
| Owner recovery key (an age identity) | Generated by `moonglass keys init` in the CLI; saved by the owner. Up to two owners can hold one | Recovering, granting and rotating without a surviving server |

1. **`moonglass keys init` is required before the first secret is saved.** Once a quarter the UI asks for a recovery-key check: the CLI proves it can unwrap a test value without revealing anything.
2. **Wrapping.** Each value is encrypted to the environment public key. The environment private key exists only as wrapped copies, one per authorised agent and one per recovery key. The control plane holds only ciphertext and wrapped copies.
3. **Backups and exports** are encrypted to the environment public key. Exports carry ciphertext plus wrapped keys and are readable with stock `age` once the owner unwraps the environment key.
4. **Grant, unprotected environment:** after a human confirms the enrolment in the UI with step-up, the control plane asks an online agent in that environment to re-wrap the key to the new agent (`RewrapEnvKey`).
5. **Grant, protected environment:** agents refuse `RewrapEnvKey`. The owner runs `moonglass secrets grant --env <name> --server <name>`; the CLI unwraps with the recovery key and shows the new server's key fingerprint; the owner checks it against the one `moonglass agent enroll` printed; only then does the CLI wrap the key.
6. **Rotate:** `moonglass secrets rotate --env <name>` creates a new environment key, re-encrypts every value, re-wraps to the remaining recipients and deletes the old wrapped copies. Old backups stay readable through the recovery key. Rotation does not un-leak, so the UI lists the values to rotate at their source.
7. **Agent key rotation** is on demand at launch: the agent makes a new key and re-wraps the environment keys it holds to itself.
8. **One reveal path:** `moonglass secrets reveal` has the agent re-encrypt the value to a one-time CLI key. The recovery key is never used for everyday reads. Values are write-only in the web UI.
9. **The CLI pins each environment's public key** on first use and warns if it changes.
10. **Git access** uses a deploy key generated on the server; the control plane holds no repository credentials after setup.

**What browser-side encryption does and does not protect** is the table in `docs/threat-model.md` §5, taken from S§3.11. In one sentence: our database never holds a readable secret; if our running service were taken over, protected environments stay sealed and unprotected ones do not.

## Consequences

- A stolen database or backup yields ciphertext and wrapped keys only (S§4).
- **If every server in an environment is gone and no recovery key exists, nobody can decrypt its secrets or backups, including us.** The UI says so at `keys init`, on the pricing page and in the docs.
- The web UI cannot show a value after it is saved. The CLI is the stronger path and can do everything the UI can.
- A takeover of the running control plane can still serve altered JavaScript or a substitute environment key to a browser, and can enrol a server into an unprotected environment.
- `internal/keys` is trusted core. Its test vectors must be readable by the stock `age` tool (B W3-1).

## Alternatives rejected

- **Encrypting backups to the server's key:** a dead server would take its backups with it (S§3.9).
- **A control plane that can decrypt:** a stolen database plus one credential exposes everything (S§4).
- **Reading secrets with the recovery key day to day:** that key is only for granting, rotating and recovering (S§3.11).

## Open questions

1. **Where is an environment key pair generated?** The plan says where the private half is stored, not where it is made. Options: (a) the owner's CLI when the environment is created, so the private half never exists in a browser; (b) the browser, so the UI alone can create an environment but the private half passes through JavaScript we serve; (c) the first agent in the environment, which needs a server before the first secret. Decide before W3-1.
2. **Who re-encrypts during rotation?** S§3.11 names two executors: "an online agent in the environment, or the owner's CLI", and for recovery-key rotation "the old recovery key or an online agent". One must be chosen per case before W3-3. Note that in a protected environment an agent re-wrapping to recipients named by the control plane is what the `RewrapEnvKey` refusal exists to prevent.
3. **Form of the recovery key.** The plan says "a file or printed code". Whether both exist, and their format, is undecided.
4. **Who may reveal.** The plan does not say whether `secrets reveal` needs step-up or is available to agent identities. Step-up is listed for approvals, destructive operations and changes to secret recipients only (S§3.10).

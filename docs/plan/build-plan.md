# Moonglass — Build plan

_How Moonglass gets built, one ticket at a time. It builds on `vision.md` (V§n), `stack.md` (S§n) and `milestones.md` (M§n). The workflow that runs this plan is `.agents/skills/dispatch/SKILL.md`; `scripts/plan` reads the ticket list below and starts ready tickets in the order they appear._

**Short version**

- **Three milestones, in order, each a release people can run:** the **alpha** (the deploy path and the dashboard), the **launch** (the features most Coolify and Dokploy users rely on every day) and **v1** (everything else, with Cloud and Business). The list covers the whole product; nothing is parked outside it.
- **Dashboard first.** A ticket that adds a capability names its dashboard flow, in the same ticket or in a ticket of the same milestone, and the milestone's gate drives that flow. Nothing is CLI-only.
- Every change is one ticket, one branch `p/<ID>`, one PR, squash-merged when CI is green and review passes. The dispatcher routes each ticket: Opus plans it and reviews the diff, a worker model writes the tests and code and runs `make ci`, and the PR auto-merges on green CI.
- The owner is involved only for a new dependency, an unsettled security decision, or a contract or ADR change: those open a draft PR labelled `needs-owner`.
- Each group ends with a gate: an end-to-end ticket in CI and a demo on real servers. There are no dates; a milestone ships when its gate passes.
- Clean from the first commit. No placeholders, no fallbacks, no code for later tickets.

---

## 1. Risk labels

Each ticket carries one risk label. It decides how much testing and review the workflow demands (`.agents/skills/review/SKILL.md`).

| Risk | Applies to | Workflow | Owner |
|---|---|---|---|
| **high** | The trusted core in `AGENTS.md`: protocol, policy, keys, auth, store and migrations, registry authorisation and operations, browser key handling, install script and systemd units, release signing and self-update | Named acceptance tests in the brief; Opus writes or closely checks the subtle parts and reviews against the threat-model checklist | Reads every line of the merged diff in the weekly review. Only one high ticket is in flight at a time |
| **standard** | Deploy, agent runtime, proxy, server, API handlers, CLI, backups, import, notifications, dashboard screens | Named acceptance tests in the brief; Opus review | The test diff first, then error paths and anything touching Docker, the filesystem or the network |
| **low** | Docs, specs, scripts, fixtures, templates, benchmark, site | Tests when behaviour changes; Opus review | Skim |

Tests must be safe to run in two worktrees at once: ports from `:0`, temp data directories, and Docker resources labelled per test run and cleaned up afterwards. Up to three tickets run at once, each in its own worktree, and at most one of them is high.

## 2. Milestones and gates

Each gate is an end-to-end ticket that runs in CI, plus a demo the owner runs on the freshly reinstalled test fleet (M§1). **Stop rule:** a failed gate means fix tickets for the failure, and the next group's tickets depend on them.

| Milestone | Gate | Passes when | End-to-end ticket |
|---|---|---|---|
| Alpha | **G0** foundations | Repository and CI live with branch protection; threat model, ADRs and UI foundations; protocol v0. SPIKE-1 has measured the memory budget and decided ADR-0001, and the waitlist is live (M§2.2) | — |
| Alpha | **G1** skeleton | M§3 skeleton demo. Agent and proxy together ≤ 100 MB. Escape suite green | — |
| Alpha | **G2** deploys | Zero failed requests across ten deploys. Rollback < 5 s. A failing pre-deploy step leaves the old release serving. Deploy suite required in CI | W2-E |
| Alpha | **G3** git and secrets | A commit builds and goes live on the 2 GB box. The database holds only ciphertext. The disk-fill demo passes | W3-E |
| Alpha | **G4** alpha | On a fresh VPS one install runs server, agent and proxy. Sign in with GitHub, make the recovery key and an environment, connect a repository, set a secret, push, watch it go live, roll back, add a second server and upgrade, all in the dashboard and from the keyboard. Every open `high` fix ticket is merged and the quick start is written. **The alpha opens to the waitlist** | W4-E, W7-E |
| Launch | **G5** safety | Crash-loop rollback within 2 min with a Slack message. Shadow-mode report, then a real rollback after opt-in. A token scoped to staging is refused in production. A coding agent's production deploy over MCP waits in the Inbox and ships after an inline approval. Local policy refuses an unlisted registry. A deleted service restores | W5-E |
| Launch | **G6** data | Postgres and MySQL created from the dashboard, backed up, and restored onto a different server with only the recovery key, from the Restore button | W6-E |
| Launch | **G7** parity | From the dashboard: a Compose app with a database from a template, a Railpack build, a pull-request preview with its URL and teardown, a member invited as viewer who cannot deploy, metrics charts, and a Coolify import | LN-E |
| Launch | **G8** launch | Seven-day soak clean. Adversarial review findings fixed or documented as limits. Launch docs, benchmark and comparison page done. **The public launch** | W8-E |
| v1 | **G9** Cloud | A managed instance signs up, connects a server, deploys, upgrades in a staged rollout and exports to a self-hosted box with its agents re-enrolled. **Cloud opens, founding members first** | V1-E1 |
| v1 | **G10** v1 | Every v1 ticket merged, with its dashboard flow driven end to end; Business available; the external review done | V1-E |

## 3. Tickets

One line per ticket, read by `scripts/plan` (a test fails on a malformed line):

`- [ ] **ID** Title — intent · depends_on: IDs or — · risk: low|standard|high [· kind: human] [· paths: seed paths]`

- IDs are stable; renumbering is not allowed. New tickets get new IDs: `AL-n` in the alpha, `LN-n` in the launch, `V1-n` in v1, and `F…` or `FQ-n` in "Fixes and requests".
- `scripts/plan` starts ready tickets in the order they appear in this file, so the order of the sections is the build order: fixes and requests first, then the alpha, the launch and v1.
- A ticket is done when its box is ticked or a squash commit `<ID>: …` is on `main`. Ticket PRs do not tick their own box (concurrent PRs would conflict on adjacent lines); the weekly drift PR ticks every merged one.
- `kind: human` tickets are the owner's: agents never start them, and a ticket that depends on one waits until it is ticked.
- `paths` is where the work is expected to land; the brief may widen it, and the PR body says why.

## 4. Change control

- Contracts: the `.proto` files, registry operations, the `agent.toml` schema, the storage schema and the ADRs. A ticket that changes one in a way this plan or its spec does not already state needs the owner first: the dispatcher, on Opus's recommendation, opens a draft PR labelled `needs-owner` with the proposal and a recommendation, and the ticket waits until the owner removes the label. The change then lands as one ticket that updates every user of the contract and **deletes the old form**.
- No compatibility code before launch. There are no users, so there is nothing to stay compatible with.
- After launch, one narrow window. Because agents update in stages (S§3.14), the control plane speaks the current and the previous agent protocol version, and nothing older (ADR-0007 decision 7). It is the only compatibility code the product ever carries, and it is deleted one release later.
- Spikes are never merged. Their output is a document and a decision.
- A mistake repeated twice becomes one line in `AGENTS.md`, or better a lint rule or test. If `AGENTS.md` passes about 150 lines, it is too long; move the rule into a lint check.

### GitHub settings

What this repo's workflow needs on `github.com/moonglass-dev/moonglass`. Confirm or change them at the pages below.

**Settings → General → Pull Requests**
- Allow auto-merge (on). The dispatcher turns it on for a PR after Opus approves, with `scripts/plan merge`.
- Allow squash merging only (turn off merge commits and rebase merging).
- Automatically delete head branches.

**Settings → Rules / Branches** (ruleset or classic protection for `main`)
- Require a pull request before merging.
- Required approving reviews: 0. The bot is not an admin, so a required review would block every merge; Opus review is a PR comment, then the dispatcher squash-merges.
- Required status checks: only the aggregate check named `ci`. Do not require `lint`, `test`, `build`, or any Engine job on its own.
- Require branches to be up to date before merging: on. A PR that is behind `main` cannot merge until `main` is merged or rebased in.
- Block force pushes and deletions of `main`.

**Settings → Actions → General**
- Workflow permissions: read-only default `GITHUB_TOKEN`. Writes to GitHub go through `GH_CONFIG_DIR=~/.config/gh-moonglass-bot`.
- Require approval for GitHub Actions from first-time outside-collaborator fork pull requests.

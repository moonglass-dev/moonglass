## Findings

### 1. The pre-deploy executor detects "not running" by matching error text

- Evidence: `internal/deploy/predeploy.go:186-190` (`isNotRunning` returns true for any error whose text contains `is not running`), used at `internal/deploy/predeploy.go:168` to decide that a failed `ContainerKill` of the step container is not an error. This is new code from W2-6, the same pattern as R-2 finding 3 (`internal/deploy/engine.go:69-72`), whose fix ticket FR2-3 covers only `isNotFound`. It disagrees with `AGENTS.md` ("One way to do each thing", "No fallback, legacy or compatibility code", "Fail loudly") and `docs/specs/release.md` ("Executor: pre-deploy steps (W2-6)": over the limit "the container is killed and the step fails").
- Impact: any Engine kill error whose message contains "is not running" (a wrapped daemon or runtime error, or a different Engine version's wording among Engine 25 to 29) is swallowed. The executor then waits on a container it may not have killed, and the real cause is lost from the result.
- Fix ticket: FR3-1

### 2. The step-up rows can be created and read, but no store method approves, declines, confirms, counts or uses one, and W4-1c, which needs them, has no internal/store path

- Evidence: `internal/store/stepups.go:34` (`CreateStepUp`) and `internal/store/stepups.go:86` (`StepUp`) are the only step-up methods (`internal/store/store.go:359-366`); nothing writes `confirm_hash`, `signed_in_at`, `approved_at`, `declined_at` or `used_at` (`internal/store/migrations/sqlite/0007_link_tokens_step_ups.sql:19-25`), and `internal/store/stepups.go:13-16` never selects `confirm_hash`. `docs/specs/auth.md` ("Step-up", "Approving" and "Using") requires the callback to store the SHA-256 of a one-time confirmation value, `POST /step-up/{org}/{id}` to set `approved_at` or `declined_at` "only before the step-up expires, only once", at most 10 unexpired unused step-ups per user (429 for an 11th), and `Invoke` to mark the row used "in one transaction" with the audit event that carries `step_up_id`. The build plan gives that work to W4-1c, whose paths are `internal/auth/, internal/registry/, internal/api/, internal/cli/, internal/server/` (`docs/plan/build-plan.md:130`), with no `internal/store/`; W4-1b and W4-1f (`docs/plan/build-plan.md:128-129`) add only the read-only `UserByIdentity`. `docs/specs/storage.md` ("Nothing outside `internal/store` writes SQL") and threat-model B2 keep all SQL in the store.
- Impact: W4-1c cannot be built inside its allowed paths. Either it stops as blocked, or it widens into `internal/store` (trusted core, a storage-contract area) without a plan or locked conformance tests for once-only approval, the use-and-audit transaction and the per-user limit. Those are what make a step-up single-use and bound to one request.
- Fix ticket: FR3-2

### 3. A link token cannot be found by its bearer, and the link callback's one transaction has no store method or ticket path

- Evidence: `internal/store/linktokens.go:13` (`AddLinkToken` stores the hash) and `internal/store/linktokens.go:35` (`UseLinkToken` takes the link's row id and runs alone on `s.db`) are the only link-token methods (`internal/store/store.go:351-356`). There is no read by hash, unlike sessions (`SessionByHash`) and enrolment tokens (`UseEnrolmentToken(tokenHash)`), and no method that writes `user_identities` and marks the token used together. `docs/specs/auth.md` ("Linking") says `GET /link/{token}` takes the bearer and is authorised by "the unexpired, unused link token" ("Routes"), the round trip carries "the link token's row ID", and "On the callback, in one transaction: the token must be unexpired and unused; the identity must not belong to another user; the server writes the `user_identities` row and marks the token used". W4-1, which builds the landing, has no `internal/store/` path (`docs/plan/build-plan.md:131`).
- Impact: W4-1 cannot turn the bearer in `/link/{token}` into the row id without SQL outside the store, and cannot make the link atomic. With two separate calls, a token can be marked used and the identity not written, or an identity linked after another request linked it to a different user, which the spec says must change nothing.
- Fix ticket: FR3-3

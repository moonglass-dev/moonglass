## Findings

### 1. The CLI and the browser cannot reach the REST API: `--listen` presents only a self-signed key carrier, and plain HTTP is closed

- Evidence: since FR1-1, `--listen` serves TLS 1.3 only, with the control-plane key in a self-signed certificate (`internal/keys/tls.go:95`, `internal/server/server.go:260`, `internal/server/server.go:279`, `cmd/moonglass/main.go:73`). A plain-HTTP request gets no HTTP response. The generated CLI sends every call with `http.DefaultClient` (`internal/cli/cli.go:203`), which does Go's standard chain verification and has no pin, so it refuses that certificate. `checkURL` (`internal/cli/cli.go:223`, `internal/cli/cli.go:231`) still allows `http://localhost` and loopback addresses, but no Moonglass listener serves plain HTTP. docs/specs/enrolment.md:31 and docs/specs/registry.md:147 say "The CLI and browser reach the REST routes over standard HTTPS with Go's standard certificate verification". docs/specs/auth.md:82 sends the session as a `Secure` `__Host-` cookie on that listener. No spec, ADR or ticket says where a CA-verifiable certificate for the API comes from (a terminator in front of `--listen`, an ACME certificate on it, or a pin in the CLI). No test runs the CLI against `moonglass server`: the CLI tests use their own `httptest` servers (`internal/cli/url_test.go:73-82`).
- Impact: `MOONGLASS_URL=https://127.0.0.1:8080 moonglass servers list` against a real `moonglass server` fails certificate verification, and `http://127.0.0.1:8080` gets no answer. The owner token from `--print-owner-token` (docs/specs/enrolment.md:44, "how the owner gets a token for the CLI and for CI") cannot be used. W2-5, W2-E, W3-2 and the build-in-CI template of W3-4 all go through this CLI. A browser hits the same untrusted certificate for the session cookie and the UI. The loopback `http://` exception is permissive code with nothing behind it, and it invites a plain-HTTP listener the threat model does not allow.
- Fix ticket: FR6-1

### 2. Image removal decides "in use" by matching the text "conflict"

- Evidence: `internal/deploy/stop.go:227-231` (`isConflict` returns true for any error whose text contains `conflict`). `removeImage` (`internal/deploy/stop.go:219`) uses it to treat a failed `ImageRemove` as "left for the disk guard" and not an error. This is new code from W2-4, with the same pattern as R-2 finding 3 and R-3 finding 1. Their fix tickets, FR2-3 and FR3-1, cover only `isNotFound` and `isNotRunning`. It disagrees with `AGENTS.md` ("One way to do each thing", "No fallback, legacy or compatibility code", "Fail loudly"). It also disagrees with docs/specs/release.md "Keep five": only "an image the Engine still uses, or no longer has, is left for the disk guard".
- Impact: any `ImageRemove` failure whose message contains "conflict" is swallowed silently by retention, and `Run`'s `onError` never sees it. Examples are a wrapped daemon or registry error, or another Engine version's wording among Engine 25 to 29. The image stays on disk with no record that removal failed.
- Fix ticket: FR6-2

### 3. W7-6e must set `Heartbeat.update_channel` from agent.toml, but its build-plan line says nothing about it and it cannot reach the loaded policy

- Evidence: docs/specs/update.md:3, docs/specs/update.md:35 and docs/specs/protocol.md:65 (made final by FR5-2) say W7-6e sets `update_channel` from `update.channel` in agent.toml. The W7-6e line (`docs/plan/build-plan.md:217`) does not mention the field, and its paths are `internal/update/, internal/agent/, deploy/systemd/, scripts/install, internal/installtest/, docs/specs/install.md`, without `cmd/moonglass/`. It depends on W7-6a, W7-6b and W7-6d, but not on W2-10b. W2-10b is the ticket that loads agent.toml in `agent connect` with `policy.LoadFile` (`docs/plan/build-plan.md:95`). Today the agent's `ConnectOptions` carries no policy or channel (`internal/agent/connect.go:35-46`), and the Heartbeat sends only `agent_version` (`internal/agent/connect.go:189`).
- Impact: W7-6e can start before `--policy` exists, and it cannot pass the loaded `policy.Config` from `cmd/moonglass` into `internal/agent`. It then either blocks, or reads agent.toml a second way inside `internal/agent`, against "One way to do each thing" and ADR-0004 decision 5's single local-policy load. If the field is left empty, the spec means every agent is never offered an update.
- Fix ticket: FR6-3

### 4. The Caddy and coder/websocket import rules still use fixed file lists

- Evidence: `.golangci.yml:38-49` (`proxy-deps`) denies Caddy only in `cmd/`, `internal/agent`, `internal/keys`, `internal/protocol` and `internal/policy`. `deploy-deps` adds `internal/deploy`. `.golangci.yml:50-62` (`websocket-deps`) denies coder/websocket only in `cmd/`, `internal/protocol`, `internal/policy`, `internal/keys` and `internal/store`. ADR-0011 decision ("import it only from `internal/proxy`") and ADR-0012 decision ("import it only from `internal/agent` and `internal/server`") name one allowed package each. Nothing checks `internal/server`, `internal/registry`, `internal/api`, `internal/cli`, `internal/update`, `internal/release`, `internal/releasetest` or the packages the plan adds (`internal/auth`, `internal/build`, `internal/rollback`, `internal/compose`, `internal/mcp`). The same thing was fixed for age, Docker, Huma, pgx, modernc, compose-go and go-toml with `$all`-with-exclusion rules (FR1-10, FR2-4; `.golangci.yml:64-134`).
- Impact: a later ticket can import Caddy into the control plane or `internal/update`, or coder/websocket into `internal/api` or `internal/auth`, and `make lint` stays green. These are the import boundaries the ADRs set.
- Fix ticket: FR6-4

### 5. docs/specs/registry.md still gives the 11-field audit hash

- Evidence: docs/specs/registry.md:135 (`hash = SHA-256(JSON [prev_hash, org_id, seq, id, at, principal_kind, user_id, token_id, operation, outcome, reason])`). Since W4-1e the code hashes 13 fields, with `session_id` and `step_up_id` after `token_id` (`internal/registry/audit.go:18-19`, `internal/registry/registry.go:254`), as docs/specs/auth.md:200 says. W4-1e's paths did not include docs/specs/registry.md.
- Impact: `registry.md` is the spec of the registry that writes the chain. A reader, or a later ticket such as W5-1b or W5-5, recomputes the chain from it and gets a mismatch on every event, or builds the next hash change from the wrong base.
- Fix ticket: FR6-5

### 6. The executor redeclares the agent-state status `retired`, and the state package names the wrong ticket for new command types

- Evidence: `internal/deploy/stop.go:26` declares its own `statusRetired = "retired"` and compares `state.DueStop.Status`, which is raw status text (`internal/agent/state/stops.go:29`), against it at `internal/deploy/stop.go:91` and `internal/deploy/stop.go:99`. The status is owned by `internal/agent/state` (`internal/agent/state/state.go:31`, docs/specs/agent-state.md "Rules"). It disagrees with `AGENTS.md` ("One way to do each thing"). `internal/agent/state/state.go:35` says "W3-7 and W5-5b add more" command types. W3-7 is merged and added none. docs/specs/agent-state.md:56 says `build`, `stop_app` and `remove_app` come "from the tickets that add those commands", and for `build` that is W3-4 (`docs/plan/build-plan.md:119`).
- Impact: if the status text changes in agent state, the executor no longer removes retired containers at `stop_after`, while the row is still recorded as stopped and its `container_id` cleared. Their containers are orphaned, and retention then deletes their rows. The comment sends the W3-4 author to the wrong ticket.
- Fix ticket: FR6-6

### 7. The AGENTS.md repo map leaves out three product packages

- Evidence: `AGENTS.md:12` lists the packages under `internal/` as `agent`, `api`, `cli`, `keys`, `policy`, `protocol`, `proxy`, `registry`, `release`, `server`, `store` and `installtest`. `internal/deploy` (W2-3, the agent's executor), `internal/update` (W7-6a, trusted core per AGENTS.md "Trusted core") and `internal/releasetest` (W7-6c) exist and are not listed.
- Impact: every pipeline agent reads AGENTS.md first. The map hides the executor and a trusted-core package, so an agent that plans from it can put deploy or update code in the wrong package, or miss that `internal/update` is high risk.
- Fix ticket: FR6-7

### 8. The passing cases of `TestHealthGateHTTPPath` run under a 6-second limit that `make test` load exceeds, so `make ci` fails at random

- Evidence: `internal/deploy/switch_test.go:281` sets `x.healthLimit = 6 * time.Second` for every case, including the two `wantPass` cases (`internal/deploy/switch_test.go:289`). A passing gate needs `healthPasses = 3` probes in a row, `healthInterval = 1s` apart, and each probe may take up to `probeTimeout = 2s` (`internal/deploy/switch.go:22-26`). That is at least 2 seconds of passing probes after the container first answers, inside a limit that also covers reading its state and address (`internal/deploy/switch.go:124-142`). This leaves about 3 seconds for a fresh container to answer, while all four subtests run in parallel with the rest of `internal/deploy` under `-race` (`make test`). The tests that need a gate to pass elsewhere in the package use 20 seconds (`internal/deploy/domain_owner_test.go:26`, `:87`, `:135`, `:189`). docs/tickets/R-6/check.json (commit 6f3fe5b, a commit that changed no code) records `--- FAIL: TestHealthGateHTTPPath/302_passes_without_following_the_redirect`: `did not pass its health gate within 6s: GET http://192.168.158.2:8080/healthz: … context deadline exceeded`, with `internal/deploy` taking 365s. It disagrees with `AGENTS.md` "Definition of done" (`make ci` is green) and "Testing rules" (tests are safe to run in two worktrees at once). docs/tickets/W2-4b.md:70 asks only that a 3xx pass, not that it pass within 6 seconds.
- Impact: `make ci` can fail on any ticket's branch for reasons unrelated to its change, as it did for this review. The `make-ci` gate of `scripts/verify check` then fails rounds at random, and a worker under the "never weaken a test" rule cannot tell this flake from a real health-gate failure.
- Fix ticket: FR6-8

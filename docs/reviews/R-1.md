# R-1: Drift review 1

2026-11-18 · commit reviewed: 7e9a26211ac2e24f93be4aa4b5425a9ce6f6ccfa (branch p/R-1, from main after W3-7) · scope: every package under cmd/, internal/, scripts/, deploy/ and proto/, plus go.mod and .golangci.yml, against docs/plan/, docs/adr/, docs/specs/ and docs/threat-model.md. This is the first drift review, so there are no earlier reports in docs/reviews/.

## Findings

### 1. Enrolment and the registry REST API run over plain HTTP, the control-plane pin comes over that channel, and no ticket moves them onto TLS

- Evidence: `cmd/moonglass/main.go:70` (`--listen` is "enrolment listen address (plain HTTP)"); `internal/server/server.go:222` and `internal/server/server.go:229` (`serveEnrol` serves `s.Handler()` with no TLS, and that handler mounts `POST /v1/enroll` and every registry operation, `internal/server/server.go:91-104`); `internal/agent/enroll.go:104-108` (the agent posts the bearer token to whatever scheme `--url` names, `http://` included, and pins the `control_plane_public_key` from that response, `internal/agent/enroll.go:132-136`); `internal/cli/cli.go:90-97` (owner tokens go as `Authorization: Bearer` to any `MOONGLASS_URL`, `http://` included). `docs/specs/enrolment.md` ("HTTP endpoint") says plain HTTP is "for loopback tests and the walking skeleton only; B3 transport protection arrives with TLS in W1-4", but `docs/specs/connection.md` ("Out of scope") lists "Moving enrolment onto TLS", and no ticket in `docs/plan/build-plan.md` §3 does it. It disagrees with `docs/threat-model.md` §3 B3 ("TLS 1.3, the control plane's public key pinned at enrolment") and §2 Tokens (one-time and API tokens shown once, never exposed).
- Impact: an attacker on the path between a new agent and the control plane can read the enrolment token and replace the control-plane key in the `EnrollResponse`. The agent then pins the attacker's key, so the B3 pin protects nothing for that server. Owner tokens from `--print-owner-token` cross the same listener in clear text on any non-loopback deployment.
- Fix ticket: FR1-1

### 2. The control plane drops the agent's age recipient at enrolment, and no spec says where it is kept

- Evidence: `internal/server/enroll.go:34` checks the length of `agent_age_recipient`, but `internal/server/enroll.go:81` stores only the signing key (`AddServer(..., hex(agent_signing_public_key))`). `internal/store/migrations/sqlite/0001_init.sql` (`servers`, `agent_keys`) and `docs/specs/storage.md` ("Row-level tables", "Server deploy keys (W3-8)") have no column for it. `docs/specs/secrets.md` ("Granting", first server) has the owner's CLI "wrap the record to the agent's recipient", and ADR-0003 (keys table, "Agent key … the recipient for wrapped environment keys") makes that key the recipient of every agent-wrapped copy.
- Impact: W4-8 and W3-3 have no stored agent recipient to wrap to, so either the storage schema (a contract) changes in a high-risk ticket that did not plan for it, or a server has to be re-enrolled to report its key again. Every server enrolled before then has to be re-enrolled.
- Fix ticket: FR1-2

### 3. The agent's private keys and the control-plane pin are read and written by `internal/agent`, outside trusted core

- Evidence: `internal/agent/enroll.go:33-36` (file names `agent-signing.key`, `agent-agree.key`, `control-plane.pub`), `internal/agent/enroll.go:72-86` and `internal/agent/enroll.go:152-200` (load and atomic write of the private keys and the pin), `internal/agent/connect.go:264` (`loadConnectKeys` reads the signing key and the pin). It disagrees with ADR-0010 ("Those stay under `internal/keys`, in its own files"), `docs/specs/agent-state.md` ("Those stay under `internal/keys`, in its own files under the agent's data directory") and the heading "Agent identity (`internal/keys`, agent only)" of `docs/specs/enrolment.md`. `internal/keys` is trusted core (`AGENTS.md`, threat model §7); `internal/agent` is not.
- Impact: a change to how agent private keys or the pin are stored, such as file modes, atomic replacement or the pin check, gets standard review instead of the trusted-core review it needs, and W3-8 (deploy key) and W4-8 (wrapped key records) have no single owner for agent key files to build on.
- Fix ticket: FR1-3

### 4. `policy.LoadFile` skips the owner check when it cannot read the uid, and repeats its own checks

- Evidence: `internal/policy/parse.go:196` (`if uidOK && uid != owner`): when the uid cannot be read the owner check is skipped and the file loads. `internal/policy/parse.go:182-187` reads the uid twice (`fileUID`, then an `interface{ Uid() uint32 }` assertion that is never true for `*syscall.Stat_t`), and `internal/policy/parse.go:210` (`_ = ok`) keeps the unused result. `internal/policy/parse.go:189` already rejects group- and world-writable files and files that are not owner-readable, so the checks at `internal/policy/parse.go:193-195` and `internal/policy/parse.go:199-201` can never fire. The error returns at `internal/policy/parse.go:173` and `internal/policy/parse.go:209` have no context. It disagrees with `docs/threat-model.md` §6 ("The file is owned by root and is not writable by the service user"), and with `AGENTS.md` ("Fail loudly", "One way to do each thing").
- Impact: on a platform or file system where the uid cannot be read, an `agent.toml` owned by the service user loads, so the code that is meant to prevent a non-root writer widening local policy fails open. The unreachable branches hide which check actually runs, in a trusted-core file.
- Fix ticket: FR1-4

### 5. Dead code in the `data_dirs` check

- Evidence: `internal/policy/check.go:264-265` (`want := filepath.Join( /* mounts/project/name */ "", ev.dataName)` followed by `_ = want`) computes a value that is never used. `internal/policy/check.go:258` tests `b.project != ev.dataProj` after `internal/policy/check.go:254` has already returned unless `ev.dataProj == s.Project`, so the second half of the condition is always false. It disagrees with threat-model checklist item 8 (no unused branch) and `AGENTS.md` ("One way to do each thing").
- Impact: a reader of the trusted-core allow check sees a path comparison that looks like it constrains the mount source but does nothing. A later edit could rely on it.
- Fix ticket: FR1-5

### 6. The ADR-0005 token format is implemented twice

- Evidence: `internal/server/server.go:28-29`, `internal/server/server.go:36` and `internal/server/server.go:157-163` (enrolment tokens: their own `mg_` prefix, length, base32 encoding and generation), and `internal/server/enroll.go:93-99` (their own format check), duplicate `internal/registry/token.go:15-29` (`NewToken`) and `internal/registry/token.go:65-67` (the same check in `Authenticate`). It disagrees with ADR-0005 decision ("One format for every bearer secret") and `AGENTS.md` ("One way to do each thing"); threat-model §2 Tokens lists enrolment and API tokens under the one format.
- Impact: the format can drift between token kinds (length, alphabet, prefix), and only one copy is in trusted core, so a change to the enrolment copy gets standard review.
- Fix ticket: FR1-6

### 7. `/v1/agent` is described as an Ed25519 challenge-response, but it authenticates by mutual TLS

- Evidence: `internal/registry/routes.go:12` ("Ed25519 challenge-response with an enrolled agent key") and `docs/specs/registry.md` ("Routes and commands that are not operations": "agent listener, Ed25519 challenge") disagree with `docs/specs/connection.md` ("Transport": "mutual TLS"), which is what the code does: `internal/keys/tls.go:95-113` and `internal/server/agent.go:40-50`. `internal/server/agent.go:22-23` still says the route "joins the fixed route list when the operation registry lands (W2-1)", but it is already on that list.
- Impact: the fixed route list is where the threat model's B1 rule says each route's authorisation is declared (§3), and for this route it names a mechanism that does not exist. A reviewer checking the route against the list would look for the wrong check.
- Fix ticket: FR1-7

### 8. The agent unit cannot create the agent-managed data directory

- Evidence: `deploy/systemd/moonglass-agent.service:15` (`StateDirectory=moonglass/agent`) with `deploy/systemd/moonglass-agent.service:20` (`ProtectSystem=strict`) leaves `/var/lib/moonglass/agent` as the agent's only writable path under `/var/lib`. ADR-0004 decision 4 and `docs/threat-model.md` §6 say the data directory is `/var/lib/moonglass/mounts/<project>/<name>`, "created by the agent". `docs/specs/install.md` ("Units") names only `/var/lib/moonglass/{agent,proxy}`. No ticket in `docs/plan/build-plan.md` §3 that will create these directories (W2-3, W6-1) lists `deploy/systemd/` in its paths.
- Impact: the first deploy with a `data_dirs` allow fails with a read-only file system error. The ticket that hits it cannot change the unit without going outside its allowed paths.
- Fix ticket: FR1-8

### 9. `go.mod` is not tidy: direct dependencies are marked indirect, and unused modules are required

- Evidence: `go.mod:53` (`danielgtaylor/huma/v2`), `go.mod:103` (`jackc/pgx/v5`) and `go.mod:235` (`modernc.org/sqlite`) are marked `// indirect` although `internal/api`, `internal/store/pg` and `internal/store/sqlite` import them. `go mod tidy -diff` moves those three into the direct block and removes 59 other requirements, among them `go.mod:27` `github.com/BurntSushi/toml` (rejected by ADR-0009), `go.mod:71` `gin-gonic/gin`, `go.mod:84` `gofiber/fiber/v2`, and the Echo, Chi, gorilla/mux and bunrouter modules (ADR-0013: "No Chi, Fiber, Gin or other adapter is imported"). Neither `Makefile` (`ci:`) nor `.github/workflows/ci.yml` checks tidiness. ADR-0010, ADR-0013 and ADR-0015 each say the module is "pinned in `go.mod`".
- Impact: `go.mod` does not show which modules the product depends on, so the AGENTS.md rule "No new dependency without an accepted ADR" cannot be checked by reading it, and the go.sum and supply-chain surface include modules nothing imports.
- Fix ticket: FR1-9

### 10. depguard does not enforce the import boundaries ADR-0009 and ADR-0010 declare

- Evidence: `.golangci.yml:80-96` (`policy-deps`) denies compose-go, go-toml, pgx and modernc sqlite only in `cmd/` and `internal/protocol`. ADR-0009 says compose-go and go-toml are imported "only from `internal/policy`"; ADR-0010 says "Only `internal/store/pg` imports pgx. Only `internal/store/sqlite` and `internal/agent/state` import modernc." So `internal/server`, `internal/registry`, `internal/api`, `internal/agent` or `internal/proxy` could import pgx or modernc and write SQL with the lint still passing, breaking threat-model B2 ("Only the storage package writes SQL"). The comment at `.golangci.yml:81-83` says file exclusions "were not applied", but `.golangci.yml:61-69` (`huma-deps`, `$all` with `!**/internal/api/**`) uses them and works.
- Impact: the only automatic guard on the SQL and policy-parser boundaries covers two packages, so a later ticket can cross them without a lint failure.
- Fix ticket: FR1-10

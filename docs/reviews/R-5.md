## Findings

### 1. Switch and rollback route domains without the cross-app domain check, so two apps' routes can claim one host

- Evidence: the only domain check is `checkDomains` at Deploy (`internal/deploy/deploy.go:69`, `internal/deploy/deploy.go:92-116`). It compares the new release with other apps' *current* releases only. docs/specs/release.md "Order" step 3 says "a candidate of another app does not hold its domains". `SwitchRelease` (`internal/deploy/switch.go:74-79`) and `Rollback` (`internal/deploy/rollback.go:66-71`) call `Proxy.PushRouted` with no check. `withRouted` (`internal/deploy/proxy.go:169-188`) and `route` (`internal/deploy/proxy.go:192-203`) put each routed app's domains into its own `host` match, with nothing that removes duplicates. This can happen in two ways. First, apps A and B both deploy candidates for `x.example` while neither is current, and both switch. Second, A's previous release routed `x.example`, B then became current with `x.example`, and A rolls back. docs/specs/release.md "Proxy config" ("A domain that another app's current release routes is REJECTED at Deploy") and the "SwitchRelease" and "Rollback" steps say nothing about this. No test in `internal/deploy/switch_test.go` or `internal/deploy/rollback_test.go` covers it.
- Impact: the pushed Caddy config holds two `terminal` routes with the same host, and the one earlier in `app_id` order serves it. A switch or rollback answers `SUCCEEDED` for an app that gets no traffic for that domain. Or one service silently takes over a domain that another service of the org on the same server was serving. The Deploy rule exists to prevent exactly that.
- Fix ticket: FR5-1

### 2. The agent.toml channel values disagree with the Heartbeat `update_channel` values the specs say are copied from them

- Evidence: docs/specs/container-policy.md "agent.toml" (lines 313 and 327) and `internal/policy/parse.go:106-112` accept only `stable` or `canary` in lower case, and an absent key becomes `Channel: "stable"`. So `policy.Config` cannot tell an absent key from `stable`. docs/specs/protocol.md:65 says `update_channel` is `"STABLE"` or `"CANARY"` "from `update.channel` in agent.toml, byte for byte". The field is empty when `update.channel` is unconfigured, and such an agent is never offered an update. docs/specs/update.md §1 (line 35) says the same. `internal/protocol/heartbeat.go:38-45` rejects `stable` and `canary`. docs/specs/update.md:35 also says the field is "set by W7-6d", but W7-6d changed only `proto/` and `internal/protocol/`, and the agent's `Heartbeat` still carries only `agent_version` (`internal/agent/connect.go:189`).
- Impact: an agent that copies the file's value byte for byte, as the specs say, sends `stable`, and every heartbeat fails to open as malformed. A server with no `[update]` table reports `stable` according to container-policy.md and the parser, but according to update.md it reports empty and is never offered an update. W7-6e, which owns `internal/agent/`, has no single rule to implement, and no spec says which ticket fills the field.
- Fix ticket: FR5-2
